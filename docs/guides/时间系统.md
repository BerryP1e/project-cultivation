## 1. 它是什么

`时间管理器` 是**全局单例**（`Assets/Scripts/Time/时间管理器.cs`），到哪都在走。
它一个人管三件事：**纪年**、**修炼机会**、**跨天事件**。

| 项 | 值 |
|---|---|
| 取单例 | `时间管理器.取()`（订阅方和被订阅方必须是**同一个入口**，不能一边 `取()`、一边 `FindObjectOfType<时间管理器>()`） |
| 挂载 | **不写进场景**，由 `场景自举` 的 `补单例` 自动补（带 `DontDestroyOnLoad`） |
| HUD | `Assets/Scripts/UI/纪年HUD.cs`（右下角） |

它在养成闭环里的位置（**规则只写在 [炼丹](炼丹.md)**）：
`灵田（挂机产出灵草） → 炼丹（主动消耗） → 聚气丹（+修为）/ 破境丹（提破境成功率）`
时间系统的职责只有一个：**每过一天发一次修炼机会**。

> **第四阶段起，挂在同一套天数上的还有两样**（本文件不管它们的规则，只说明"共用哪个值"）：
> **日常循环**的今日清单（跨天刷新，比对的是 `时间管理器.当前天数`）与**两大伏笔的按天发酵**
> （灵田线每 2 天升一级异象）。两者都**不订阅 `过了一天`** —— 那个事件只在时间推进时发、
> **读档不补发**，所以它们都改成**比对当前天数**。见 [guides/日常循环](日常循环.md)。

## 2. 一天与纪年

**`秒每天 = 600`（10 分钟现实 = 1 游戏日）**。调这一个数，所有依赖日期的东西自动跟着变。

| 参数 | 默认 | 含义 |
|---|---|---|
| `秒每天` | `600` | 现实秒 / 游戏日 |
| `起始年` | `1` | 太虚历 1 年 = 开局 |
| `每月天数` | `30` | |
| `每年月数` | `12` | |

**`天数` 是唯一真值**（累加天数，不存日期）：

```
年 = 起始年 + 天数 / (每月天数 × 每年月数)
月 = (天数 / 每月天数) % 每年月数 + 1
日 = 天数 % 每月天数 + 1
时辰 = 把一天分 12 段
```

> 【为什么存"第几天"而不是存日期】存日期的话，改「一天多少秒」或改月天数
> 会让老档的月/日错乱；存累加的天数就永远自洽。

### 2.1 ⚠️ 为什么"不算离线时间"

设计稿里提到"离线挂机"，但**按现实时间戳算会失控**：10 分钟一天 ⇒ 离线一晚上回来就是几百天。

> **只用游戏内时间推进。关掉游戏，时间不走。**

好处：快慢完全可控、方便测试、数值不会失控。代价：没有「关掉游戏也在长」这个卖点。
**以后要做**，应该做成**独立的"离线收益"结算**（按真实时间给一笔资源），而不是让时间疯跑；
后者会把作物成熟、NPC 行为、任务时限全部带偏。

## 3. 修炼机会与修炼次数

**两套账本**，分开算、分开存，**只有花掉的时候才互相换算**：

| 来源 | 字段 | 存量 | 会过期吗 |
|---|---|---|---|
| **每日**（每过一天 +1） | `日常机会`（`天数 → 剩余次数` 字典） | 一场最多同时留 3 天 | **会**，第 4 天作废 |
| **打怪** | `打怪机会`（小数） | 小数累积，无上限 | 不会 |

| 参数 | 默认 | 含义 |
|---|---|---|
| `每日机会数` | `1` | 每过一天发几次（`<= 0` 就完全不发） |
| `机会保存天数` | `3` | 每日机会最多留几天 |
| `每日修炼上限` | `10` | **每天总共最多修炼 10 次**（日常 + 打怪合计） |

**消耗顺序：先花日常的**（它过期，先花更划算），日常花完再花打怪的。
`消耗一次修炼()` 返回是否花成功：先 `清理过期机会()`，再按上面的顺序扣。
打怪机会走 `加打怪机会(次数)`；任务直接发日常机会走 `加日常机会(次)`。

> 【为什么每日机会要"逐日记账"】要支持"最多保存 3 天、到期消失"，存一个总数就
> **没法知道哪一次是哪天发的、也就没法让它过期**。所以内部是 `天数 → 剩余次数` 的字典，
> 每过一天清掉太老的账（`清理过期机会`）。

### 3.1 跨天事件与 `处理跨天`

| 事件 | 签名 | 谁在听 |
|---|---|---|
| `过了一天` | `Action<int>`（新 `天数`） | `灵田.处理过了一天`、`纪年HUD.处理跨天` |
| `时间推进` | `Action<float>` | 要按帧看进度的界面 |
| `机会变化` | `Action` | HUD 刷新机会显示 |

推进在 `Update` 里按 `秒每天` 累加 `日内进度`；跨过 1 就 `天数++`、清过期账、发当天机会，再 `过了一天?.Invoke(天数)`。

### 3.2 ⚠️【坑】订阅必须 `OnEnable`/`OnDisable` + 先 `-=` 再 `+=`

**`Start` 订阅 + `OnDestroy` 退订不够**：`纪年HUD` 挂在主相机上，而主相机切场景时会被
`场景自举` **重新补组件** ⇒ `Start()` 又跑一次 ⇒ **每切一次场景就多一份订阅**
（实测 `过了一天` 的调用列表里 `处理跨天` 重复 3 次，跨天日志打 3 遍、日期像快了三倍）。

修法三条一起：① 订阅/退订放 **`OnEnable` / `OnDisable`**（Unity 保证成对出现）；
② 在 `OnEnable` 里**先 `-=` 再 `+=`**（即使被重复调用也不叠加），`OnDisable` 里 `-=`；
③ 订阅方和被订阅方用**同一个"取单例"入口**。通用规矩：**任何 `event +=`，
都要问一句"哪里 `-=`，会不会被调用多次"**。完整分析与代码见 [踩坑总库 H24](../ai/踩坑总库.md)。

## 5. 存档（版本 8）

| 字段 | 说明 |
|---|---|
| `天数` / `日内进度` | 纪年。**存累加天数，不存日期**（`日内进度` 是 0~1 的当天进度） |
| `日常机会` | 格式 `天数:剩余次数`，分号分隔（逐日记账的字典导出） |
| `打怪机会` | 小数 |

导入时：`打怪机会` 夹到 `>= 0`；`日常机会` 逐条读回字典；当天还没有账且 `每日机会数 > 0`
就补上当天的机会，再 `清理过期机会()`。

**老档（版本 < 8）走 `重置()`** 而不是套 0：版本 < 8 的档这些字段根本不存在，
直接套会让"今天的机会"永远不发。

## 6. 坑与遗留

### 6.1 已知的坑

| 坑 | 规避 |
|---|---|
| 只写 `Start` + `OnDestroy` 订阅 → 每次补组件都叠加 | `OnEnable`/`OnDisable` + **先 `-=` 再 `+=`**（见 3.2） |
| 混用 `时间管理器.取()` 和 `FindObjectOfType<时间管理器>()` | 统一走 `取()` |
| 存日期而不是存天数 → 改尺度后老档错乱 | 存累加 `天数` |
| 逐日记账直接套 0 → 老档"今天的机会"永远不发 | 版本 < 8 走 `重置()` |
| 让游戏内时间跟现实时间跑（离线挂机） | **别做**，要做就做成独立"离线收益"结算（见 2.1） |

### 6.2 还没做的

| 事项 | 说明 |
|---|---|
| **修炼动作** | `时间管理器.消耗一次修炼()` 已经能花机会，但"花掉后干什么"（加多少经验/走什么演出）还没接 |
| **离线收益结算** | 见 2.1 —— 要做就做成独立结算，别让游戏内时间疯跑 |
| **炼丹房 / 炼器房**（第二阶段） | 见 [炼丹](炼丹.md) |
| **镇妖塔挂机**（第三阶段） | 需求里塔改成"离线挂机试炼"，与现在的**手动刷塔**冲突，要先跟策划对齐 |
