## 1. NPC 的 AI 架构

```
NpcAiBase（抽象基类）  感知 / 状态机 / 移动 / 动画降级 / 出手 / 受击 / 死亡 / 收服预留
├── NpcAiAnimal        兽类
└── NpcAiCombatant（抽象）  索敌→追击→出手→脱战 的公共实现
    ├── NpcAiDemon     妖魔
    └── NpcAiHuman     人类
```

| 文件 | 作用 |
|---|---|
| `Assets/Scripts/Npc/Ai/NpcAiBase.cs` | 基类 + `NpcAiState` + `NpcAttackConfig` |
| `Assets/Scripts/Npc/Ai/NpcAiCombatant.cs` | 会打人的两类的公共逻辑 |
| `Assets/Scripts/Npc/Ai/NpcAiAnimal.cs` / `NpcAiDemon.cs` / `NpcAiHuman.cs` | 三种类型的差异 |
| `Assets/Scripts/Npc/Ai/NpcProjectile.cs` | 施法用的飞行道具（子弹） |

**子类只实现 `决策()`**（下一步想进哪个状态）；怎么走、怎么播动画、什么时候结算伤害全在基类。

### 1.1 自动装配（不用给 200 个 prefab 手动挂）

`NpcInstance.Start()` 会调 `NpcAiBase.确保(this)`：按 **`NpcDefinition.类型`** 自动加对应的 AI 组件。
- **prefab 上已经手动放了 AI 就不动它**（`确保` 直接返回），方便单独调参
- 只有「代码自动加的」才灌类型默认值（`应用类型默认值()`），否则会覆盖 prefab 上手调的数字
- 类型是「未指定 / 中立」→ **不加 AI**（村民、练功木桩就是这类）

### 1.2 配置表新增的两列

`NPC表.csv` 从 36 列变 **38 列**：`类型` = `兽类` / `妖魔` / `人类` / `中立` / `未指定`
（**成员名要和 `NpcKind` 枚举写得一模一样**）；`索敌范围` = 米，0 = 用该类型自己的默认值。
已按 id 前缀批量填好：`beast→兽类(11)` / `demon→妖魔(54)` / `human→人类(26)` / `npc·monster→中立(20)`。

### 1.3 三种类型的行为

| | 兽类 | 妖魔 | 人类 |
|---|---|---|---|
| 初始好感（表里） | 10~30 | −10 ~ −50 | 10 |
| **视玩家为敌的阈值** | **永不**（只会躲） | **≤ −10** | **≤ 9**（= 好感 10 及以上才友好） |
| 好感 > 60 | **凑过来跟随**，到 3 米停下 | — | — |
| 好感 < 10 | 玩家靠近就**躲开** | — | — |
| 挨打 | **朝反方向跑 3 秒** | 播 Wound + 短硬直 | 同妖魔 |
| 玩家进索敌范围 | 只是「注意到」 | **锁定玩家、主动上前打** | 好感掉下去之后才打 |
| 死亡 | 没动画 → **粒子消散** | 播 Death → 4 秒后销毁 | 播 Death → 5 秒后销毁 |
| 其他 | — | — | `可对话`、`收服()` 预留 |

**出手分工（策划约定）**：`Attack1` 走**普通攻击**，`Attack2` / `Attack3` 走**主动神通**
（默认 Attack2 = 物理主动神通，Attack3 = 特殊主动神通）。伤害在**动画播到 `出手进度`（默认 40%）时**才结算
（和 `首次造成伤害时间` 同一个思路）。`Attack2` / `Attack3` 可以勾 `是施法` + 填 `子弹特效路径`，走 `NpcProjectile`。

### 1.4 【坑】好感度曾经写在 ScriptableObject 上

原来 `NpcInstance.对主角好感度` 直接读写 `NpcDefinition.对主角好感度` ——
**那是个资产，运行时改会写回磁盘**，玩一次就把表里的初始值改脏了。
现在：**资产上的值只当初始值**，运行时用 `NpcInstance.运行好感度` 副本，对外接口名不变
（`对主角好感度` / `是敌对目标` 照旧），其他脚本不用改。
挨打自动掉好感在 `ReceiveAttack` 里做，`每次受击降好感` 默认 **20**（策划要求"极大程度降低"）。
⚠️ 这是**每次伤害结算**都掉 —— 焚天炎术那种多段 AoE 会掉很多次。

### 1.5 【坑】`SphereCast` 从自己体内出发会打到自己

`前方被挡()` 一开始用 `Physics.SphereCast`，球心起点在自己身上 → **每次都命中自己的胶囊**
→ NPC 一步都不动，日志里还什么都看不出来。改成 `Physics.SphereCastAll` + **过滤掉自己身上的碰撞体**。

### 1.6 【坑】攻击距离是「中心距」，填小了会死循环

妖魔 `攻击距离` 早期填 **2.2**，而它被物理挡在 **2.31 米**进不去 → `可出手()` 永远 false
→ 永远停在「接近」，看着像"AI 不工作"。**`攻击距离` 是两个 pivot 的中心距**，
要比双方碰撞体半径之和大一截。现在妖魔 3.2 / 人类 3.4。

### 1.7 ⚠️ 阻塞：NPC 现在**打不中玩家**（闪避公式问题）

实测：玩家 闪避 **0.08** / 忽视闪避 0.05；妖魔 闪避 0.06 / 忽视闪避 **0**。

`闪避率 = (受击方闪避 − 攻击方忽视闪避) ÷ 受击方闪避`
→ 妖魔打玩家 = `(0.08 − 0) ÷ 0.08 = **1**` → **100% 被闪避**，30 次一次没中。

**只要攻击方的「忽视闪避」是 0、而受击方闪避 > 0，命中率就是 0。**
这和「免暴率 / 免会心率公式反转」是同一类问题：**拿受击方的属性做分母**，
导致任何正数的防御属性都变成完全免疫。

**这是数值设计决定，没有擅自改。** 三个选项：
1. **改公式**（推荐）：`闪避率 = 受击方闪避 − 攻击方忽视闪避`，直接相减、clamp 到 [0,1]。
   和暴击/会心的修法一致，也符合"0.08 = 8% 闪避"的直觉读法。
2. **给 NPC 配「忽视闪避」**（数据改动）：让 NPC 的忽视闪避 ≥ 玩家的闪避。治标不治本，玩家闪避一涨又打不中。
3. **临时开关**：`NpcAttackConfig.必定命中` 勾上 → 无视闪避。**只为先验证 AI 链路**，不是长久方案。

> 落地状态见 **§2.7**（按第 1 个选项改成了 `闪避 ÷ (闪避 + 忽视闪避 + 闪避基准)`）；
> §1.7 保留为需求来源与决策记录。

### 1.8 怎么验证

```csharp
var 妖 = Instantiate(Resources.Load<GameObject>("NPC/Demon/BaiLuJing_01/BaiLuJing_01"), 位置, Quaternion.identity);
var ai = 妖.GetComponent<NpcAiBase>();       // Start 之后会自动装上 NpcAiDemon
ai.状态                                      // 待机 / 接近 / 攻击 / 受击 / 死亡
ai.出手 += (a, 配置, 结果) => Debug.Log(配置.动作名 + " " + 结果.伤害);
```

实测（Play Mode）：自动装配 妖→`NpcAiDemon`、兽→`NpcAiAnimal`、人→`NpcAiHuman` ✔；
妖魔 接近(9m) → 攻击(3.2m) → 出手 Attack3 命中 **188** ✔；妖魔伤害（开必定命中）玩家血 420 → **86.6** ✔；
野兽跟随 好感 80 → 凑到 3 米停下 ✔；野兽躲避 好感 5 → 远离 ✔；
野兽挨打逃跑 好感 20→0，逃跑中距离 6.71 → 9.41 ✔；
人类翻脸 好感 10（友好）→ 挨打降到 −10 → 视为敌 → 攻击 ✔；中立/木桩 不装 AI ✔。

## 2. NPC 资产修复

> 这一节全是**动画/碰撞体/Avatar** 层面的资产 bug，症状都是"看不出来但就是不工作"；
> 每个坑的修法都做成了菜单工具，可反复跑。

### 2.1 【bug】动画控制器是空壳，片段从来没接上

**这是"部分 NPC 动画没做好处理"的真正原因**，比 loop 设置严重得多：
- `Assets/Animations/NPC/*.controller`（101 个）里**所有状态的 `motion` 都是 `null`**
- 实测 `BaiLuJing.controller` **引用了 0 个 GUID** —— 只有状态名和过渡的空壳
- 真片段在 `Assets/resources/NPC/<类>/<名字>_Animation/<名字>@<动作>.FBX` **里面**（FBX 内嵌子资产，不是 `.anim`）
- `Gou` 更彻底：整个目录只有模型 `Gou.FBX`，**一个动画文件都没有**

好消息是**控制器的结构本身是对的**：参数 `Action:Int + Speed:Float`、`AnyState → 每个状态` 的过渡、
`Action Equals N` 切换 —— 这套机制没问题，缺的只是片段。

**修复工具**：菜单 **修仙 / NPC 资产 / 修复动画控制器**（先跑 **检查动画控制器（只读）** 看规模）。它会：
按名字找到 `<名字>_Animation` 目录和 `<名字>@<状态名>.FBX` → 把片段接回对应状态 → 顺手修循环
（**`Idle` / `Specialidle` / `Walk` / `Run` / `Fight` → 循环**，`Attack*` / `Death` / `Wound` / `Dodge` / `Deffence` → 一次性）。

> 【坑】FBX 内嵌的片段**不能**直接改 `AnimationClipSettings`（只读），
> 必须改 **`ModelImporter.clipAnimations[].loopTime`** 再 `SaveAndReimport()`。
> 所以这个工具会重新导入一批 FBX，慢是正常的。

### 2.2 【bug·已修·根因是 Write Defaults】NPC 姿势诡异 + 陷进地板

容易先入为主地怀疑贴地算法 / 挑错了身躯，但**狗的体型和命名跟白骨娘娘毫无共同点**，所以原因更底层。
**真正的原因**：`Animator` 的状态有个 **`writeDefaultValues`** 开关。它为 **true** 时，
进入该状态会把**所有没被动画驱动的属性重置成默认值**。而这些状态 **`motion` 全是 `null`**（见 §2.1）：

> 进入 Idle → 没有任何片段驱动骨骼 → **所有骨骼被重置成默认姿势** →
> 蒙皮网格当场塌陷成一团 → 姿势诡异，而且**整个网格沉到地面以下**。

和体型、命名、贴地算法都无关，所以**所有** NPC 都会中招。

**修复**（已执行）：`NpcAssetFixer.处理动画` 现在做两件事：① 把 `<名字>@<状态>.FBX` 里的片段接回每个状态
（**385 个状态接上**）；② 对**仍然没有片段**的状态关掉 `writeDefaultValues`（**保险**，实测 1 个）。
**执行结果**：101 个控制器，接上 **385** 个片段（另有 315 个本来就接好）、1 个片段缺失
（`逍遥子@Specialidle` —— **该 NPC 已于 2026-09-26 删除**）、2 个控制器没有动画资源（`Long_texiao` / `ZhanQi`）。

> **循环设置其实一直是对的**：实测 `Idle/Run/Walk/Fight` 的 `loopTime` 本来就是 `True`，
> `Attack*/Death/Wound` 本来就是 `False` —— 所以「0 个 FBX 需要改循环」。用户感觉"没设 loop"，
> 真正原因是**片段根本没接上**，不是 loop 标志错了。

> 剩下的 `标定贴地()`（用身躯渲染体最低点，而不是碰撞体底部）依然是对的，它是**第二道保险**。

### 2.3 【bug·已修】武器的包围盒被算进碰撞体

白鹿精的胶囊原来是 `height 2.6 / radius 1.3` —— 半径等于半高，等于一个球，乘根缩放 1.3 后直径 **3.4 米**。
于是它一靠近就把玩家挤出去，**永远够不到攻击距离**。

**按「体积最大的渲染体」挑身躯是错的**：白骨娘娘体积最大的是**飘带**（`BaiGuNiangNiang_02`，
体积 8.63 > 身体 4.76），飘带最低点在 **0.945 米高** → 拿它贴地会把 NPC 整个往下压 0.945 米。

**现在按命名挑**：
1. 先排掉名字带 `wuqi` / `weapon` / `武器` 的
2. 剩下的优先取**名字以 `_01` 结尾、且数字后缀最少**的那个（`BaiGuNiangNiang_01` ✓、`BLJ_01` ✓ 而不是 `BLJ_01_01`、
   `BaiXiongJing_01_01` ✓ 而不是 `_01_02`、`Changdaonv_01` ✓ 而不是 `ChangDaoNv_02`）
3. 都对不上（`gou` / `muji` 这种单网格）→ 取体积最大的
4. **安全阀**：第 2 步挑出来的高度不到「所有非武器渲染体并集」的 60% 就是小挂件 → 改用并集
   （实测 `BaiLuJing_02` 挑出来只有 **0.69 米**，并集 2.35 米 → 走安全阀 ✓）

包围盒用 mesh 的**绑定姿势本地包围盒**（`sharedMesh.bounds`）再算世界值，不用 `Renderer.bounds`
（当前姿势的动态值，没播动画时不可靠）。**已执行**：261 个 prefab **改了 272 个**（两轮）。
关键结果（旧 → 新胶囊）：`BaiLuJing_01`（`BLJ_01`）r=1.3 h=2.6 → **r=0.66 h=2.32**；
`BaiLuJing_02`（`BLJ_02_01`）r=1.25 h=2.51 → **r=1.18 h=2.35**；
`BaiXiongJing_01`（`BaiXiongJing_01_01`）r=1.62 h=3.24 → **r=1.25 h=2.5**；
`BaiGuNiangNiang_01`（`BaiGuNiangNiang_01`）r=1.19 h=2.62 → **r=0.68 h=2.15**。

> 胶囊参数是**本地空间**的，会被根缩放再乘一次（狗根缩放 10 → 本地 r=0.05 其实是世界 0.5 米，是对的）。

### 2.4 `类型` 列不该由我擅自决定（已修正）

按 id 前缀把 `npc` 那 19 个批量标成了 `中立` —— **这是越权**，用户已对照检查并把大部分改回 `人类`，
`NPC表.csv` 以用户改过的为准。

> **教训**：批量填数据列前先问一句，别替策划做分类决定。改了 CSV 记得跑导入器（有自动检查）。

⚠️ **遗留·还没做**：**没有攻击动画的「人类」会一直追着玩家但打不出来**
（`可用出手方式()` 为空 → `可出手()` 恒 false）。这类 NPC 应判定为"不参战"、停在待机而不是追人。

### 2.5 【bug·已修】挨打之后直接飞天（射线打到自己）

**现象**：母鸡被打一下，Y 从 0.02 **一路涨到 372 米**，而且是**匀速爬升**（≈41 m/s）。
匀速爬升 = **每帧棘轮式上升**，指向 `贴地()`：

```csharp
Vector3 起点 = transform.position + Vector3.up * 3f;
if (Physics.Raycast(起点, Vector3.down, out var hit, 12f, 地面层, ...))
    目标Y = hit.point.y + 贴地基准偏移;   // ✗ 射线先命中了【自己的胶囊顶】
```

射线从 `+3` 往下打，**最先命中的是自己的碰撞体顶部**，于是被摆到自己的顶上；
下一帧起点更高、又命中自己 —— 每帧涨「胶囊中心高 + 半径」，正好是那个匀速值。

> `前方被挡()` 里修过一次「排除自己」，但漏了 `贴地()` 和 `视线通畅()`。
> 现在三处统一走 `取首个外部命中()`（`RaycastAll` + 按距离排序 + 跳过自己的碰撞体），不会再漏。

**为什么只有母鸡中招、狗和妖魔不飞**：狗的胶囊是「薄片」（下半部分几乎贴地），射线往下第一个命中的是
**地面**而不是自己；母鸡的胶囊中心偏高，就先命中了自己。所以这个 bug **跟 NPC 体型强相关**，
换个 NPC 就可能复现 —— 不能只看一个案例就收工。

**顺带修的**：`Animator.applyRootMotion`。实测 **261 个 prefab 里 127 个开着**（`MuJi_01` / `Gou_01` 都开着，
`BaiLuJing_01` 是关的）。AI 用 `transform` 自己驱动移动，Root Motion 会和它打架 ——
循环片段（Idle/Walk）位移每轮抵消看不出来，**一次性片段（Wound/Attack）位移会累积**。
两边都处理了：运行时 `NpcAiBase.关掉RootMotion()` 兜底 + 菜单 **修仙 / NPC 资产 / 修复 Root Motion** 批量改资产。

> ⚠️ `LeiGong_02.prefab` 因为**本身有 Missing Script**，`SaveAsPrefabAsset` 会报错保存不了
> —— 这个 prefab 有问题，得手动清理。运行时的兜底开关能兜住它。

**实测（修复后）**：鸡 Y `0 ~ 0.02`、狗最高 `0.02`、妖最高 `0.002` ✔ 都不飞天。

### 2.6 【bug·已修】`Animator.avatar` 为空 → 动画完全不播（而且极难发现）

**现象**：白鹿精站在那儿**一动不动**。**根因**：`Animator.avatar = <空>`，而这些片段是**人形片段**
（`clip.isHumanMotion = True`、150+ 条**肌肉曲线**）。

> 人形片段**不会直接驱动骨骼** —— 它靠 **Avatar** 把「肌肉空间」的曲线重定向到实际骨架。
> **Avatar 为空 → 映射不上 → 一根骨头都不动。**

**为什么极难发现**：`NpcAnimator.CurrentAction` 在变 ✅、`Animator` 状态机在切换 ✅、Console 没报错 ✅，
但**蒙皮完全不动** ❌。**所以「动画在播」的验证必须验骨骼**：

```csharp
var 左手 = animator.GetBoneTransform(HumanBodyBones.LeftHand);
// 隔 0.12 秒采样 6 次，算最大位移；> 0.01 米才算真的在播
```
（`GetBoneTransform` 只在**人形 Avatar** 下有效 —— 顺便也验证了 Avatar 对不对。）

**修复**：菜单 **修仙 / NPC 资产 / 修复 Animator 的 Avatar**。Avatar 从**模型 FBX** 里取

### 2.7 【已修】闪避公式：两个大数算出 0~1 的概率

老公式（见 §1.7）拿受击方属性做分母，攻击方忽视闪避为 0 时闪避率恒等于 **1**。
新公式（`CombatCalculator.闪避基准` / `闪避上限` 可调）：

```
闪避率 = 闪避 ÷ (闪避 + 忽视闪避 + 闪避基准)
```

**`闪避基准` 和表里的数值同量级**：表里填小数就用 1（默认），填点数就改成 100。

1000,0 → 100% → **75%**（被上限压住）。

特点：**永远到不了 0 也到不了 1**（除非闪避为 0 = 必中），单调、无突变。

## 3. NPC 死亡粒子：落到地上再被玩家吸收

**需求**：杀死怪之后炸开的粒子**不要各自消散，而是落到地上**，**等待 1s**，之后**飞向玩家**、
在玩家身上消失，产生**被玩家吸收**的感觉。

### 3.1 四段

| 段 | 行为 |
|---|---|
| 1 **炸开** | 从身躯包围盒中心炸出一批粒子（起手和老的消散同量级） |
| 2 **落地** | 往下掉，**碰到地面就停住**（不再各自淡出） |
| 3 **等待** | 全部落地后原地停 **1 秒**（用户定的） |
| 4 **飞向玩家** | 加速飞向玩家胸口，**越近越小**，贴到身上就消失 = 被吸收 |

新文件 `Assets/Scripts/Npc/Ai/NpcAbsorbEffect.cs`（纯代码生成，不依赖美术资产；材质/贴图复用
`NpcDissolveEffect.取材质()` —— 那个方法为此从 private 改成 public）。
**开关**：`NpcAiBase.死亡粒子被玩家吸收`（**默认勾着**）。去掉勾 = 老行为（各自随机淡出）。

### 3.2 为什么这四段必须自己写，不能用 ParticleSystem 的模块

「**落地停住 → 再朝玩家飞**」是**逐粒子**的分段行为：`velocityOverLifetime` 是**整团一个向量**，
做不到每颗粒子朝各自方向飞向玩家；「落地」是**世界坐标上的一个碰撞点**，模块里根本没有。所以**完全接管**：

```csharp
main.startSpeed = 0f;          // ★ 粒子自己一步都不动
main.gravityModifier = 0f;     // ★ 重力也自己算
// 每帧：GetParticles → 手动积分位置 → SetParticles
```

> **两个容易漏的点**：
> 1. 手动写 `position` 之后，**ParticleSystem 还会用 velocity 再积分一次** ——
>    所以每帧都要把 `particle.velocity` 清 0，否则等于动了两遍。
> 2. **`colorOverLifetime` 必须关掉**。老消散的「各自随机淡出」就是它干的；
>    吸收版要粒子**全程是实的**，直到飞进玩家身上才消失。

### 3.3 实测时间线

```
击杀 t=0
 t≈0.7s   全部落地（人形怪 0.66 秒 / 境界 90 胖怪 0.87 秒）
 t≈0.7~1.7s  原地停 1 秒          ← 用户要的那 1 秒
 t≈1.7s   开始飞向玩家
 t≈2.09s  全部吸完、特效物件自己销毁（境界 90 是 2.35 秒）
```

证据：`screenshots/absorb_30_burst.mp4`（境界 1 人形 + 境界 90 胖怪各一次，3 倍慢放）、
`absorb_apex_lv1.png` / `absorb_apex_lv90.png`（最高点那一下的静帧）、`absorb_20_small.mp4`、
`absorb_20_landed_demon_bingpoguai_04.png`（粒子趴在地上那一下）。

### 3.4 **越近越慢**（否则会「擦过去绕回来」）

「全速 16 米/秒直冲玩家」实测有一颗粒子**从玩家旁边擦过去**：距离 2.02 → **3.06** → 才绕回来吸掉 ✗
现在期望速度 = `min(吸附最快, 距离 × 减速系数)`（默认 6）→ 远处全速、近处减速，是「被吸住」而不是「弹过去」。

### 3.5 尺寸与散布：**吸收版不吃那个 3 倍缩放**

根因是**复用了老消散的尺寸体系**：`NpcAiBase.播放消散特效()` 算出来的
`半径 = 身躯半径 × 死亡消散特效缩放(3)` —— 那个 **3 倍是给老的「爆发式消散」用的**（炸得又大又远、
各自淡出）。吸收版拿它当基准，粒子就变成半米多一团、飞出去两三米 ✗
现在**吸收版直接传「身躯半径」，尺寸/散布全部由 `NpcAbsorbEffect` 自己按身躯半径算**（以前 → 现在）：
传给特效的半径 身躯半径**×3** → **身躯半径**；单颗粒子大小 身躯半径×0.48~1.2 → **×0.10~0.22**；
初始散布 半径×0.85 → **×0.7**；粒子数（自动）半径×260 上限 160 → **按境界算**（§3.6），16 ~ 150。

### 3.6 粒子数按境界

`NpcAbsorbEffect.按境界算粒子数(境界)` = `clamp(round(14 + 1.25 × 境界), 16, 150)`：
境界 1/20/50/81/90 → 粒子数 **16/39/76/115/126**。
单个 NPC 想自己定数量的，填基类的 `死亡消散粒子数 > 0` 覆盖。
**实测峰值数 = 预期数**（境界 1/50/90 → 16/76/126，一颗不多一颗不少）。

### 3.7 ⚠️【坑】"炸开初速 = 身躯半径 × 系数"对**小体型**等于没有炸开

`爆开系数` 定成 2.2 时看着像调好了，其实没验证过。实测：

```
身躯半径 0.4（人形怪） → 初速 = 0.4 × 2.2 = 0.88 米/秒
重力 20 → 弹起高度 = v²/(2g) = 0.88² / 40 ≈ 0.019 米 ≈ 2 厘米
```

**2 厘米 = 肉眼完全看不出炸开**，粒子还是"直接落地" —— 正是用户抱怨的那件事。
（`爆开系数` 看起来"太大了"是因为当时还在乘那个 3 倍，半径是 1.2~1.5。）
**修法：先定"要弹多高"，再用 `vy = √(2gh)` 反推初速。**

```csharp
目标高度 = 爆开高度 + 每级爆开高度 × (境界-1) + 身躯半径 × 身躯高度加成
vy = √(2 × 重力 × 目标高度 × 随机(0.55~1.15))     // 逐粒子不同，整团才有层次
vh = vy / sin(仰角) × cos(仰角)                    // 仰角 = lerp(45°, 90°, 上抛比例)
```

这样**大怪小怪都能看到同样明显的炸开**，身躯大小只作为"再加一点"的加成项。

### 3.8 【坑】"落点硬夹回圈里"会让粒子落地变成一个**圆环**

落地时把超圈的粒子拉回圈边，初速变大后**所有飞远的粒子会一起贴在圆周上** → 看起来像个环 ✗
**修法：在发射那一刻就把横向初速压回圈内**（预测落点 = 横向初速 × 滞空时间）：

```csharp
滞空 = vy/重力 + √(2 × (出生离地 + 弹起高度) / 重力)
出生偏移 = 粒子出生点离中心的水平距离     // ★ 必须扣掉，否则球外侧出生的会飘出圈
想落 = 圈 × 随机(0.25~1.0) - 出生偏移
if (vh × 滞空 > 想落) vh = 想落 / 滞空
```

落地时的硬夹**保留成兜底**，并加了 `被拉回圈内数` 计数器好验证。**实测（应为 0）**：

| 境界 | 身躯半径 | 粒子数 | 弹起 | 落点半径实测 | 圈 | 被夹回 | 下落耗时 |
|---|---|---|---|---|---|---|---|
| 1 | 0.4（人形） | 16 | 0.71 米 | 0.12 ~ 0.47 | 0.60 | **0/16** | 0.66 秒 |
| 50 | 0.4 | 76 | 0.97 米 | 0.03 ~ 0.58 | 0.60 | **0/76** | 0.72 秒 |
| 90 | 0.8（胖怪） | 126 | 1.71 米 | 0.06 ~ 1.17 | 1.20 | **0/126** | 0.87 秒 |

整段四段流程自己走完并销毁：**2.09 秒**（境界 1）/ **2.35 秒**（境界 90）。

### 3.9 调参入口（都在 `NpcAbsorbEffect` 的 Inspector 上）

`大小系数`（乘身躯半径，**粒子大小**）= 0.10 ~ 0.22；`爆开高度`（米，**炸多高**）= 0.40；

### 4.2 【bug·已修】地面放焚天炎术「陷进地里」—— 动作的贴地补偿

**文件**：`Assets/Scripts/Core/PlayerAnimationController.cs`（只动了这一个）。
**症状**：不御风、站在地面放焚天炎术时人往下沉；御风时反而没事。
玩家 `Transform` 全程**不动**（实测 Y 恒为 −0.4431，`isGrounded` 恒 true）—— 沉的是**模型**，
不是角色控制器，别往重力 / 碰撞体那边查。

**根因**：`技能动作2` 是从别的角色**重定向**来的（和 §2.2 的 Write Defaults 同一类问题：骨骼被写成了不属于本骨架的高度）。
而那段"贴地补偿"代码**从来没生效过**：

> `记录髋骨高度()` 只在**两只脚都拿不到**时才给 `髋骨节点` 赋值 → 正常路径下 `髋骨节点` 恒为 `null`
> → `LateUpdate` 开头 `if (髋骨节点 == null) return;` → `已施加偏移Y` **全程恒为 0**。

**判据选谁（三个都实测过，别猜）** —— 焚天施法 / 普攻_远程_01：
全网格最低顶点 −0.25（陷）/ +1.75（悬空）；最低脚骨 −0.064 / +1.048；最低趾骨 −0.080 / +1.009。

- **不能用"全网格最低顶点"**：角色挂着**垂到脚边的长袍下摆 / 佩剑**，它们的顶点才是全局最低点
  （实测最低点恒在 `Y=−0.64`、离左脚 0.9 米）。钉住它 = 脚离地、人整个悬空。
- **不能用脚骨**：脚骨只是脚踝，会随脚踝转动失真（差 4 倍）。
- **结论**：判据 = **脚那一撮网格顶点** —— 用 `boneWeights` 取每个顶点的主骨骼，
  只留主骨骼 ∈ {脚、脚趾、小腿} 的（本角色 7893 顶点里筛出 744 个）。

**四个坑（都实测过）**：
1. **基准不能等到 `播动作` 里才量**。`播动作` 会 `animator.runtimeAnimatorController = 覆盖控制器`，
   Animator 重绑会把姿态搅一下，那一刻量到的脚底比真正站着时高 **0.166 米**，整套补偿把人托高 0.166 米。
   改成**每帧空闲时**记 `待用基准参照Y`，且必须在 `维护贴地补偿()` **之后**采样（收招那帧偏移在里面还回去）。
2. **增量要加在世界坐标**（`补偿根.position`）。补偿根 `Player_Visual` 的 `lossyScale = 1.8`，
   加在 `localPosition` 上收敛点虽对，但每帧只走一部分 —— 普攻那种「0.2 秒抬 1.75 米」会留下 **0.18 米**滞后。
3. **补偿根必须是「动画不写的那个物件」**（= Animator 所在物件 `Player_Visual`）。曾设成髋骨自己，
   动画写、每帧也写 → 数值发散，Hips Y 炸到 127 米。
4. 采样开销可忽略：`BakeMesh` + `GetVertices(List)`（List 重载免 GC）7893 顶点 **0.085 ms/帧**。

**一个开关：`允许下拉 = false`** —— **只治「陷下去」，不治「浮起来」。** 因为 `普攻_远程_01` 是拿
**嫦娥的浮空施法动作**重定向来的：整段悬空约 1 米、腿是收起来的，硬拉回地面会变成**蹲坐在地上**
（实测贴地后髋骨 −0.84 米）。素材库里真正站在地上的替代动作（按贴地后髋骨偏离排序）：
`WuNiang@Attack1` 0.085 米（另一个是 `逍遥子@Attack1`，该 NPC 已删除）。

`isGrounded` 恒 true；脚底高度残差 **0.01~0.02 米**（原来沉 0.25 米）；收招后模型根回到原位；

站着时下摆本来就在地面下约 0.15 米，属于美术表现；② `普攻_远程_01` 仍悬空约 1 米（嫦娥的浮空动作），不换片段。

### 4.3 【改动】凭虚御风：按住 Shift → **按一下切换**

改在 `Assets/Scripts/Abilities/YufengFlight.cs`，**只动这一个文件**（动画由 `御风.状态变化` 事件 +
`御风流程中` 那个 bool 驱动，速度由 `PlayerController` 读 `御风.御风中`，**都不读 Shift**，不用改别处）：

```csharp
public KeyCode 切换键  = KeyCode.LeftShift;    // 按一下起飞
public KeyCode 切换键2 = KeyCode.RightShift;   // 左右 Shift 都认
public bool 想飞 { get; private set; }         // 玩家「想飞」的开关
public void 切换()                             // 抽成公开方法：按键 / UI 按钮 / 测试都能用
```

**四条容易漏的规矩（都按这个实现了）**：

| 情况 | 行为 | 为什么 |
|---|---|---|
| **升空 / 落地过渡中再按** | **忽略** | 不然刚起飞就被自己按掉，动作会来回抽搐 |
| **灵气不足时按"开"** | **不接受**（保持关闭） | 否则会「按了关 → 灵气回满 → 自己又飞起来」 |
| **灵气耗尽自动落地** | **`想飞` 一起关掉** | 同上：不然灵气一回就自动复飞 |
| **`强制落地()`**（开面板 / 死亡 / 卸组件） | **`想飞` 一起关掉** | 关面板 / 复活之后不该自己飞起来 |

**实测（逐帧驱动 `切换()`，走真实施法路径）**：按一下 → `想飞=True` → 下一帧 `升空` → **0.86 秒**后
`御风`、高度 2.40 ✓；升空中再按仍是 `想飞=True / 升空` ✓（被忽略）；再按一下（御风时）→ `想飞=False`
→ `落地` → **0.71 秒**后 `地面`、高度 0 ✓；静置 2 秒（灵气已回满）仍 `地面 / False` —— **不会自己又飞** ✓；
灵气=0 时按"开"被拒绝，保持 `地面 / False` ✓；御风 3 秒（把 `回复倍率` 置 0 才量得到）
灵气 160.0 → 159.7、**实耗 0.301** = 0.1/s × 3 ✓；灵气清零 → 立刻 `落地` 且 `想飞=False` ✓。

> **测试踩的坑**：`PlayerVitals.回满()` 会把**灵气也补满**，测试里每帧调它会把消耗全盖掉；
> 而且玩家有 **灵力回复 4/秒**（`PlayerDefaultStats`），比御风的消耗还大。想量消耗必须**同时**
> 把 `回复倍率` 置 0 —— 这点也适用于以后任何"持续消耗"的验证。

> ℹ️ **一个已知但【用户明确说不用管】的数值现象**：**灵力回复 4/秒，御风只耗 0.1/秒** →
> 飞行时灵气其实在**净涨**（+3.9/秒），所以「**灵气耗尽自动落地**」这条规则**实战中基本永远不会触发**，
> 飞等于免费。**别去调它。** 代码里那条自动落地路径本身是**对的、也验过**（见上表最后两行），
> 只是暂时用不上；以后真要收费，把神通表里的「维持消耗灵力」提到 4 以上即可。

## 5. 白熊精：纯近战（按动画进度出伤）

**一句话**：`Attack1` 是普攻、`Attack2` 是主动神通，**两招全是物理**；
出伤**按动画进度**在「武器砸到人身上」那一刻结算，**命中特效和出伤同一时刻**播。

`NpcAiBase.攻击中()` / `立即命中()` 出伤时刻不变（`出手进度`），`立即命中` 以前**一个特效都不放**，现在统一放命中特效。

| — | `Attack3` | 不用（动作名留空） | | | | |

**出手进度是【实测】出来的（换模型/改动画要重新量）** ——

|---|---|---|

### 5.1 ⚠️ 为什么【不做】「用武器网格实时判定」

用户否掉了这一版（原话：*"既然你出伤都没有按照网格碰撞来，那么特效应该配合出伤，
在出伤时播放特效，就不用网格碰撞检测了"*）：

1. 那个判定本质上是「**胸口点落在一个大 AABB 里**」，而熊的武器盒有 2~4 米大 —— 等价于距离判定，
   并不比按进度出伤更"准"，但更难预期；
2. **特效必须跟出伤同步**。网格判定下出伤发生在"盒子刚碰到人"的那一帧，
   可能早于武器视觉上砸到的那一刻，特效就会提前闪 ✗
3. 每帧烘焙顶点 + 每帧碰盒的开销（~0.05ms/帧 × 每只怪）也省掉了。

> 实测数据（武器前伸多少米）**没有浪费** —— 它正好用来定 `出手进度`。
> 同理，`NpcBodyBounds.取武器实时包围盒()` 那套也一起删了（要用的话按上面的量法重写即可）。

### 5.2 ⚠️【bug·已修·老代码就有的】Attack2 播不完

用户报的：*"白熊精的 attack2 明明有将近 1.25 秒，但是它播不完"*。
**根因**：`攻击中()` 用 `Animator.GetCurrentAnimatorStateInfo(0).length` 当"这一招多长" ——
但那一帧动作刚 `SetInteger` 切过去、**状态还没切完**，读到的是**上一个状态**的长度：
战斗里 NPC 的待机是 **`Fight` = 1.333 秒**（就是用户看到的"将近 1.25 秒"）；
Attack2 = **1.867 秒** → 在 1.333 秒被 `收招()` 砍断 ✗；Attack1 = 1.4 秒，和 Fight 只差 0.07 秒 → **一直没人看出来**。

**修法**：新增 `NpcAnimator.取动作长度(动作名)`，**按"我请求播的那个动作"**去控制器里查片段长度。
受击那条（`Wound`，0.733 秒）有同一个毛病，一并修了 —— 以前挨打会僵直 1.3 秒而不是 0.733 秒。
**实测（修完）**：`Attack1` 状态持续 1.403~1.406 秒（片段 1.4）、`Attack2` 持续 **1.873 秒**（片段 1.867）✓

### 5.3 站位：中心距 2.5 米（武器最远伸到身前 **3.44 米**）

> ⚠️ **【坑·已修】近战的「攻击距离」要按观感定，不是按「判定框够不够得着」定。**
> 按"武器能伸 3.44 米"填了 **3.2** 时判定完全打得到（45 秒 10/10 命中、命中距离稳定 3.19 米）——
> **但用户一眼就看出「武器没打到玩家身上」**：武器尖只是刚够到人，等于站在极限距离用武器尖捅空气 ✗
> 改成 **2.5 米**后：武器能伸 3.44 米，等于**整条武器从玩家身上扫过去**。实测 Attack2 在 **72%~86%**
> 这段窗口里武器盒**一直盖着玩家人心**；`screenshots/bx_02_attack2_78.png` 能看到棍子横着压在玩家身上。

> 底线是别穿模：熊胶囊半径 ~1.45 + 玩家 0.4 = 1.85 米，所以 2.5 米安全。

### 5.4 冷却的【真实含义】

`冷却` 是**从收招（动画播完）开始算**的，所以两次命中之间的实际间隔 ≈ **动画长度 + 冷却 + 后摇**：

**想让"两次神通正好隔 10 秒"，把 `神通冷却` 调到 8 左右。**

## 6. 命中特效：所有物理攻击最起码要有一个

**需求**：**所有物理属性的攻击**都要有一个**基础命中特效**；部分高级攻击可以用更高级的。
特殊（法术）攻击各自有各自的表现，不强制。

**机制（三条伤害路径以前全都没有特效）**：

| 路径 | 以前 | 现在 |
|---|---|---|
| `立即命中()`（够近就命中，**白熊精走的就是这条**） | **完全没特效** | 在玩家胸口放 |
| `在目标结算()`（飞弹命中） | 只在**自己配了** `命中特效路径` 时才放 | 走统一入口，物理攻击自动兜底 |
| ~~`武器判定()`（近战·武器网格）~~ | — | **已删**（见 §5.1：不做网格判定了） |

**出伤和特效是同一个时刻**（都在 `攻击中()` 的 `出手进度` 那一下），所以看起来就是"打到身上的那一下"。
核心就两个方法（都在 `NpcAiBase`）：

```csharp
// 这一招该放哪个特效（空 = 不放）
取命中特效路径(配置)：
    1. 这一招自己配了 命中特效路径 → 用它（★ 高级攻击走这条）
    2. 没配、但是【物理】伤害     → 用 物理基础命中特效（默认 FX/Hit_Physical）
    3. 特殊伤害又没配             → 不放

// 在命中点放出来；朝向 = 从命中点指向攻击者（火星朝攻击者溅）
生成命中特效(配置, 命中点, 朝向)
生成命中特效(配置, ICombatTarget)      // 打在某个单位身上，自动取判定点 + 朝向
```

两个开关：`NpcAiBase.物理基础命中特效`（默认 `FX/Hit_Physical`）—— 全 NPC 共用的基础特效；
`NpcAttackConfig.用命中特效`（默认**勾着**）—— 只有"一秒打十几下"的多段攻击才需要关掉；
`NpcAttackConfig.命中特效缩放 / 命中特效存活` 已有，继续可用。

> **只在 `命中 && 伤害 > 0` 时才放** —— 被闪避就不放，这样"打没打中"一眼能看出来。

### 6.1 特效是自己做的（不依赖第三方特效包）

菜单 **修仙 / 构建命中特效**（`Assets/Editor/Builders/HitFxBuilder.cs`），全部程序化生成：

| 产出 | 说明 |
|---|---|
| `Assets/resources/FX/Hit_Physical.prefab` | **基础命中**：细四芒星闪光（0.62）+ 15 颗拉伸火星 |
| `Assets/resources/FX/Hit_Physical_Heavy.prefab` | **重击**：更大星芒（1.15）+ **26 颗**火星（更快更久） |
| `Assets/resources/FX/Textures/*.png` | 程序化画的贴图：星芒（64px）/ 光点（32px） |
| `Assets/resources/FX/Materials/*.mat` | 加色混合粒子材质 |

朝向约定：**预制体的 +Z 指向"攻击者"那一侧**（和飞弹命中特效一致），
所以调用方传 `Quaternion.LookRotation(攻击者位置 − 命中点)`。
两个粒子层都是 `playOnAwake` + 世界空间 + 一次性爆发，销毁交给调用方。

> **重击曾经有一个「冲击光环」，用户说有点突兀，已经删掉了**（贴图 / 材质 / 粒子层全删了）。
> 现在重击和基础的区别只靠**星芒更大 + 火星更多更快**。要加环回来的话注意：
> 环和星芒同心会读成"白色齿轮"，而且环晚 0.03s 出现才像冲击波。

### 6.2 高级攻击怎么用更高级的（白熊精就是例子）

```csharp
普攻.命中特效路径 = 普攻命中特效;        // 留空 → 自动用基础物理特效
神通.命中特效路径 = 重击命中特效;        // "FX/Hit_Physical_Heavy"
神通.命中特效缩放 = 1.15f;
```
实测解析结果：`Attack1（物理）→ FX/Hit_Physical`、`Attack2（物理）→ FX/Hit_Physical_Heavy` ✓

### 6.3 四个坑

1. **星芒和光环不要同心叠**。基础和重击都做"星芒 + 光环"时，两者同心叠在一起，40ms 那帧看着像个**白色齿轮** ✗
   （后来环干脆整个删了，见上。）
2. **`清掉飞弹配置()` 以前把 `命中特效路径` 也一起清了**。白熊精神通刚设好的重击特效被自己抹掉、
   又退回基础特效（实测解析出来是 `FX/Hit_Physical`，不查根本发现不了）✗ 命中特效**不是飞弹专属**，不能清。
3. 星芒的尖要**细**（`σ≈0.03`）。太粗 = 齿轮感。
4. **截图要隔一帧**：粒子是 `Instantiate` 之后**下一帧**才模拟出来的，
   出伤那一帧立刻 `Camera.Render()` 拍到的是**还没有粒子**的空画面。

`BasicSword01HitEffect`（飞剑穿过敌人炸一簇火花）、`BasicRemoteAttack01`（弹道 / 闪光 / 命中三条路径都有）
—— 侧重点不同，没并到这套里。

## 7. 冰魄怪：近战普攻 + 冰弹神通

`Attack2` 是**特殊**冰弹（动画 63% 从**左手**射出，12 秒冷却）。
文件：`Assets/Scripts/Npc/Ai/NpcAiBingPoGuai.cs`（一个类覆盖 `BingPoGuai_01~04`）。

### 7.1 招式

| 招 | 动画 | 属性 | 类别 | 倍率 | 冷却 | 出手进度 | 打出去的是 |

### 7.5 ★★ 根因：动画的「转体」烘在 Root Motion 的根旋转里，被 `applyRootMotion = false` 丢掉了

用户一步步描述出来的现象（原话）：
> 「正常应该是向前挥出的手臂会附带一个转体……但是你可能设计了怪的 ai 要时刻朝向玩家，所以导致了实际上右手刺歪了」
> →（改完还是歪）「……**他手臂向后蓄力时身体没有转过来，侧身送出手臂时身体也没有转过来，好像身体转不过来一样**」
> →「最开始是对着正下方的，经过扭动，最后对着右下方，然后攻击用的手指向了最开始的方向，
> **说明动画是没问题的，只要攻击过程不转向玩家就行**」

**「身体转不过来」是钥匙。** 量下来：`Animator.avatar` = **`BingPoGuaiAvatar`（Humanoid）**；
Attack1 的根路径曲线 = `RootT.x/y/z` + **`RootQ.x/y/z/w`** + 一堆肌肉曲线（`Spine Twist Left-Right` …）；
`Bip01` 根骨骼自身的偏航（Play 定格 / 自然播，两种方式）**全程 0°**。
也就是说**「转体」不在骨骼上，在根变换的 `RootQ` 里**。而 `NpcAiBase.关掉RootMotion()`
当年为了治「Wound/Attack 位移累积、挨一下飞天」，把 `applyRootMotion` 直接设成了 `false` ——
**那等于把 `RootT` 和 `RootQ` 一起丢掉**，于是转体没了、手刺歪 ✗
> 当年那个 `false` 治的是**位移**（RootT），治过头把**旋转**（RootQ）也一起杀了。

**修法：`applyRootMotion = true` + 自己实现 `OnAnimatorMove()`，只吃旋转、丢掉位移。**

```csharp
// Awake
接管RootMotion();      // 设 applyRootMotion = true

/// 只要实现了 OnAnimatorMove，Unity 就不再自动应用 root motion —— 由我们决定怎么消费
protected virtual void OnAnimatorMove()
{
    if (动画 == null || !强制关闭RootMotion) return;
    if (状态 != NpcAiState.攻击 || !攻击期间锁定朝向) return;
    if (自己 != null && 自己.IsDead) return;

    transform.rotation *= 动画.deltaRotation;   // ★ 只吃旋转
    // deltaPosition 一律丢掉 → 不会「挨一下飞天」
}
```

- `applyRootMotion` 必须是 **true** —— 不是要它自动应用，而是**只有 true，Unity 才会调 `OnAnimatorMove`**
- **攻击中不能锁 `transform.rotation`**（加过硬锁，会把刚找回来的转体又摁掉）

**实测**：运行时 `applyRootMotion = True` ✓｜攻击期间根节点**开始跟着动画转了** ✓
｜受击 1.5 秒内位移 **0.000 米**（没飞天）✓

## 9. NPC 变体的称呼：由弱到强（不许叫 01/02/03）

**一句话**：拆分脚本本来给每个蒙皮版本起名「`白熊精01` / `白熊精02`」，
用户要求「**不要直接起 01，02，03，给这些 npc 一个由弱到强的称呼，编号越低越弱、越高越强**」。
现在变成 **`白熊精·幼 / 白熊精·壮 / 白熊精·悍 / 白熊精·王`**。

### 9.1 两套称号（顺序就是强弱，别乱调）

| 类型 | 由弱 → 到强（8 档） |
|---|---|
| **妖魔** | 幼 · 少 · 壮 · 猛 · 凶 · 悍 · 霸 · 王 |
| **人类** | 微末 · 寻常 · 出众 · 拔萃 · 超群 · 绝顶 · 盖世 · 无双 |

> **人类为什么不用「初学 / 小成 / 宗师」那套**：人类那一列里**平民和神仙是混着的** ——
> 既有 老头 / 李村医 / 山城土匪，也有 嫦娥 / 哪吒 / 杨戬。用修士进阶的词会出来「**嫦娥·初学**」
> 「**老头·大家**」这种一眼别扭的名字 ✗（那套试过，截图一看就不对，换成了气势档次的词 —— 凡人和神仙都读得通。）
>
> 想换词：只改 `NpcVariantSplitter.妖魔称号` / `人类称号` 两个数组，再跑一次
> **修仙 / 配置表 / NPC 称号按版本命名** 就会整表重排（见 §9.3 坑 2）。

### 9.2 怎么分档

家族内按**境界升序**排名，把 8 个称号**均匀铺开**：第一个 → 称号[0]，最后一个 → 称号[7]。
即 `idx = round(第几个 × 7 / (共几个 − 1))`，所以不会重词：
2 版 → 幼 / 王（微末 / 无双）；3 版 → 幼 / 凶 / 王；4 版 → 幼 / 壮 / 悍 / 王；5 版 → 幼 / 少 / 猛 / 悍 / 王；
8 版（山城土匪）→ 八个全用上。实测：`山城土匪·微末 → 寻常 → 出众 → 拔萃 → 超群 → 绝顶 → 盖世 → 无双`
（境界 31→90）✓

### 9.3 三个坑

1. **★【坑·已修】不能再靠「名字以 NN 结尾」来认变体行。**
   原来是靠这个条件做到两件事：认拆分行 + **顺带排除手工家族**。名字一改成「白熊精·壮」，
   这个条件就永远不成立 —— 再跑一次递推会**整表跳过**（看着像"没坏"），而一旦有人把它去掉，
   又会**把白鹿精的 1/4/10 冲成 1/11/21、赤蟒精的 21/51/71 冲成 21/41/61** ✗
   现在改成：**只看 id**（`<基>_NN`），手工家族用**显式名单**排除（`NpcVariantSplitter.手工家族` =
   `demon_bailujing / demon_chimangjin / demon_guiqijiang / demon_mingyao`）。
2. **只改「本步骤管得着」的行**，所以手工起过名的一个都不动：冥妖·一 / 鬼气将·帅 / 火狼 / 土地公 / 铁匠……
   > 判定见 `名字可重排()`：`<原名>NN`（以数字结尾）或者 `<原名>·<梯子上已有的称号>`。
   > 第二种是为了**能换一套词重跑**。注意：**换词时如果新梯子和旧梯子的词完全不重叠，就认不出来**了 ——
   > 这时得先从备份（`D:/project：cultivation/_backup_NPC表_*.csv.bak`）恢复再跑（换人类的词就是这么做的）。
3. **`手工家族` 要连递推一起排除**，不只是不重命名。她们的境界是手工分档的（白鹿精 1/4/10、赤蟒精 21/51/71），
   递推会按「每版一大档」重算，直接冲掉。

### 9.4 结果

- 改了 **207 行 / 67 个家族**；`名字以数字结尾的行 = 0`
- 手工家族一分未动：白鹿精 1/4/10、赤蟒精 21/51/71、鬼气将 31/51/71、冥妖 31/41/51/61 ✓
- 名字同时是**真灵列表里的显示名**（`NpcDefinition.名字` → `DisplayName`），也是击杀日志里的名字
  —— 所以列表里看到的就是「白熊精·悍」这种
