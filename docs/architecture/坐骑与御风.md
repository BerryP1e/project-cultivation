### 1.1 ★【坑 1】巨龙小了 **25 倍**，而且看起来像"碎掉了"

刚导入时巨龙的包围盒只有 **0.11 米**（11 厘米），`capture_asset` 渲出来是一堆**白色尖片**，第一眼像网格坏了。实际查下来：`bindposes` 53 个对 53 根骨骼、**没有一个是 null**（全是"旋转 + 极小平移"）→ **绑定是完整自洽的**；`fileScale = 0.01`（FBX 按厘米）、`globalScale = 1` → 原始网格只有 **19 个单位**；那些"尖片"其实是它**展开的破烂翅膀**，套上贴图后一眼就是条龙。

**修法**：`ModelImporter.globalScale = 25` → 3.64 米。**凡是显示"碎成片"的先量包围盒和 bindpose，别急着判死刑**；先对齐尺寸 + 接上贴图再看。

### 1.2 ★【坑 2】`.fbm` 文件夹不能改名，但引擎能自动接上

3ds Max 导出 FBX 时会生成同名 `.fbm` 文件夹放贴图，FBX 内部按相对路径引用。**保持原样复制过去**，Unity 的 `ImportViaMaterialDescription` 就能自动把 `_MainTex` / `_BumpMap` 都接上（神龙 8 个材质 8 个都接上了，连法线都对）。`Hair` 那个只有 `_D`、没有 `_N`，所以它没有法线 —— 那是素材本身就没有，不是导错。⚠️ **所以神龙的 FBX 和 `.fbm` 目录名故意没改**：`01-环绕飞行.fbx` 内部按**相对路径**引用 `01-环绕飞行.fbm\T_xxx.png`，改名两边就对不上了；文件夹是 ASCII（`ShenLong_01/`），代码路径干净就够。

### 1.3 【坑 3】巨龙的贴图要手动接

它的 FBX 里材质叫 `BossLeiLong`，但贴图文件叫 `dragon.png` / `dragon-No.png`，**名字对不上**，所以 Unity 没搜到。手动建材质接上即可。另外 `dragon-No.png` 要**手动把 Texture Type 改成 NormalMap**，否则当普通贴图用会很难看。

### 1.4 规范化收尾

1. **提外部材质**：项目约定材质放 `<资产>/Materials/*.mat`（FBX 内嵌的不好改）。神龙 8 个（`MI_MB1SuiguangMd00501Body` → `ShenLong_01_Body` …）、巨龙 1 个（`JuLong_01.mat`）、碧水兽 1 个（`BiShuiShou_01.mat`），用 `ModelImporter.AddRemap(new AssetImporter.SourceAssetIdentifier(typeof(Material), 原名), 新材质)` 重映射回去。
2. **法线贴图**：`dragon-No.png`、`Pet_Bishuishou_N.tga` 都设成 `TextureImporterType.NormalMap`。
3. **循环标记**：`CINEMA_4D___`（神龙）/`ZhanLi`/`XingZou`/`Idle*`/`FightRun` 设 `loopTime = true`；攻击、死亡、出生、升级等一次性动作 `false`。

> ⚠️ **片段名一个都别改**。用户明确说过「**我还没有为这三份资产的动画改名**」—— 命名是他的事。改过的话还原办法：`mi.clipAnimations = new ModelImporterClipAnimation[0]; mi.SaveAndReimport();` —— 清掉片段覆盖后 Unity 会**从 FBX 的 take 重新生成**，拿回来的是真正的原始名字（比手打猜测靠谱，`CINEMA_4D___` 后面到底几个下划线原本是猜的）。改完片段名记得同步：控制器里的**状态名** + prefab 上 `NpcAnimator.动作列表`。

### 1.5 骨架类型为什么是 Generic（和现有坐骑不一样）

现有坐骑（`LangQi_01` / `ZhanQi_01`）是 **Human** + `avatarSetup = CreateFromThisModel`，动作 FBX 用 `CopyFromOther` 指向基础模型的 Avatar。**但龙/兽必须用 Generic** —— Human 要求有人形骨架映射（头/脊柱/双臂/双腿），套在四足龙身上是错的。所以这三套保持 Unity 自动判定的 **Generic**。

> Generic 的 `avatarSetup = NoAvatar`、`Animator.avatar = null` **是正常的**，不是漏配：Generic 片段按**层级路径**绑定（实测 8 个片段各 360~390 条曲线，**失配 0 条**），不需要 Avatar。**别按现有坐骑那样硬塞一个 Avatar 进去**。

### 1.6 建的架子：控制器 + prefab（用户同意先留着）

**不是统一模板** —— 每套按**它自己的动画数量**配（用户强调过"每个坐骑都会有独立的脚本，动画的数量也不同"）：神龙 `Assets/Animations/NPC/ShenLong.controller`（1 个状态）+ `ShenLong_01.prefab`；巨龙 `JuLong.controller`（6 个状态）+ `JuLong_01.prefab`；碧水兽 `BiShuiShou.controller`（8 个状态）+ `BiShuiShou_01.prefab`。

控制器结构照抄现有 `LangQi.controller`：参数 `Action`(Int) + `Speed`(Float)，一个动作一个状态，靠 `AnyState → 状态` 且 `Action Equals <索引>` 切换，`writeDefaultValues = true`（和 `LangQi` 一致；"状态没 motion"那个坑才发作，这里每个状态都有片段，所以安全）。

prefab 根上：`Animator`（`applyRootMotion = false`、`cullingMode = AlwaysAnimate`）+ `NpcAnimator`（`动作列表` 按索引顺序填好）+ `CapsuleCollider`。**没挂 `NpcInstance` / `NpcIndicator`** —— 那要配定义资产和 NPC 表，属于坐骑系统本身。

### 1.7 还没做的（属于"坐骑系统"本身）

- `NpcInstance` + `NpcIndicator` + NPC 表行
- 每个坐骑**各自的脚本**
- 贴图没用上的通道：碧水兽的 `_E`（自发光）/ `_S`（高光）/ `_M`（遮罩）

### 1.8 导入后的渲染实测

三只摆一排、各自套上动作采样后都能正常渲染（`screenshots/mount_all_posed.png`）。接上控制器后逐个动作播一遍，**姿势确实各不相同**（`mount_anim_test.mp4`）—— 碧水兽 `Idle` 2.05×1.55×2.04 / `FightRun` 1.93×1.26×2.12 / `HuDong` 1.81×1.62×1.76 / `Birth` 1.39×2.73×0.95 / `Die` 1.05×2.34×1.04；巨龙 `ZhanLi` 2.87×2.71×1.72 / `XingZou` 3.17×3.27×2.33 / `SiWang` 1.92×3.85×1.87（6 个全不同）。

> 【坑·用户报的】"**播什么动画都是待机的样子**" —— 根因是**当时根本没有控制器**（只导了资产），不是片段坏了。另外 Animation 窗口对纯动画 FBX 会显示「No model is available for preview」也**是正常的**：那 8 个动作 FBX `SkinnedMesh=0 MeshFilter=0 材质数=0`，里面没有模型可显示，得把基础模型拖进预览区。

## 2. 坐骑表与坐骑页

用户给了概念图「坐骑ui（i键唤出，默认境界）」，要求先实现 UI，再「**对照着那个被动神通的表以及现有的坐骑资产，弄一个坐骑的表，表头基本一致的**」。

### 2.1 坐骑表（`Assets/Data/Tables/坐骑表.csv`）

**表头 = 被动神通表 的写法照搬**，只把神通专属的几列换成坐骑的：身份列是 `坐骑id` `坐骑名称` `坐骑品阶` `修炼门槛` `模型资源路径` `待机动作` `介绍`；增益列**逐字照抄被动神通表**共 15 列：`气血增益` `攻击增益` `防御增益` `灵力增益` `移动速度增益` `暴击增益` `暴击抗性增益` `闪避增益` `冷却缩减增益` `攻速增益` `气血回复增益` `灵力回复增益` `普攻伤害减免增益` `主动法术伤害减免增益` `被动法术伤害减免增益` —— 共 22 列 × 9 行。**列名 = 字段名**，属性列由 `TableSpec("坐骑表", typeof(MountDefinition), "增益", "增益")` 自动识别（剥掉「增益」后缀 → 匹配 `AttributeUtil.GetDisplayName`）。

> ⚠️ **数值是按品阶编的占位值**（门槛 1/10/20/25/30/35/45/60/75 由弱到强），用户还没定数值，要调就改 CSV 再跑一次 **修仙 / 从配置表生成资产**，别去改 `Assets/Data/Generated` 下的资产。9 套坐骑：`灵翅(黄品1)` `狼骑(玄品10)` `灵鹿(玄品20)` `碧水兽(地品25)` `熊猫坐骑(地品30)` `战骑(地品35)` `麒麟坐骑(天品45)` `巨龙(天品60)` `上古神龙(仙品75)`。

### 2.2 ★【坑】坐骑 prefab 不能用 `NpcPrefabs.加载`

`NpcPrefabs.加载` 靠「挑带 `NpcInstance` 的那个」来避开同名 FBX 的坑，但**坐骑 prefab 上没有 `NpcInstance`**，用它会把 FBX 挑出来。坐骑的判别条件换成 **`NpcAnimator`**：实测三个新导坐骑的 **FBX 根节点上没有 `Animator`**（`Animator: 无`），而组装好的坐骑 prefab 一定有 `Animator` + `NpcAnimator`。所以 `MountPrefabs.加载` 的优先级是：**带 `NpcAnimator` → 带 `Animator` → 第一个（并警告）**。

### 2.3 坐骑页（`UIMountPage.cs` + `CharacterPanelBuilder.BuildMountPage`）

布局照概念图：上半是**坐骑 idle 动画展示（3D）**（`RawImage + RenderTexture`），下半左边「拥有的坐骑 [滚动条]」、右边「选中坐骑信息」。

**3D 预览不用加图层**：在 **y = −4000** 开一块「口袋场地」，把坐骑实例、3 盏点光、一台相机都放那儿。相机 `clearFlags = SolidColor`、`farClipPlane = 60`，游戏世界在 4000 米外进不了视锥 → **只画得到坐骑**，不需要改 `TagManager`。

> ⚠️ **灯必须自带**：那地方是空的，没灯坐骑全黑。要用**点光**（range 18~26），**不能用平行光** —— 平行光照亮全世界，会把游戏场景一起点亮 ✗
>
> ⚠️ **预览实例的 Animator 必须 `cullingMode = AlwaysAnimate`**：Unity 会按「离相机远」剔除 Animator，表现是**姿势冻住不动**。

页签顺序按新概念图**重排过**：`背包 / 境界 / 神通 / 法宝 / 灵阵 / 战阵 / 坐骑`（原来是 `境界…背包`，`背包` 从最后挪到最前，`坐骑` 新增在最后）。

### 2.4 【坑】面板打开时 `timeScale = 0`

`CharacterPanelUI` 打开时会把时间停住。写验证脚本时 **`yield return new WaitForSeconds(...)` 会永远等不到**（`yield return null` 还正常），表现是脚本卡死直到 bridge 超时。**改用 `WaitForSecondsRealtime`。**

### 2.5 实测

`I` 唤出 → 切「坐骑」页：**只激活 1 个页面**、列表 **9 行**（按门槛由低到高）、滚动条正常、四个坐骑来回点都能换预览 —— 灵翅 6.5% / 巨龙 6.0% / 上古神龙 1.9%（蛇形龙细长，占比本来就小）/ 碧水兽 3.4% 非背景像素，预览模型分别叫 `预览_灵翅` / `预览_巨龙` / `预览_上古神龙` / `预览_碧水兽`。证据：`screenshots/mount_page.png`。

> 信息栏那个**品阶色方块**（天品是淡紫）**不是丢贴图**：`MountDefinition.图标` 没填时 `UIEntryInfo` 用 `UIEntryRow.TierColor(品阶)` 当占位底，和其它页一个行为。想要真图标就往表里加一列 `图标`（`Sprite` 字段已经有了）。

## 3. 坐骑系统

### 3.1 需求要点

> 「所有的坐骑都有 4 个状态：上坐骑，坐骑行进中，坐骑待机，下坐骑」
> 「按 e → 上坐骑：先播御风升空到场景中现在的高度，碧水兽同时播 birth，**两个动画对齐一下时间**，都结束后进入 行进中/待机」
> 「待机 = 坐骑 idle + 玩家御风idle；行进中 = 坐骑 fightrun + 玩家御风前进」
> 「再按 e → 下坐骑：御风落地落到地面，碧水兽播 levelup 并在过程中消散，同样对齐时间」
> 「骑乘坐骑时无法开始御风，但是同样不会掉高度，除此之外只是借用了动画」

### 3.2 新增 / 改动

| 文件 | 作用 |
|---|---|
| `Assets/Scripts/Player/MountRider.cs` | **新增**。四态状态机 + E 键 + 高度管理 + 坐骑生成/消散 |
| `Assets/Scripts/Abilities/YufengFlight.cs` | 加 `禁止切换`（骑乘期间屏蔽 Shift 起飞） |
| `Assets/Scripts/Core/PlayerController.cs` | 加 `坐骑` 接线；骑乘时 `ApplyMountHeight()` 接管高度、速度用坐骑速度 |
| `Assets/Scripts/Core/PlayerAnimationController.cs` | 加 `设置外部御风` / `触发升空` / `触发落地`（坐骑**借用**御风四片段） |
| `Assets/Scripts/UI/UIEntryInfo.cs` | 操作按钮加**坐骑分支**：装备坐骑 / 取消装备 |

**动画时间（资源实测，默认值就是它们）**：

```
坐骑 BiShuiShou：Birth 2.67s  LeveUp 2.03s  Idle 4.00s  FightRun 1.00s  applyRootMotion=False
玩家 PlayerLocomotion：御风_升空 0.90  悬停 2.00  八向移动各1.333  御风_落地 0.70
参数：Speed(float) Flying(bool) FlyMoving(bool) FlyX(float) FlyY(float) TakeOff(trigger) Land(trigger)
```

**对齐做法：两段各自按原生速度播，短的先放完就停在结束状态等长的那个**（不拉伸动画速度）：上坐骑总时长 = max(0.90, 2.67) = **2.67s**（玩家 0.90s 升到位后转 御风_Idle，等坐骑出生完）；下坐骑总时长 = max(0.70, 2.03) = **2.03s**（玩家的落地段**推迟到 1.33s 才触发**，让「脚踩到地面」和「坐骑消散完」同时发生）。**「规划 Birth 开始点」靠 `applyRootMotion = False` 解决**：坐骑不会被动画带着跑，所以出生动画直接在骑乘位播放，播完它自然已经在待机位置上 ✓

### 3.3 ★★【坑·已修】坐骑的 CapsuleCollider 把骑手弹飞

碧水兽 prefab 根上带一个 `CapsuleCollider`（非 trigger），骑手是 `CharacterController` —— 两者套在一起互相顶，实测**下坐骑时人被弹到 33 米高**（`t=0.00 Y=5.64 → 0.88 Y=28.47 → 1.30 Y=33.31`）。速度远超高度控制的 ±10m/s → **不是高度控制的锅，是 `CharacterController.Move` 的穿透修正**。

**修法：生成坐骑后把实例上所有 Collider 关掉**（坐骑本来也不该挡住自己的骑手）：`foreach (var c in 坐骑实例.GetComponentsInChildren<Collider>(true)) c.enabled = false;`

修完实测：`Y 轨迹 = 5.6 5.4 4.4 3.0 1.5 0.6 0.1 0.0`，最高点 5.64 ✓ 单调落地。

### 3.4 ★【坑】摆位时挪动 `Player_Visual` 是会留在运行时的

用户为了摆位把 `Player_Visual` 挪到本地 `(-3.249, 4.100, -2.930)`。**但 `PlayerAnimationController` 的贴地补偿是 `补偿根.position += Vector3.up * 增量` —— 只改 Y，不会把 X/Z 拉回来**，所以这个位移运行时**会留下**（角色模型偏出 3.2m）→ 已把 `Player_Visual.localPosition` 复位为 `(0,0,0)`（本地缩放 1.801 保持）。

> ⚠️ 这串 **-4.85 后来被推翻**（按网格中心对的，被撑大的包围盒带偏了），定稿见 §5.2。

### 3.6 【坑·已修】用户实测的三条反馈

**① 角色朝向歪 ~90°：`Player_Visual` 被转过 76.42°** —— 用户报「往上时朝右、往下时朝左、往左时朝上、往右时朝下」；实测 `Player_Visual.localEulerAngles = (0, 76.42, 0)`，**摆位时顺手转的**（§3.4 只复位了位置、没管旋转）。修法是 `视觉.localEulerAngles = new Vector3(旧.x, 0f, 旧.z);` —— **只清 yaw、保留 X**：模型物件自己的 `(270,0,0)` 是 FBX 的 Z-up 补偿，动了模型就躺下。修完 `forward 与玩家根一致度 = 1.000`。

**② 上坐骑后和碧水兽方向没对齐 —— 和 ① 同一个原因**：碧水兽的朝向是正的（从骨骼算：头/脚尖都在 +Z），是玩家模型歪了 76° 才显出错位。① 修完 `坐骑/玩家朝向一致度 = 1.000` ✓ **不需要给坐骑加额外 yaw 偏移**。

**③ Birth 动画"碧水兽卡住了" —— `NpcAnimator` 实例化当帧还没就绪**：`NpcAnimator.PlayAction` 开头是 `if (!已就绪 …) return false;`，而 `已就绪` 在 `Start` 才置位；在 `Instantiate` 的**同一帧**就调了 `PlayAction("Birth")` → 返回 false → **出生动作根本没放上**，碧水兽停在默认姿势，看起来就是"卡住"。**修法：每帧重试，成功为止**（`尝试上坐骑` 里不要直接播，改在 `更新上坐骑` 里 `if (!出生已开播) 出生已开播 = 播坐骑动作("Birth", false);`）。修完实测出生期间 `坐骑动作 = Birth` 连续保持 2.67s ✓（可用动作表：`Idle/FightRun/HuDong/IdleSpecial/IdleSpecial01/Birth/LeveUp/Die`）

> **通用教训**：**运行时 `Instantiate` 出来的物件，不要在同一帧调它的 `Start` 类初始化**。要么延后一帧，要么像这里一样重试。

**④ 顺带按用户要求加了「上坐骑时静止」**：`PlayerController` 里 `bool 坐骑过渡 = 坐骑 != null && 坐骑.过渡中;` 时把 `targetSpeed` 压成 `0f`，实测下坐骑过渡中 `当前速度 = 0.00` ✓

### 3.7 【历史】御风与坐骑双向拦截（现行规则见 §7.5）

用户追加要求：「**御风时无法召唤坐骑**」。当时**两个方向都挡**：骑乘中 → 不许起飞（`MountRider.锁住御风()` 置 `YufengFlight.禁止切换 = true`）；御风中 → 不许召唤坐骑（`MountRider.尝试上坐骑()` 开头 `if (御风.御风流程中) { 提示; return; }`）。

**为什么要双向挡**：御风有自己一整套高度控制（`YufengFlight.地面高度 + 高度偏移`），坐骑也有一套（`MountRider.角色目标高度` → `PlayerController.ApplyMountHeight`）。只挡一边的话会进入"飞行中上坐骑"的叠加态 —— 两套高度系统同时往 `CharacterController` 里写，状态谁也不管谁。`御风流程中` 包含 **升空 / 御风 / 落地** 三段，过渡中按 E 也会被拦住。实测：御风中按 E → `骑乘状态=未骑乘、坐骑实例=无` ✓；落地后按 E → 正常骑上 ✓；骑乘中按 Shift → 仍在地面 ✓。按键后来统一成 Shift、规则改成"装备坐骑自动停用御风、启用御风自动取消装备坐骑"（§7.5），`尝试上坐骑` 里的硬拒绝现在换成 `御风.强制落地()` + warning。

### 3.8 【功能】骑乘时坐骑与玩家**朝向分离**

用户要求：「当坐骑在前进中时，假如玩家有锁定，那么此时**坐骑是朝向移动方向的**，而**玩家是朝向锁定方向的**，直到移动停止，坐骑再转向玩家朝向」。**玩家侧不改**（用户明确说「玩家就是原来的那个锁定面向敌人的方法就好，这个已经有了的」，`PlayerController.FaceDirection` 里原有的锁定面向逻辑一行没动），**只改坐骑侧** `MountRider.摆坐骑(float 角色Y)`，把位置和朝向**分开算**：

```csharp
// 位置：始终挂在玩家根上、用**玩家朝向**算偏移
//   ★ 不能用坐骑朝向 —— 否则坐骑一转向，玩家就从背上滑到侧面去了
t.position = 基准 + transform.rotation * 坐骑相对偏移;

// 朝向：行进中 且 有锁定 → 朝移动方向；其他情况 → 跟玩家朝向
float 目标Yaw = 玩家Yaw;
if (行进中 && 有锁定 && 移动方向.sqrMagnitude > 0.0001f)
    目标Yaw = Quaternion.LookRotation(移动方向.normalized, Vector3.up).eulerAngles.y;

当前坐骑Yaw = Mathf.MoveTowardsAngle(当前坐骑Yaw, 目标Yaw, 坐骑转向速度 * Time.deltaTime);
t.rotation = Quaternion.Euler(0f, 当前坐骑Yaw, 0f) * Quaternion.Euler(坐骑朝向);
```

**"移动停止后坐骑再转回玩家朝向"是 `MoveTowardsAngle` 自然产生的**，不需要额外判断停步事件 ✓ 新增参数：`坐骑转向速度`（默认 240 度/秒）、`目标管理器`（自动找 `NpcTargeting`，判断有没有锁定）。实测（反射直接驱动，不依赖键盘输入）：

```
锁定练功木桩，玩家 yaw = 288.2（与目标方向夹角 0.0°，即原来的锁定面向）
① 行进中(+X) + 有锁定：坐骑 yaw = 90.0   玩家 yaw = 288.2   ✓ 两者分向
② 停止后            ：坐骑 yaw = 288.2  玩家 yaw = 288.2   ✓ 转回玩家朝向
③ 行进中但无锁定    ：坐骑 yaw = 288.2  玩家 yaw = 288.2   ✓ 不分流，跟玩家
```

> **测试技巧**：坐骑的"行进中"依赖键盘输入（`MoveDirection` 来自 `Input.GetAxisRaw`），自动化测试推不动。用反射设 `行进中` 与 `PlayerController.MoveDirection` 两个属性、再把 `坐骑转向速度` 设成 0（瞬时）后直接调私有的 `摆坐骑(float)`，就能确定性地断言朝向，不用等帧、也不受输入影响。

### 3.9 【功能】朝向怎么跟角色走：三种方式，**每只坐骑自己配**

用户两轮要求：「上古神龙和翅膀类似，是**相对角色的位置卡死的**，其实更类似一个**环身的特效**」→「**让龙和翅膀也有点不一样，翅膀是直接锁死的，让龙就变成平滑缓慢的插值吧**」。所以**不再用类里的字符串列表**（`朝向始终跟玩家的坐骑 = {...}` 已删除），改成 `坐骑摆位` 里的两个字段（每只坐骑自己一条）：

| 字段 | 说明 |
|---|---|
| `朝向跟随` | `分离` / `硬跟玩家` / `平滑跟玩家` |
| `跟随速度` | 只在「平滑跟玩家」时用（度/秒），**越小越慢越飘** |

| 方式 | 谁用 | 行为 |
|---|---|---|
| `分离`（默认）| 其余 7 只 | 行进中且有锁定 → 朝移动方向；停下转回玩家朝向。速度用全局 `坐骑转向速度`(240) |
| `硬跟玩家` | 灵翅 | 每帧**直接等于**玩家朝向，完全不插值 |
| `平滑跟玩家` | 上古神龙 | 每帧 `MoveTowardsAngle` 缓慢追上玩家朝向，速度用这只坐骑的 `跟随速度`(45) |

**三种方式的位置处理完全一样**：每帧按**玩家朝向**算偏移挂上去（硬锁）。位置不能插值 —— 否则坐骑一转头，玩家就从它背上滑到侧面去了（§3.8 的教训）。分支写法：`朝向跟随 == 硬跟玩家` 时 `当前坐骑Yaw = 玩家Yaw;`（每帧直接赋值、不过 `MoveTowardsAngle`），否则走 §3.8 的 `MoveTowardsAngle`。实测（把玩家朝向从 0 阶跃到 120°，采样坐骑 yaw）：

```
灵翅      硬跟玩家          0 → 120（第一帧就到，完全无过渡）✓
碧水兽    分离 240度/秒     0 → 61.6(0.25s) → 120(0.5s) ✓（240×0.5 = 120）
上古神龙  平滑 45度/秒      0 → 11.6 → 23.2 → 34.9 → 46.7 → 58.3 → 70.0 → 81.7
                            ✓ 线性，实测 ≈46 度/秒；转 180° 约 4 秒
```

> **为什么不用字符串列表**：`朝向始终跟玩家的坐骑 = {...}` 这种写法等于"每只坐骑的行为散落在几个全局列表里"，和用户明确要的"每只各一份"是两种风格；而且列表一旦漏写 id 就是静默失效（没有 warning）。放进 `坐骑摆位` 后，摆位和朝向行为在同一行里，改一只不会碰到别的。

### 3.10 【改】下坐骑播的是「死」，不叫 LeveUp

用户：「**就不要叫消失动画叫做 levelup 了，就叫 dead 吧，改一下之前的错误**」。原来把下坐骑写成了 `PlayAction("LeveUp")` —— **概念错了**（LeveUp 是升级）。现在字段叫 `消失动作`，主名 `Die`，备用 `{ dead, Dead, LeveUp }`。

> **为什么主名是 `Die` 而不是 `dead`**：碧水兽控制器里那个状态的**字面名就是 `Die`**（实测 `动作列表 = Idle/FightRun/HuDong/IdleSpecial/IdleSpecial01/Birth/LeveUp/Die`），填 `dead` 会直接播不出来（NpcAnimator 会报「没有动作 dead」）。所以主名用 `Die`、把 `dead` 放进备用列表 —— 以后控制器改成 `dead` 也不用动代码。

### 4.1 ★ 怎么判断翅膀的"正确摆位"

用户在 3C_Testbed 里手工摆了一个 `Chibang_01` 当参考，但这个参考**是错的**：`偏移 X = 0.821`、`朝向 y = 92.4`，表现是"绑在了角色的右手"。正确的判据是**量几何**，不是看着调：

```
翅膀根骨骼 Bone19 / Chibang_Bone 世界 X = ∓0.061   → 几乎在正中，X 不该有偏移
yaw = 0 时网格世界尺寸 = (4.875, 4.871, 2.101)     → 翼展沿 X，说明 yaw=0 才是正的
翼根 Z = −0.381                                     → 翼根在身后 ✓
```

所以 `朝向=(0,0,0)`、`偏移.x=0`。**遇到"这东西绑歪了"，先把骨骼世界坐标和网格尺寸打出来**。

### 4.2 ★ 贴图坑：翅膀一片黑

`Chibang.mat` 原本是 `Legacy Shaders/Self-Illumin/Diffuse`（不读 alpha）→ 黑色矩形。换成 `Legacy Shaders/Transparent/Cutout/Diffuse` + `_Cutoff=0.5` + queue 2000→2450 后正常，说明贴图**是有 alpha 的**，只是旧 shader 不用它。

> 副作用：Legacy Shaders 里**没有** `Transparent/Cutout/Self-Illumin/Diffuse`，自发光那一层丢了。目前接受。

### 4.3 ★ 朝向：硬跟，不许插值（位置永远不插值）

用户原话：「应该是**紧密的卡死在角色的后方**的，而不是现在这样平滑的插值变化」。所以硬跟分支**每帧直接赋值、不过 `MoveTowardsAngle`**（代码见 §3.9）；**位置仍然用玩家的 rotation 算偏移**（曾经的 0.82m 横移就是栽在这）。

### 4.4 ★★★【大坑】项目里有**两个都叫 `Chibang`** 的 AnimatorController

| 路径 | 状态 |
|---|---|
| `Assets/Animations/NPC/Chibang.controller` | 动作是**对的**（红鲱鱼） |
| `Assets/Animations/NPC_Creature/Chibang.controller` | **预制体实际引用的是这个**，Idle 和 Run 两个状态的 `motion` **都是 `null`** |

症状极具误导性：`NpcAnimator.CurrentAction` 显示 `Idle` / `Run` 完全正常，但网格**一动不动**。**真因的判据只有一行**：`animator.GetCurrentAnimatorClipInfo(0).Length == 0`（状态有，clip 没有）。**教训**：同名控制器在项目里可以共存（这里还偏偏同名 `Chibang`），排查"动画不播"时**先确认预制体到底引的是哪个 `.controller`**，别按名字找。

### 4.5 ★【方法】断言"动画在播"不能看状态名

| 判据 | 可信度 | 说明 |
|---|---|---|
| `NpcAnimator.CurrentAction == "Idle"` | ✗ 无效 | 只说明 `SetInteger` 调到了，§4.4 就栽在这 |
| `Animator.GetCurrentAnimatorStateInfo(0).normalizedTime` | ✗ 不可靠 | 状态机在走，clip 可能是空的 |
| **`GetCurrentAnimatorClipInfo(0)` 的 Length / weight** | ✓ | 直接证明"这一层真挂着 clip" |
| **逐骨骼累积位移** | ✓✓ 最强 | 跑 N 帧把每根骨骼的位置变化累加，看几根真动了、最大位移多少 |

实测（翅膀）：`GetCurrentAnimatorClipInfo(0).Length = 1，Idle weight = 1`；`Idle` 20/20 根骨骼在动、最大位移 2.93m；`Run` 最大位移 3.43m。"20/20 根骨骼在动"这种量级才叫**证明**；`CurrentAction` 那种只是**猜测**。

### 4.6 【功能】翅膀的出生 / 消散：**从小变大**（不是淡入）

用户定稿要求：「试试从小变大的一个效果？最开始很小，然后把它体积慢慢变大到正常」，并且「出生时也要卡死在背后」。**无 Birth 的坐骑走保底**：`kk = Clamp01(过渡计时 / 出生保底时长)`（出生保底时长 = 1.2）→ `s = SmoothStep(0,1,kk)` → `localScale = Vector3.one * (实用缩放() * Lerp(出生保底起始缩放, 1f, s))`（出生保底起始缩放 = 0.05）。

**为什么不做位置补偿**：早先按**绑定姿势的 `localBounds`** 反推补偿，实测仍有 0.197m 水平漂移（蒙皮网格的 `localBounds` 和实际 `bounds` 不一致）。现在**干脆不补**：坐骑根就落在角色下背，让翅膀**从根往外长**，看起来天然就是"从背后长出来"，既不用和蒙皮包围盒较劲，也**没有任何补偿量可以算错**。

### 4.7 ★★【坑·已修】出生 / 下坐骑时翅膀"位置偏高"

用户报「下翅膀坐骑时，它会在更上面的位置，而没有卡死玩家的背部」「在上坐骑时生成好像也是在更上方的部分生成的」。是**两个独立的 bug**，症状都被描述成"位置不对"：

**① 出生时钉在了终点高度**：`更新上坐骑()` 把坐骑摆在一律 `起始高度 + 骑乘高度`（= 5.64 的终点高度），玩家还在从地面往上飘，翅膀已经在终点等着了。修法：无出生动画的坐骑跟着玩家的**当前**高度 —— `摆坐骑(无出生动画 ? transform.position.y : 起始高度 + 骑乘高度);`

**② 消散时吃错了缩放**：`更新下坐骑()` 用的是通用 `坐骑缩放`(3.8762) 而不是 `实用缩放()`（翅膀 = 1）：翅膀先被放大到 3.9 倍，又因为网格中心在根之上，看着就是"一边放大一边往上飞"（日志里能看到 `缩放 = 3.876`）。修法：必须走会吃 `个别坐骑摆位` 覆盖的 `实用缩放()` —— `缩放 = 实用缩放() * (1f - SmoothStep(0, 1, Clamp01((进度 - 0.4f) / 0.6f)));`

### 4.8 ★ 验证判据：**别断言绝对高度**，看"坐骑根相对玩家的偏移是否恒定"

绝对 Y 一直在变（玩家在升降，看不出对错）：

```
                 坐骑根Y   玩家Y    差       缩放
上坐骑 t=0.30s    0.88     1.88    -1.00    0.357     ← 差恒定
上坐骑 t=0.90s    4.61     5.62    -1.01    0.995
坐骑待机          4.65     5.66    -1.01    1.000
下坐骑 t=0.90s    2.42     3.43    -1.01    0.939
下坐骑 t=1.50s   -0.16     0.85    -1.01    0.210
```

## 5. 摆位与高度标定

### 5.1 ★ 判据换成**骨骼**：包围盒在这里不可信

按老办法量 `SkinnedMeshRenderer.bounds` / `localBounds` 得到一堆**自相矛盾**的数：玩家网格高 3.305（实际身位 1.8，比值 3.305 / 1.801 ≈ 1.835 才发现被 `Player_Visual` 的缩放二次乘了）；坐骑网格顶 4.666，但它的头骨在 5.78 —— **包围盒竟然比骨架还小，不可能**。蒙皮网格的 `bounds` 是**绑定姿势 + 大幅外扩**的估计值，`localBounds` 再叠上渲染器自己的缩放，两次量出来互相打架。**结论：量摆位一律用骨骼世界坐标**（`GetComponentsInChildren<Transform>()`，排除渲染器）。用骨骼量出来的真相（改前，玩家脚底 = 5.654）：

```
碧水兽 脚趾 1.74~1.83   ← 它本身就悬浮在离地 1.74
       骨盆 3.30  背脊 3.44   ← 这才是"背"
       脖子 4.15  头 5.78
玩家   脚底 5.654  ← 竟然在它**头顶之上**
       骨盆 6.539
```

玩家的座位离碧水兽的背 3.1、脚底比它头顶还高 —— 「高差太远」完全对上。（顺带解释了为什么 §3.4 那串 `-4.85` 是错的：它是**按网格中心**对的，网格中心被撑大的包围盒带偏了。）

### 5.3 ★★★【大坑】场景 YAML 里的中文字段名是 `\uXXXX` 转义的

为了确认"这些值到底存哪"，在 `.scene` 里 grep `骑乘高度` / `坐骑相对偏移` —— **一条都搜不到**，差点得出「没被序列化，改 `.cs` 默认值就行」的结论。**完全错了。** 场景文件里实际长这样：

```yaml
  "\u5750\u9A91\u76F8\u5BF9\u504F\u79FB": {x: 0.29, y: -4.85, z: 0.24}   # 坐骑相对偏移
  "\u5750\u9A91\u7F29\u653E": 3.8762                                      # 坐骑缩放
```

**Unity/Tuanjie 把非 ASCII 的字段名转义成 `\uXXXX` 写进 YAML**（`.cs` 里是原文，所以 `grep 骑乘高度 MountRider.cs` 有结果、grep 场景没有）。于是「用中文名 grep 场景」这个动作**永远搜不到**，是个会误导人的假阴性。**后果**：`MountRider` 挂在场景的 `Player` 上（`PrefabInstanceStatus = NotAPrefab`），所有摆位参数都是**场景实例自己序列化的值**；只改 `.cs` 里的默认值，运行时读到的还是场景里那份 —— **改了等于没改**。

**正确做法**是把值写进场景实例的序列化字段：`new SerializedObject(骑)` → `so.FindProperty("坐骑相对偏移")` → 设 `vector3Value` → `so.ApplyModifiedPropertiesWithoutUndo()` → `EditorUtility.SetDirty(骑)` → `EditorSceneManager.SaveScene(EditorSceneManager.GetActiveScene())`。**★ 不 SaveScene 就只活在内存里。**

> **通用教训**：改任何挂在**场景/预制体实例**上的公开字段前，先确认它序列化在哪。判断方法不是 grep，是 `SerializedObject.FindProperty(字段名)` 读出来的实际值。改完必须 `SaveScene`。想用 grep 找的话，得先查 `\uXXXX` 转义形式。

## 6. 给每只坐骑单独配：摆位表 / 动作表

### 6.1 【改】摆位从「全局 + 覆盖」改成「每只坐骑一条」

用户：「**不要把坐骑相对偏移值设成全局值，给每个坐骑都弄个相对偏移值**」。

| 改前 | 改后 |
|---|---|
| `坐骑相对偏移` / `坐骑朝向` / `坐骑缩放` 三个**全局**字段 | **删掉**（不再有全局值可退）|
| `个别坐骑摆位[]`（可选覆盖，留空就用全局）| **`坐骑摆位表[]`**（每只坐骑一条，必填）|
| `取摆位覆盖()` 可能返回 `null`，调用处到处三元判断 | `取摆位()` 一定返回一条；缺了 → **warning + 兜底** |
| `实用缩放()` = 覆盖.缩放 或 全局缩放 | `实用缩放()` = 这只坐骑自己那条的缩放 |

`取摆位()` 的兜底是**故意设成错的**（偏移 0 / 缩放 1，坐骑会糊在玩家身上），这样漏配会立刻被看见，而不是悄悄用某个"看起来还行"的全局值。warning 用 `已报缺失的坐骑id` 去重，因为 `摆坐骑()` 每帧都会调它。

**为什么原来那套非改不可** —— 各模型原始尺寸差 2.5 倍（实测骨骼包围盒，缩放 1 时；后者是原全局缩放 3.8762 下的世界高）：灵翅 3.105 → 3.11（它有覆盖、缩放 1）、碧水兽 1.294 → 5.02、狼骑 1.322 → 5.12、战骑 1.030 → 3.99、上古神龙 0.992 → 3.85、熊猫 1.760 → 6.82、麒麟 2.243 → 8.70、灵鹿 2.438 → 9.45、巨龙 2.513 → 9.74（且它的根在**头顶**，骨骼全在根下方 −1.86～0.66）。一个全局缩放只能对一只合适（`3.8762` 是当年从碧水兽量出来的），全局偏移同理。

**落地方式**：用 `SerializedObject` 写 `坐骑摆位表`（9 条，id 从 `坐骑表.csv` 第一列读，保证不漏），再 `SaveScene`。实测 9 只逐只召唤，**全部命中自己那条**（偏移/缩放与表里完全一致），无兜底 warning。目前 7 只（除灵翅、碧水兽外）先按**原全局的等效值**填入 —— 行为零变化，但它们**还没做过目视校准**。

### 6.2 【功能】一个动作兼四个阶段：只改速度（`坐骑动作表[]`）

用户对上古神龙的说明：

> 「上古神龙只有一个动画，就是环绕飞行，它同时是 idle、birth、run、levelup 这四个动画，只是 birth 和 level 是 1.7 倍速，idle 是 0.5 倍速，run 是 1 倍速，通过播放速度的不同来表示 4 个阶段，**最好不要拆开，只改变速度就可以了**」

实测确认：`ShenLong_01.prefab` 上 `NpcAnimator.动作列表 = [CINEMA_4D___]` —— **真的只有一个动作**。字段（每只坐骑一条）：`坐骑id`（和 `坐骑表.csv` 第一列一致）、`待机动作` / `待机速度`、`跑动动作` / `跑动速度`、`出生动作` / `出生速度`（**留空 = 这只没有出生动画** → 走「粒子 + 从小变大」保底）、`消失动作` / `消失速度`（下坐骑播的那个）。上古神龙那条：四个名字**全是 `CINEMA_4D___`**，速度分别是 0.5 / 1.0 / 1.7 / 1.7。

★★ **速度必须每帧重设，不能只在换动作时设一次** —— 上古神龙的待机和跑动是**同一个动作**，换阶段时动作名没变，"名字变了才重播"的判断会漏掉，速度就永远停在 idle 的 0.5 倍 ✗

**过渡时长改成「片段长 / 速度」**：`上坐骑总时长 = max(玩家升空时长, 出生片段长 / 出生速度)`；`下坐骑总时长 = max(玩家落地时长, 消失片段长 / 消失速度)`。量不到就退回配置值 —— `NpcAnimator.取动作长度()` 是**按 clip 名**查的，控制器里"片段名"和"状态名"不一定一致（碧水兽的状态叫 `Die`，但没有叫 `Die` 的片段）。实测：

```
碧水兽   出生 speed=1.00 动作=Birth        时长=2.67s（= 片段 2.67 / 1）
         待机 speed=1.00 动作=Idle         clip 数=1
         消失 speed=1.00 动作=Die         时长=2.03s（退回配置值）
上古神龙 出生 speed=1.70 动作=CINEMA_4D___ 时长=5.10s（= 片段 8.67 / 1.7）
         待机 speed=0.50 动作=CINEMA_4D___ clip 数=1 ✓（单片段真的在播）
         消失 speed=1.70 动作=CINEMA_4D___ 时长=5.10s
```

> 顺带：碧水兽的跑动状态在控制器里的字面名仍然是 `FightRun`（当年说"改成 Run"其实没改控制器），现在直接在它那条配置里写明 `FightRun`，不再依赖备用名兜底。

### 6.3 【修】巨龙的模型轴向不对 → 摆位里加 +90° X 旋转

用户：「巨龙这个坐骑，**预制体本身可能有点问题，需要先沿 x 轴旋转 90 度**处理一下」。实测确认（缩放 1、无旋转，量**骨骼**包围盒）：

```
(0,0,0)    尺寸 X=2.195 Y=2.513 Z=1.164   最低Y=−1.858  最高Y=+0.655
           最低 4 根全是 Finger/Tail、最高 4 根是 Finger/Head
           → 整个模型挂在根**下方** 1.86
(90,0,0)   尺寸 X=2.195 Y=1.164 Z=2.513   最低Y=−0.001  最高Y=+1.163   ← 脚正好落在根上 ✓
(−90,0,0)  尺寸同上（镜像），但**脚朝天**（最低 4 根变成 NAME/Finger）✗
```

**符号是 +90，不是 −90。** 判据有两条，以后遇到"模型躺倒/悬空"照这个来：① **最低的那几根骨骼必须是脚**（脚趾/脚掌），不能是手/角/尾；② **bbox 最低点要落在根附近** —— `(0,0,0)` 时整个模型吊在根下面，所以看着才不对。

改法：`坐骑摆位表` 里巨龙那条 `朝向 = (90, 0, 0)`。`摆坐骑()` 里的旋转是 `Quaternion.Euler(0, 坐骑Yaw, 0) * Quaternion.Euler(朝向)`，所以是**先跟玩家转 yaw、再绕自身 X 轴转 90** —— 正是要的顺序。**不用改预制体、不用改代码**，`朝向` 这个字段本来就是给这种"模型轴向不对"留的。实测（骑乘中，缩放 3.8762）：`坐骑根 euler = (90, 0, 0)` ✓；骨骼最低点 − 坐骑根 = **−0.022**（修前 ≈ −7.20：模型吊在根下面）、最高点 − 坐骑根 = +4.49；世界尺寸 X=8.58 Y=4.51 Z=9.39。

> 它的 `偏移` 还是继承来的 `(0.29, −3.95, 0.24)`（原本是碧水兽的值），世界尺寸到这个量级后肯定要单独调 —— 按用户"之后逐个再调"的意思留着。

### 6.4 【功能】在地面跑的坐骑（狼/鹿/熊猫）：每只自己的骑乘高度 + 贴地跟随

用户：「狼骑，鹿坐骑，熊猫坐骑最好都是**在地上跑**的，**控制体系到你觉得合适**，角色只是**漂浮在稍微上方一点点**上方，**不能像之前的其他坐骑一样飞的很高**」。

**为什么必须连**缩放**一起改（不然"低"不下来）**：这三只原来都在吃碧水兽的全局缩放 `3.8762`，而各模型原始尺寸差很多 —— 狼骑在这个缩放下是 **14 米长、背高 4.5 米**，玩家坐上去只能在 4.5 米以上。所以按实测的**背高（Spine 骨骼）**反推缩放：

| 坐骑 | 背(Spine)@缩放1 | 目标背高 | 缩放 | 骑乘高度 | 实测背高 |
|---|---|---|---|---|---|
| 狼骑 | 1.164 | 1.00 | **0.86** | **1.15** | 0.97 |
| 灵鹿 | 1.116 | 1.25 | **1.12** | **1.40** | 1.37 |
| 熊猫 | 0.647 | 0.80 | **1.24** | **0.95** | 0.71 |

**`骑乘高度` 也变成每只坐骑自己一条**：原来 `骑乘高度 = 5.64` 是全局字段（按碧水兽定的 —— 用户早先说过"装备坐骑后的高度均以碧水兽为准"）。现在挪进 `坐骑摆位`：悬浮的（碧水兽 / 翅膀 / 神龙）保持 5.64，地面坐骑 0.95~1.40。**`偏移.y` 直接写成 `-骑乘高度`** —— 三只模型的脚都正好落在根上（实测 bbox 最低 −0.016~0.008），于是 `坐骑根 = 玩家根 − 骑乘高度 = 地面高度` → **脚正好踩在地上**，一个补偿量都不用算。

**`贴地` 开关：每帧向下打射线取脚下地面**：`角色目标高度 = 基准地面高度 + 骑乘高度`，其中 `基准地面高度 = 贴地 ? 当前地面高度() : 起始高度`。射线起点放在**脚底稍上方 0.15m**：胶囊是凸体，**起点落在它内部时不会被自己挡住** —— 这是不用 layer mask 就能排除自己的关键；探不到（悬空 / 找不到地面）就退回上坐骑那一刻的地面高度。实测（临时造一个 3 米高台，测完销毁、残留 0）：

```
平地上    狼骑：玩家脚底 1.137  坐骑根 −0.013  背 0.958   → 脚在地上、玩家在背上方 0.18
3 米台上  玩家脚底 4.137（= 3 + 1.15）  坐骑根 2.987（踩在台面，没陷进去）
挪回平地  玩家脚底 1.165  坐骑根 0.015
```

> **悬浮坐骑不受影响**：它们的 `基准地面高度` 就是上坐骑那一刻的高度，行为与之前完全一致。顺带：`起始高度` 从此有两个层次 —— `起始高度` 是"上坐骑那一刻的地面"，`基准地面高度` 是"这只坐骑该拿谁当地面"，改高度相关的代码时别混。
>
> ⚠️ `贴地` 这个字段**后来整条废弃了**（代码不再读），见 §7.4。

### 6.5 遗留：战骑 / 麒麟 / 巨龙 还没归类

用户只点名了狼骑 / 灵鹿 / 熊猫。其余三只现在仍是"悬浮类"（骑乘高度 5.64、不贴地）：**战骑**是马，按同样逻辑**应该也在地上跑**，但它的模型很怪 —— 缩放 1 时 宽 X=5.923 / 长 Z=4.119 / **高 Y 只有 0.840**，背骨(Spine) 仅 0.365，宽 > 长、扁得反常，**疑似和巨龙一样有轴向问题**，要单独查；**麒麟坐骑 / 巨龙**待定（麒麟是在云上走的瑞兽，巨龙会飞，悬浮也说得通）。

## 8. 灵鹤（`mount_zhanqi_01`）：套碧水兽 + 两个坑

用户：「**灵鹤（也就是 zhanqi）可以完全套碧水兽**（除了没那么大，然后没那么多动画）」。

先纠正一个认知：它"没那么多动画"其实是**一个动画都没有** ——

- 控制器 `Assets/Animations/NPC/ZhanQi.controller` 的 Idle / Run 两个状态 **motion 都是 null**（片段数 0）
- 模型 FBX（`ZhanQi_01.FBX`）的导入设置 **`importAnimation = False`**；打开试了一次 `defaultClipAnimations = 0` → **FBX 里根本没有动画数据**（试完已还原开关）
- 后果：Animator 每帧把骨骼重置成**绑定姿势**（"站立"的窄高鹤：本地头 +2.0 / 尾 −2.15，高 4.14），而美术在预制体里存的是**展翅滑翔**的姿势（翼展 5.923、机身厚 0.84、长 4.119）——**等于白存了**

### 8.1 坑①：humanoid 骨架会**直接忽略**原始 Transform 曲线

把预制体里那个滑翔姿势采样成一个静态片段（400 条曲线、40 根骨骼）挂进 Idle/Run 后，运行时 `clip 数 = 1`（确实在播）**但姿势一点没变**。

**原因**：`animationType = Human`。Mecanim 对 humanoid 只读**肌肉曲线**，路径式的 `localPosition / localRotation` 曲线**会被忽略**（不是路径写错，是根本不看）。

**修法**：把预制体上 `Animator.avatar` **置空** → Mecanim 按 **Generic** 处理，原始曲线立刻生效。没动 FBX 导入设置，只改了灵鹤自己的预制体 —— 反正它没有任何动画，humanoid 重定向对它毫无用处。实测：翼展 **4.50** / 高 **0.78** / 长 **3.13**（= 5.923 / 1.030 / 4.119 × 缩放 0.76）✓ 正是那个滑翔姿势

> **通用手法：把美术摆好的姿势固化成动画片段** —— 逐根 `Transform` 算 `AnimationUtility.CalculateTransformPath(t, 根.transform)` 当路径，对 `localPosition.x/y/z`、`localRotation.x/y/z/w`、`localScale.x/y/z` 各写一条 2 帧常量曲线，用 `AnimationUtility.SetEditorCurve(clip, EditorCurveBinding.FloatCurve(path, typeof(Transform), prop), 常量曲线)`；片段存成 `.anim` 资产、挂进状态即可。**注意 humanoid 骨架要先按坑①处理。**

### 8.2 坑②：碧水兽的 `Die` 状态是**空的**

按用户要求把下坐骑从 `LeveUp` 改成 `Die` 后，`取动作长度("Die")` 一直是 0。查控制器发现 **8 个状态里有 2 个 motion 是空的**：`Die` 和 `IdleSpecial01`。也就是说只"改名字"的话，下坐骑会变成**姿势冻住**（状态切过去了、但没有片段在播）。

**修**：把 `LeveUp` 的片段（2.033s —— 就是原来实际播的那个消失动画）**填进 `Die` 状态**。名字（dead/Die）和动画就都对了，外观与以前完全一致。

> **教训**：改动作名之前，先确认那个状态的 **motion 不是空的**。`NpcAnimator.AvailableActions` 只说明"状态存在"，不说明"有片段"—— 和 §4.4 的翅膀是同一类"名字对了但没内容"的坑。

### 8.3 摆位：真的"完全套碧水兽"，只有缩放不同

| | 碧水兽 | 灵鹤 |
|---|---|---|
| 骑乘高度 | 5.64 | **5.64**（一样高）|
| 贴地 | 否 | 否 |
| 朝向跟随 | 分离 | 分离 |
| 缩放 | 3.8762（骨高 5.02m）| **0.76**（翼展 4.5m、长 3.13m —— 明显更小）|
| 偏移 | (0.29, −3.95, 0.24) | **(0, −0.93, 0)** |

偏移**不能照抄**：滑翔姿势下机身局部 Y 是 `0.000 ~ 1.030`（根就在机身下沿），所以 `偏移.y = −(1.030 × 0.76 + 0.15) = −0.93` → 实测玩家脚底落在鹤背上方 **0.148** ✓。照抄 −3.95 的话，鹤会跑到玩家脚下 3 米以外。

### 8.4 改名：**CSV 不是运行时直接读的**

用户反馈「坐骑的 ui 界面还是叫做战骑，没有改名叫作灵鹤」。链路是：`坐骑表.csv` --DataTableImporter（菜单「修仙/从配置表生成资产」）--> `Assets/Data/Generated/MountDefinition/*.asset`（ScriptableObject）--> 运行时面板读这个。

所以**只改 CSV，面板不会变**（实测改完 CSV 后资产里还是「战骑」）。要跑一次 `DataTableImporter.ImportAll()`（会报「坐骑表: 更新 9」）。`DataTableImporter.找出未同步的表()` 按时间戳判断，可用来确认是否同步。

> ★ 但跑 ImportAll 会**往场景里实体化约 86 个角色面板属性行**（`Row_气血` / `Row_攻击` / …）再加 168 个 UI 元素的布局数值刷新 —— 一次性 6000+ 行的场景 diff，**跟代码无关**。**能只改生成资产就别跑全量导入。**

### 8.5 idle/run：它一个动画都没有，所以用代码现做

用户反馈「没有 idle 和 run 的动画」。在美术那个**展翅滑翔**姿势的基础上程序化生成两段循环动画：

| 片段 | 周期 | 翅膀各段幅度（Clavicle/UpperArm/Forearm/Hand/Finger0）| 机体起伏 | 脖子摆动 |
|---|---|---|---|---|
| `ZhanQi@Idle` | 2.40s | 4 / 8 / 6 / 4 / 3 度 | 0.02 | 2 度 |
| `ZhanQi@Run` | 0.90s | 9 / 20 / 14 / 9 / 6 度 | 0.06 | 5 度 |

做法（**可复用的"程序化动画"手法**）：① 实例化预制体拿到基准姿势，记下每根骨的基准 local TRS + 世界位置；② 逐帧：所有骨恢复基准 → 对翅膀链 `骨.Rotate(Vector3.forward, 幅度 × sin(2πt/T) × 左右符号, Space.World)`（绕**机身前后轴**扇动；左右反相 → 两侧对称）→ 骨盆世界位置 `+= up × 起伏 × sin` → 脖子绕世界 X 摆；③ **读回**每根骨的 local TRS 写进曲线 —— 用"先设变换、再读回"的办法，省掉自己推四元数/局部旋转轴（这是整段最省事的地方）；④ `AnimationUtility.SetEditorCurve` 建曲线。

★★ **必须同时设 `AnimationClipSettings.loopTime = true`** —— **Mecanim 认的是它，不认 `clip.wrapMode`**。只设 wrapMode 的症状很迷惑：状态时间照常推进（归一化时间一直涨）、**但姿势播一遍就定住不动** ✗（实测 `clipSettings.loopTime = False`；改成 true 后翼尖才开始连续往复）

实测：`ZhanQi@Idle` 翼尖 Y 在 **4.80 ~ 6.12** 之间往复、周期约 2.4s ✓；`ZhanQi@Run` 翼尖 Y 在 **3.95 ~ 6.77** 之间往复、周期约 0.9s ✓（幅度明显更大更快）。

> 遗留：`坐骑表.csv` 里这一行的**介绍文案**还是「战阵之骑。披甲衔枚，与主人同进退。」—— 那是"战骑"的文风，配灵鹤不合适，但改文案是策划的事，等用户定。

## 9. 麒麟坐骑摆位标定 + 【通用公式】偏移y = −(鞍座局部高度 × 缩放)

### 9.1 问题：摆位是照抄碧水兽的，但两个模型不一样大

麒麟（`mount_qilingzuoqi_01`）的摆位原本**逐字照抄碧水兽**：缩放 `3.8762`、偏移 `(0.29, -3.95, 0.24)`、骑乘高度 `5.64`。但两只的局部包围盒差很多：碧水兽 `2.06 × 2.15 × 2.02`、**麒麟 `1.28 × 3.24 × 4.86`**（又高又长）。

后果（用正交侧视渲图看出来，见 §9.7）：**麒麟整只 16.2m 高（碧水兽 9.5m）**，而且玩家不在背上 —— 卡在它**肚子/腿**那个高度，看起来像"人吊在麒麟身上"。用户：「大小要微调，飞起来后高度和碧水兽差不多，和玩家的相对距离和鹿差不多」。

### 9.2 ★ 通用公式：`偏移.y = −(鞍座局部高度 × 缩放)`

**和 `骑乘高度` 无关**（玩家的脚要踩在鞍座上，坐骑根就得按鞍座高度往下挪）：

```
坐骑根 Y = 玩家 Y + 偏移.y
鞍座世界 Y = 坐骑根 Y + 鞍座局部高度 × 缩放
要让 鞍座世界 Y = 玩家 Y   →   偏移.y = −(鞍座局部高度 × 缩放)
```

**用现成的两只反验，精确吻合**：

| 坐骑 | 鞍座局部 | 缩放 | 公式算出的 偏移.y | 场景里的实际值 |
|---|---|---|---|---|
| 灵鹿 | 1.25 | 1.12 | **−1.40** | `-1.40` ✓ |
| 碧水兽 | 1.019 | 3.876 | **−3.95** | `-3.95` ✓ |

**鞍座局部高度怎么取**：模型的**胯骨 `Bip01` 的局部 Y + 0.15~0.2**。麒麟 `Bip01` 在局部 `y=1.159` → 鞍座 ≈ **1.33**；渲图量"鞍座在世界里的高度"再反推，同样是 **1.33** ✓（两条路互验）

### 9.3 尺寸的上限：缩放太大，坐骑会陷进地里

坐正之后 `脚底离地 = 骑乘高度 − (鞍座 + 抬腿) × 缩放` —— **缩放越大脚越贴地**：

| 缩放 | 整只高 | 脚底离地 | 玩家坐背上？ |
|---|---|---|---|
| 3.876（原值）| 16.2 | **−2.31（陷地里）** | 要坐正就得陷地 ✗ |
| 2.60 | 10.9 | 0.31 | ✓ |
| **2.30（第一轮试过的值）** | **9.62** | **0.90** | ✓ |

> 所以"玩家坐在背上"+"脚不陷进地里"两条一起要，**麒麟的缩放上限约 2.6**。骑乘高度 5.64 是用户要的"和碧水兽差不多"，别再动它。

### 9.4 定稿：按「比狼和鹿大一些」= 缩放 **1.30**

第一轮的 2.30 被用户否掉：「麒麟不用这么大，可以再小一点，**比狼和鹿大一些**就可以了」。所以先把"狼 / 鹿"量出来当尺子：

| 坐骑 | 缩放 | 骑乘高度 | **整只高（实测）** | 脚底离地 |
|---|---|---|---|---|
| 狼骑 `mount_langqi_01` | 0.86 | 1.15 | **2.36** | −0.51（贴地跑）|
| 灵鹿 `mount_luzuoqi_01` | 1.12 | 1.40 | **3.32** | −0.15（贴地跑）|
| **麒麟 `mount_qilingzuoqi_01`** | **1.30** | 5.64 | **5.43** | 2.96 |

→ 麒麟 = 鹿的 **1.63 倍**、狼的 **2.3 倍**，正是"比狼和鹿大一些" ✓

**定稿值（三个游玩场景同步）**：

| 字段 | 原值 | 定稿 |
|---|---|---|
| 缩放 | `3.8762`（照抄碧水兽）| **`1.30`** |
| 偏移 | `(0.29, -3.95, 0.24)` | **`(0, -1.73, 0)`**（= −1.33 × 1.30，§9.2 的公式）|
| 骑乘高度 | `5.64` | 不变（用户要的"和碧水兽差不多"）|
| 朝向 / 朝向跟随 | `(0,0,0)` / 分离 | 不变 |

（横向偏移从 `(0.29,…,0.24)` 改为 `(0,…,0)` —— 正对玩家、横向和鹿一样居中；中间轮次 2.30 的边界结论见 §9.3。）

### 9.5 ★ 小坐骑 + 高骑乘高度 = 它必然浮得高（留给以后的取舍）

玩家离地高度锁在 `骑乘高度 = 5.64`，坐骑又必须让人坐在背上，于是 **坐骑越小、脚底离地越高**（`脚底 = 骑乘高度 − 2.056 × 缩放`，2.056 = 鞍座 1.33 + 抬腿 0.726）：

| 方案 | 缩放 | 骑乘高度 | 玩家离地 | 脚底离地 | 观感 |
|---|---|---|---|---|---|
| **A（定稿）** | 1.30 | **5.64** | 5.63 | **2.96** | 玩家高度和碧水兽一模一样；麒麟整只悬空 3m |
| B（备选）| 1.30 | **3.20** | 3.19 | **0.52** | 麒麟贴着地面飞（像碧水兽那样只离地 0.5m）；玩家坐得更低 |

> **当前场景里写的是 A** —— 因为"高度和碧水兽差不多"是用户明确要求过的一条，A 的玩家离地 5.63 和碧水兽 5.63 完全一致。若嫌"浮太高"，把 `骑乘高度` 改成 **3.20** 就是 B —— **只改这一个数**，偏移不用动（§9.2 的公式和骑乘高度无关）。

### 9.6 ★【坑】量坐骑大小 / 坐位时的三个坑

1. **`SkinnedMeshRenderer.bounds` 不准**：它用的是**美术手填的 `localBounds`**，和真实姿势对不上 —— 碧水兽报 9.51m，画面上只有 4~5m。**判断大小 / 坐位只能靠渲图看**，别信这个数（当"相对比较"用还行）。
2. **`SkinnedMeshRenderer.BakeMesh(mesh)` 的顶点空间和 `localToWorldMatrix` 对不上**：自己乘一遍得到的包围盒比 `Renderer.bounds` 还高一截（实测 48m vs 15m），想用它"量背高"会得到一个比模型还高的荒唐值 ✗。
3. **运行时改 `坐骑摆位.缩放` 不生效**：`摆坐骑()` 里那句 `if (缩放.x <= 0.0001f) 实例.localScale = 缩放` **只在缩放到 0 时才写**，真正的缩放是 `尝试上坐骑()` 那一刻设的。调试时改参数必须**同时**改 `坐骑实例.transform.localScale`。

### 9.7 渲图验收的土办法（口袋场地 + 正交侧视相机 + `RenderTexture`）

① `GameObject.CreatePrimitive(Plane)` 在 `y=−4000` 铺一块临时地板（当"地面基准线"，也是地面探测的靶子）；② 玩家瞬移到那里、`rotation = identity`（坐骑正面朝 +Z，相机放在 +X 就是**纯侧视**）；③ 正交相机 `orthographicSize ≈ 7`、`backgroundColor` 纯色、`cam.Render()` → `RenderTexture`；④ `Texture2D.ReadPixels` 抓下来，多只拼成一张大图写进 `screenshots/`；⑤ 图里**必须带上参照物**（碧水兽 / 灵鹿），否则"大不大"没有判据。

产出图：`screenshots/qilin_after.png`（碧水兽 | 麒麟坐正 | 麒麟定稿）、`screenshots/qilin_applied.png`（场景数据验收：碧水兽 | 麒麟）、`screenshots/qilin_small.png`（候选 1.30 / 1.60 与狼鹿同框）、`screenshots/qilin_small_applied.png`（狼 | 鹿 | 麒麟A | 麒麟B）。

### 10.1 一个现象，四个独立原因（少修一个都还是坏的）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| ① | **横向拉宽 ≈3.6 倍** | `RenderTexture` 写死 `512×512`，而预览图矩形是 **1190×331**（比 3.595）→ 方形图被拉满宽扁矩形 | RT 的宽高比**必须等于预览图矩形**；长边取 `max(贴图边长, 矩形长边)`，并在 `Update` 里**复核**（首帧布局前 rect 可能是 0/旧值） |
| ② | 6/9 只**骨架一根不动** | prefab 上挂着**旧版 `Animation` 组件**（灵翅/狼骑/灵鹿/熊猫/麒麟/灵鹤）→ Unity 里 Animator 与 Animation 互斥，Mecanim **不绑 clip**（状态机照常推进！） | `Instantiate` 后把所有 `Animation` **销毁**（不是 `enabled=false`）—— 同 `MountRider` 的处理 |
| ③ | **全部 9 只**姿势冻住 | 面板打开时 `CharacterPanelUI.pauseGameWhenOpen` 把 **`Time.timeScale = 0`**，而 Animator 默认 `updateMode = Normal`（吃缩放时间）→ deltaTime=0 | 预览实例的 Animator 全设 **`AnimatorUpdateMode.UnscaledTime`** |
| ④ | 待机动作**根本没播上** | `NpcAnimator.PlayAction` 要等它**自己的 `Start`** 才「已就绪」，而 `Instantiate` 当帧 Start 还没跑 → 返回 false（**和 §3.6③ 出生动画卡住是同一个坑**） | 记下 `待播动作`，在 `Update` 里**每帧重试**（上限 120 帧，免得刷警告） |

> **②③ 叠在一起才是"完全不动"**：②让 6 只**连动都动不了**，③让**剩下 3 只也冻住**（那 3 只没有旧版 Animation，本来状态机是好的）。所以只修一个都会看到"还是没动画"。

### 10.3 【测试方法·两条都用得上】

**① 量"画面有没有被拉伸"：绝对不能用世界轴！** 要把偏移量取在**相机自己的**轴上：

```csharp
var p0 = cam.WorldToScreenPoint(心);
var px = cam.WorldToScreenPoint(心 + cam.transform.right * 0.5f);   // ★ 相机自己的右/上
var py = cam.WorldToScreenPoint(心 + cam.transform.up    * 0.5f);
// 两个方向的像素长度相等 = 等比例（不拉伸）
```

第一次写成 `Vector3.right / Vector3.up`（世界轴），量出 **0.9587 → 假阳性"还在拉伸"**。原因：相机有 yaw/pitch，世界轴偏移会带**朝向分量** → 深度变了 → `WorldToScreenPoint` 是透视除法，投影非线性；而且 pitch 8° 时世界 Y 也不是相机的上。**换相机轴后立刻是 1.0000。**

**② 量"到底动没动"：别只看 `normalizedTime`。** `GetCurrentAnimatorStateInfo(0).normalizedTime` 在**旧版 Animation 抢绑**时照样推进（②那种情况就是"状态机在走、骨架一根不动"）。可靠做法是**姿势签名**：把所有 `Transform` 的 `localPosition + localRotation` 拼成一个数组，隔 30 帧取第二次，比**最大逐项差**和**有几个骨骼变了**。这次就是它把 ②③ 直接证成了"动的骨骼=19/29"这种硬数字。

## 12. NPC 的御风（师父）：为什么必须**按骨架子重烘**

**现象**：师父御风时**躺着过来**（用户 2026-10-03 报的）。实测「头→髋」与世界上方夹角 **117.6°**（头比髋还低），而站姿是 5°。

**根因**（三段缺一段就会修错方向）：

| # | 事实 |
|---|---|
| ① | `御风_升空/Idle/前进/落地` 是 §7.3 那个 `YufengClipBuilder` 生成的 **Humanoid 肌肉曲线**（`path=""` + 肌肉名）⇒ **只有带 Avatar 的 Animator 播得动**（玩家就是这么播的） |
| ② | NPC 的 Tripo FBX 全是 **Generic**（`Animator.avatar = null`），控制器里另外 9 个动作也是 Generic ⇒ **不能给 NPC 直接挂人形 Avatar**（那 9 个会全废） |
| ③ | 于是 NPC 吃的是当年**烘到大师兄骨架上**的 `大师兄_御风_*`：`path="Armature/BoneRoot/..."` 的**绝对局部旋转**。**绝对旋转绑死骨架的静止朝向** —— 实测师父与大师兄同名骨骼**静止局部旋转 31 根差 >20°、最大 165°**（`R_Thumb1`）⇒ 同一段旋转套上去就翻 |

**做法**：`Assets/Editor/Builders/师傅御风重定向.cs`，菜单 **`修仙 / NPC 资产 / 师傅御风重定向（一键）`**（另有"只检查"）：

1. 师父 FBX → **Humanoid + 自建 Avatar**（`太虚宗掌门（师傅）Avatar`，`isHuman/isValid`，51 人骨）。⚠️ **只能用他自己的** —— 借别人的 Avatar 同样会翻；
2. `HumanPoseHandler.SetHumanPose` **逐帧**把四个**人形片段**重定向到师父骨架上，读回每根骨骼的局部 TRS，写成师父自己的 **Generic 片段**（`太虚宗掌门_御风_*.anim`，只给"被动作动过"的骨骼写曲线，与 `大师兄_御风_*` 同风格，各 ~345 条曲线）；
3. `AnimatorOverrideController`（基 = `大师兄.controller`）**只覆盖这四个状态**（`Yufeng_TakeOff/Idle/Forward/Land`），挂到师父 prefab 上；**`Animator.avatar` 保持 null** ⇒ 其余 9 个动作照旧。

**实测**（Play，`village`）：`Yufeng_TakeOff / Forward / Idle` 分别播 `太虚宗掌门_御风_升空/前进/Idle`，
头→髋夹角 **3.5° / 10.3° / 7.2°**（修前 117.6°）；`Idle` 状态仍播原来的 `idle`，夹角 **3.9°**、与大师兄**完全一致**（证明那 9 个 Generic 动作没被弄坏）。
截图 `cultivation/screenshots/师傅御风_修后.png`（左师父 / 右大师兄，同在 `Yufeng_Forward`）。

**通用规矩**：**绝对姿势不是可移植数据** —— 换骨架就得按新骨架重烘，或者走 Avatar 肌肉空间；
给某个角色换动作请用 `AnimatorOverrideController` 只覆盖那几个状态，**别改共享控制器**（一堆 NPC 全靠它）。见 [踩坑总库 B92](../ai/踩坑总库.md)。
