## 1. 核心思路

> **策划表里一行 = 剧情的一个阶段。** 引擎不认剧情，只认「条件满足 → 执行动作 → 进下一行」。
> 对话、NPC、镜头、场景、黑幕全都是同一张任务表的**动作列**。

所以改剧情 = 改 `任务表.csv`，不用碰代码。

---

## 2. 三层结构

```
Assets/Data/Tables/任务表.csv              ← 唯一真相源，一行一个阶段
  │ 菜单：修仙/从配置表生成资产
  ▼
Assets/Data/Generated/QuestDefinition/<id>.asset     （编辑器产物，不要手改）
  │ 菜单内部自动跟着跑：收集
  ▼
Assets/resources/任务/任务库.asset          ← 运行时才读得到
  ▼
代码：QuestDatabase.取()（静态缓存）
```

「收集」这一步是因为生成资产不在 Resources 里、运行时取不到，所以要摊平成库资产放进 Resources；
`修仙/从配置表生成资产` 结束时自动收集一次。

## 3. 任务模型：阶段链

一行任务表 = 一个 `QuestDefinition`。同一个 `任务id` 的多个阶段按 `阶段` **升序串成链**。
运行时只记 `当前阶段[任务id] = 阶段号`；导出进度是一行字符串 `q_main_004:7;q_main_002:0`（`:0` = 整条已完成）。

```csharp
var 下一 = db.取阶段(任务id, 阶段.阶段 + 1);
if (下一 != null) 进入阶段(任务id, 下一);      // 内部会 执行动作 + 加接取标记
else { 当前阶段.Remove(任务id); 已完成任务.Add(任务id); }   // 整条完成
```

`Update()` 每 `检查间隔`（默认 0.25 秒）轮一次条件。

## 4. 完成条件（`任务条件`）

| 条件 | 判定 |
|---|---|
| `无` | 成为当前阶段的**下一帧**就完成 → **一个阶段只能挂一个动作** |
| `等待秒数` | `Time.time - 阶段开始时间 >= 等待秒` |
| `到达` | 玩家与 `坐标` 水平距离 ≤ `到达半径` |
| `对话` | **玩家按下某一段的「回答 / 继续」时**才完成（填法与自查见 [对话系统](对话系统.md)，那里是唯一权威） |
| `提交物品` | 背包有 `物品id × 数量`（完成时真扣掉） |
| `击杀` | 目标 `目标npcId` 死亡（留空 = 任意 NPC 死一个） |
| `NPC到位` | 目标 NPC 走到（最近一次「飞到」记下的）落点 1.5 m 内 |
| `落点结束` | 玩家落点流程结束（「移动玩家」/「移动玩家且黑幕」把主角放到位） |

## 5. 动作（`任务动作`）

### 5.1 过场演出类（不需要目标 NPC）

| 动作 | 说明 |
|---|---|
| 黑幕字幕 | 台词列按 `\|` 拆行，逐字打出；等待秒 = 打完后再停留多久 |
| 闪白 | 白屏闪一下 |
| 播放对话 | 强制弹框（不用玩家按 F） |
| 镜头看目标 / 镜头回玩家 | 镜头调度 |
| 移动玩家 | 把玩家挪到「坐标」（落点，见 §8.4） |
| 移动玩家且黑幕 | 同上，但**同帧先落黑幕**当遮罩（四幕切到宗门用） |
| 切换场景 | `LoadSceneAsync` 单场景加载 |
| 生成NPC | 按「动作参数」的预制体路径生成到「坐标」 |
| 确保NPC | 不在场就按「动作参数」重建 |
| 接取任务 | 动作参数 = 要接取的任务id |

### 5.2 NPC 调度类（先按 `目标npcId` 找 `NpcInstance.定义.id`）

播动画 / 攻击玩家 / 销毁 / 走向 / 飞到 / 处决。

> ⚠️ **「找到目标 NPC」失败会静默跳过**（只打一条 Warning），但**阶段照样推进** →
> 表现常常是"对话弹了但人不在"，去 Console 搜 `动作的目标 NPC 不在场景里`。
>
> `生成NPC` 会登记「这个 NPC 是用哪个预制体造的」，`找NPC` 找不到时就**就地重建**（重建点 = 玩家附近）
> —— 登记的 id **优先取 `动作目标npcId`，没填拿实例的 `NpcInstance.定义.id` 兜底**；
> 只有 `动作参数`（预制体路径）时也记得住。详见 §9.4。

### 5.3 其它

`无`。

### 5.4 观感参数全部表驱动（改表即可，不用动代码）

**硬规矩**：演出的可调数字**不许硬编码在 C# 里**，必须能从任务表改。用到的列：

| 想调什么 | 列 | 说明 |
|---|---|---|
| 黑幕台词 | `台词` | 多行用 `\|` 分隔 |
| 黑幕打完停留 / 等 N 秒才推进 | `等待秒` | 等不及可点左键跳过；`条件=等待秒数` 也用它 |
| 黑幕淡入 / 淡出快慢 | `淡入档数` / `淡出档数` | 档数 ÷ `黑幕字幕.淡步频`(12) = 秒。默认 24 ≈ 2 秒 |
| 黑幕打字快慢 | `打字速度` | 字/秒。0/空 = 组件默认 18 |
| NPC 走/飞速度 | `动作速度` | 米/秒 |
| 镜头时长/高度 | `镜头时长` / `镜头高度` | |
| 奖励 | `奖励物品` | `物品id:数量\|...` |

读取方在 `任务管理器`（例如 `取淡入档数(阶段)`）。**加一个新可调项 = 加一列 + 在 `QuestDefinition`
加字段 + 消费它的代码去读**（三步见 [reference/配置表字段](../reference/配置表字段.md) 的 4.2）。

> ⚠️ 约定：**0 或空 = 用代码里的默认值**（`任务管理器.默认淡入档数` 等）。这几个数值 0 在语义上没意义，
> 所以拿它当"没填"的哨兵；想"不淡"就填 `1`。要写进新列的 Tooltip，否则分不清"空 = 默认"还是"空 = 0"。

## 6. 标记（flags）：任务与对话解耦的桥

任务**不直接改对话**，对话**不直接看任务**，两边都只认一个全局集合：

```csharp
对话标记.添加一批(阶段.接取加标记);   // 进入阶段时
对话标记.添加一批(阶段.完成加标记);   // 完成阶段时
```

于是"任务到某一步时 NPC 多一个专属回答" = 任务写标记 + 对话行填「需要标记」并给个**更高的优先**。
反方向靠对话表的 `触发任务` / `完成任务` 两列（在**按下回答时**执行，见 `DialogueUI.按下回答` →
`任务管理器.处理对话绑定`）。

### 6.1 三个加标记的列（别混用）

| 列 | 什么时候加 | 用途 |
|---|---|---|
| `接取加标记` | 阶段被设为当前时 | "这个阶段开始了" |
| `完成加标记` | 阶段完成时 | "这个阶段过去了" |
| **`打标记`** | **不主动加** —— 只在**读档时按进度重放** | **补回旧档缺的标记** |

**为什么需要 `打标记`**：前两列只在阶段**实际走到**时才打，而读旧档时阶段早就过去了，标记永远补不上 ——
表现是大师兄回话时 `q_主线_在宗门` 是 false，三条主线对白全不满足，对话系统退到通用段 `dlg_common_01`。
做法：`任务管理器.补齐进度标记()` 在读档 / 跨场景后调，对每个任务把「已完成的阶段」和「当前阶段之前」的
所有 `打标记` 重放一遍（`HashSet` 幂等，重复加无害）。

**填表口径**：某个标记从"这一阶段起就该有" → 在这一阶段的 `打标记` 里写上。
例：`q_main_004` 阶段3「从此踏上修仙路」的 `打标记 = q_主线_在宗门`。

### 6.2 标记与存档

`对话标记` 随存档走（`SaveData.对话标记`），而且是**静态内存、会跨 Play 会话残留** ——
编辑器里测新流程**先重启 Unity**。读档时 `恢复存档进度()` 先按存档恢复，再调 `补齐进度标记()` 兜底，
所以**旧档 + 新加的 `打标记` 也能自愈**，不用重开档（见 [design/存档系统](存档系统.md)）。

## 7. 触发区与演出锁

### 7.1 任务触发区（`任务触发区.cs`）

挂在场景里的圆柱上，管三件事：

```
进圈 → 接取「触发任务id」/ 推进一格「完成阶段任务id」/ 写「加标记」
前置：需要完成任务id（推荐，会存档）| 需要标记（不存档）| 高度容差
```

| 设计点 | 做法 |
|---|---|
| 半径 | **跟随范围圈**：`实际半径 = 范围圈.lossyScale.x / 2` —— 缩放场景里那个圆柱就是改触发范围 |
| 高度 | **用玩家碰撞体中心判**，不用脚底根坐标（地面不平时脚底偏低会误挡） |
| 排查 | **进圈不触发会说明原因**（哪条前置没满足、高度差多少） |
| 体检 | 菜单 `修仙/主线/触发区一览（当前场景 / 全部场景）` |

### 7.2 演出锁：挡住玩家 + 挡住推进

```csharp
// ① 挡玩家操作（Player 上的 演出锁 组件）
演出锁.cs：该锁 = 黑幕字幕.演出中 || (对话也锁 && DialogueUI.正在显示)
// ② 挡阶段推进（任务管理器.Update）
if (演出中) return;
```

## 8. 跨场景与落点

根因：`LoadSceneMode.Single` 会**销毁旧场景的一切**。

### 8.1 两条接力通道

```
旧场景销毁前：钉住任务进度(导出进度())  → 静态快照（背包/功法/神通/任务进度）
新场景 Awake：                         → 灌回() → 导入进度()
```

- 存储是**静态字段**（`跨场景数据.cs`），不随对象销毁；玩家靠 `DontDestroyOnLoad` 宿主跨过去。
- 进度用 `跨场景数据.钉住任务进度(导出进度())` 在**切场景之前**钉住（接力竞态见 [踩坑总库 B 段](../ai/踩坑总库.md)）。
- **动作接力**：切场景那阶段的动作不能当场发（新场景还没激活完），所以推进一格 + 任务id塞进静态队列
  `跨场景待发动作` + 钉住进度 → 新场景第一帧 `Update` 再取出来执行。

### 8.2 黑幕要先盖上再切场景（四幕开头的定式）

```
阶段3  落黑幕(无字)  淡入 24 档 ≈ 2s，等待秒 2      ← 黑幕在古古镇就盖上
阶段4  切换场景 Sect 坐标=宗门落点                   ← 全程黑屏；同时登记落点
阶段5  黑幕字幕      「从此，一个平凡的少年踏上了修仙路」淡入 0（**不淡**）、
                     打字 9 字/秒、打完停 2s 或点左键跳过
阶段6  落点结束 → 生成NPC（大师兄）
```

- **为什么先盖幕**："切完场景再淡入"会在切换那一帧露出画面，主角被拉到策划点位的**拉扯过程也会被看到**。
- **`落黑幕` 动作**：只落黑幕、不打字（台词列留空），可同时登记玩家落点；
  等待秒 = 等它淡完的时间（≈ `淡入档数 ÷ 淡步频(12)`）。
- 落点登记放在**切场景那个阶段**（黑幕阶段还在旧场景，在那登记落点没意义）；`切到场景` 会读「坐标」列，
  填了就 `请求落点()`，由新场景的管理器执行。
- 那一段 `条件=无`：起幕 → 等 2 秒 → 进下一阶段（切场景）。

### 8.3 跨场景必须活着的状态

| 状态 | 存在哪 |
|---|---|
| 黑幕字幕 | `DontDestroyOnLoad`（黑屏 + 切场景时画面不能露出来） |
| 落点目标 / 是否仍在接管 | 静态字段 |
| 未走完的等待秒 | 静态字段（否则「等候 60 秒」一切场景就清零重来） |
| 已执行动作 | 静态 `HashSet`（三条派发路径不能重复执行同一阶段） |
| `演出中` | **`static`**（任务管理器随场景重建，实例字段会让新管理器读到 `false`） |
| 黑幕的收幕计时 / 淡入淡出进度 | 黑幕自己的**实例字段**（它 `DontDestroyOnLoad`，计时不会被切场景打断） |

> 协程随对象销毁消失、`演出中` 必须 `static`、等待秒数跨场景清零、重复派发三条路径 —— 权威条目见 [踩坑总库 B 段](../ai/踩坑总库.md)。

### 8.4 落点机制（`移动玩家` / `移动玩家且黑幕`）

```
请求落点(坐标, 接管秒) → 记静态目标 + 截止时刻；Update 每帧 处理落点():
  · 登记当帧不动（让新场景先摆完）· 只在偏离超过 容差(1m) 时才纠正 · 到截止时刻无条件放权（默认 0.6 秒）
```

- **不是协程**（原因见 [踩坑总库 B 段](../ai/踩坑总库.md)），是静态状态 + `Update`。
- 只负责"放到位"，**不负责按住玩家**：早期版本每帧硬写 `position` + 反复开关 `CharacterController`，
  把玩家锁死在落点上（往外跑又被拉回来）。
- `移动玩家且黑幕`：同帧落黑幕 + 登记落点，黑幕盖住那段拉扯。
  四幕流程：`1 等2秒 → 2 切场景 → 3 移动玩家且黑幕 → 4 等「落点结束」`。
- 找玩家优先 `GameObject.Find("Player")`，再退到按 `PlayerVitals` 组件找。
- ⚠️ **0 秒接管必须真的立刻放置一次**：原来 `请求落点` 里 `Mathf.Max(0.1f, 接管秒)` 把 0 抬成 0.1，
  `处理落点` 又先判 `Time.time >= 落点截止时刻` → 0 秒立刻成立 → 直接放弃，**位置从来没被应用过**。

### 8.5 跨场景接力：三条必须守住的规矩 ⚠️

「从宗门传送到个人洞府后，背包全丢、神通全没、也没落在对应落点上」一口气踩了三条（详见 [踩坑总库 专题：场景一致性](../ai/踩坑总库.md)）。

**① 存档只在「本局第一次进游戏场景」时应用一次。** `任务管理器.Start()` 里调的 `应用存档()` 原来**每个场景都跑**，而 `SaveSystem.应用到角色()` 的"是新档"分支会清空玩法数据并无条件重建 `面板.物品`：

```csharp
bool 是新档 = 存档里 背包/法宝/灵阵/坐骑/真灵 全空;
if (是新档) 面板数据.清空玩法数据();     // 连已学功法、已获得神通一起清
恢复面板(数据, 面板数据);                 // 面板.物品 = new List<>() 无条件清空重建
```

存档是空的时候（新开档还没存过），每次切场景都会把 `跨场景数据` 刚接过来的背包清成空 → **玩家数据全丢**。→ 用静态 `本局已应用存档` 挡住。

**② 接力期间不要用存档位置覆盖落点。** `SaveSystem` 会按 `数据.位置` 摆玩家，而切场景的目标是**目的地的落点** —— 冲突时**落点必须赢**：`跨场景数据.正在接力` 为真时跳过"按存档位置摆放玩家"（由 `黑幕字幕.开始场景过渡()` 置真、过渡第 5 段位置假）。

**③ 落点的 `0 秒接管` 必须按 §8.4 的做法真的应用一次**，否则传送落点等于没登记。

### 8.6 传送落点（`Teleporter` 用**名字**给落点）与传送交互

任务表给的是**坐标**落点；传送门给的是**名字**落点 —— `黑幕字幕.开始场景过渡(场景名, 显示名, 落点, 落点名)` 里二选一：

```
case 1（新场景加载完）:
  · 有 落点名 → 找场景物体(落点名) → 请求落点(点.position, 0f)   // 0 秒 = 立刻放置一次
  · 只有 落点坐标 → 请求落点(坐标)                              // 默认接管 1.2 秒
```

**铁律：落点名必须是目标场景里真实存在的物体名。** 找不到时**不报错**，只是不摆位 → 玩家留在**场景默认点**上，表现成"传送了但站的地方不对"。**约定：落点就用目标场景自己那道传送门的点位。**

| 出发点 | 目标 | 落点 |
|---|---|---|
| Sect / `main teleport` | village | `village to sect` |
| Sect / `main teleport` | Sect_Wilderness | `wild to sect` |
| Sect / `sect2 to tower` | Demon-Suppressing Tower | `tower to sect2` |
| Sect / `sect1 to 3c` | 3C_Testbed | `3ctestbed to sect1` |
| village / `village to sect` | Sect | `main teleport` |
| Sect_Wilderness / `wild to sect` | Sect | `main teleport` |
| 3C_Testbed / `3ctestbed to sect1` | Sect | `sect1 to 3c` |
| Demon-Suppressing Tower / `tower to sect2` | Sect | `sect2 to tower` |

> 宗门有 **3 道门**：`main teleport`（古古镇 / 宗门野外）、`sect2 to tower`（镇妖塔）、`sect1 to 3c`（3C）。**其他地图回宗门都是回到 `main teleport`**。用「修仙/体检/场景一致性」逐条核对；这三条传送门自身的点位脚下都是实心地面（实测门 y 与地面差 0~0.24m、门点重叠 0 个）。

**传送交互**（不再"走上去自动弹面板"，改成和 NPC / 建筑同一套设施交互）：

```
走近（< 交互距离 3.5m） → 出现「F 前往古古镇」提示 → 按 F → 弹「是否传送？」面板
                        → 点选项传送 ／ ESC 关掉 ／ 走出范围自动关
```

- 传送圈在 `Awake()` 里给自己**运行时补**一个 `StationInteractable`（类型=传送、按键=F）；
  面板仍由 `Teleporter` 自己画（要按选项数量动态生成按钮）。
- 接线细节、ESC 协调、界面开关的规矩收进 **[design/交互系统](交互系统.md)** —— 那里是**唯一权威**。
- 顺带消掉了老隐患：以前落点若压在传送圈里会"立刻再次触发、来回弹"，现在要按 F 才开。

## 9. 坑与注意

### 9.1 重复派发（做法与判据统计见 [踩坑总库 B 段](../ai/踩坑总库.md)）

三条路径会在切场景那一帧碰同一阶段：`进入阶段()` 自己、`导入进度` 的 `待发动作` 队列、跨场景静态队列 `跨场景待发动作`。「生成NPC」因此跑两遍、后一个大师兄顶掉前一个 → 对话不出现。
**做法**：静态 `已执行动作`（`任务id#阶段`），由 `执行动作` **入口**登记，两条队列在派发前先查它；⚠️ 别用 `阶段开始时间` 当去重判据（`导入进度` 会给接手阶段写那个时间戳，两者语义必须分开）。

### 9.2 无条件阶段的拆分代价

`条件=无` 的阶段必须"一个阶段一个动作"，导致四幕被拆成十几段。

### 9.3 引导（`任务引导`）看的是任务表末尾四列

演出之外，玩家还得知道**现在该去哪**。这件事由 `任务引导.cs` 一个人做（左侧追踪面板 +
目标头顶感叹号 + 出画面时的屏幕边缘箭头），**只读任务数据、不改任何任务状态**。

| 项 | 口径 |
|---|---|
| 引导哪一条 | **只看 `类型 = 主线`**；多条并跑取 **`任务id` 最大**的那条（id 按剧情顺序编，越大越靠后） |
| 目标怎么来 | 先查 `引导npcId` / `引导坐标`，**推不出来才按 `条件` 自动推**（`对话/击杀/NPC到位` → 找 NPC；`到达` → 用 `坐标X/Y/Z`） |
| 四列 | `引导npcId` / `引导坐标`（`x;y;z`，**分号**）/ `引导地点名` / `引导场景`，见 [reference/配置表字段 §4.3](../reference/配置表字段.md) |
| 跨场景 | 填了 `引导场景` 而玩家不在那个场景 → **不画标记**（两套坐标空间），面板改写「目标：X（在「Sect」）」 |
| 挂载 | 由 `场景自举` 补到**主相机**上，不写进场景 |

> **两个反复咬人的点**：① 不能只订阅 `阶段开始/阶段完成` —— 读档与跨场景接手走
> `导入进度()`，它**故意不发事件**，只订阅事件的 UI 会显示过期状态（现在每 0.4 秒自检一次）；
> ② ⚠️ **任务动作 `生成NPC` 造出来的是场景内对象，跨场景必丢**，而 `已执行动作` 会跳过它、
> **不会在新场景重跑** ⇒ 剧情 NPC 要跨场景活着，**别靠"往场景里摆一份"**（见 §9.5），
> 靠任务系统的按需重建。
> 完整规则、算法与实测数字见 [guides/任务引导](../guides/任务引导.md)。

### 9.4 跨场景的剧情 NPC：**登记 + 缺人就补**

`生成NPC` / `飞到` 造出来的都是**场景内对象**，玩家一切场景就随旧场景销毁；而任务动作
**不会**在新场景重跑（`已执行动作` 按 `任务id#阶段` 跳过）。所以"某段对话要跟某人说话，
而那人不在场"必须能被兜住 —— 这件事由 `任务管理器` 管，共两块：

**① `生成NPC` 必须登记"这个 NPC 是用哪个预制体造的"。**

```
生成过的NPC[ npcId ] = 预制体路径      // 供 找NPC 在它不在场时就地重建
```

⚠️ 登记 id **优先取任务表的 `动作目标npcId`，没填就拿刚生成出来那个实例的
`NpcInstance.定义.id` 兜底**（都拿不到才打一条警告「这个 NPC 以后不在场时没法自动重建」）。

**为什么非要兜底**：早期只按 `动作目标npcId` 登记，而任务表里 `生成NPC` 那一行
**常常只填了 `动作参数`（预制体路径）** —— 于是"人不在了就重建"这段代码**写得没错、
却从来没被走到**：`q_main_004` 阶段5 生成的大师兄一次都没被记下来，玩家自己走进洞府
（走传送门，**不是**任务驱动的 `切换场景`）之后他就永远消失，洞府那一幕的对话条件
**永远达不成**、整条灵田教学线卡死。

**② `确保对话NPC在场(阶段)`：要跟谁说话，那人不在就补在玩家旁边。**

对每个 `条件=对话` 的**当前阶段**各调一次：

| 项 | 口径 |
|---|---|
| 要跟谁说话 | 任务表 `目标npcId`；**没填**就用 `对话id` 走 `DialogueDatabase.取NpcId()` 反查 |
| 补在哪 | 玩家旁边（重建点 = 玩家附近，`找NPC` 的兜底位置） |
| **谁会补** | ⚠️ **只补任务自己生成过的 NPC**（内部查 `生成过的NPC`）—— **不会凭空造出场景里本来没有的路人** |
| 什么时候 | 主循环里，**演出锁之前、条件判定之前** —— 它不参与"条件是否达成"，纯粹是"把场景补齐"，所以不该被演出锁挡住（否则过场期间进场景，人得等过场结束才出现） |
| 频率 | 每个「阶段 + NPC」**只试一次**（失败也不刷屏） |
| 补完能引导吗 | 能。`任务引导` 走的是同一套 `目标npcId` / `对话id` 解析 |

**实测**（洞府那一幕）：`[任务] 生成 大师兄_任务生成 于 (24.07,-0.69,-5.29)`
→ 进洞府 + 拨到阶段18：`[Warning] 找NPC：npc_dashixiong 不在场 → 就地重建于 (0.00,0.02,1.20)`、
`「灵田初见」要跟 npc_dashixiong 说话，但它不在场 → 已就地补出来 @(0.00,0.02,1.20)`
→ 面板立刻有目标（`[目标：大师兄　2.7 米]`、头顶感叹号激活）→ 说完话 18→19、阶段19 的「飞到」正常执行。

**反面对照**（"不会凭空造路人"这一条也实测过）：在一个**没跑过主线**的场景（`village`）等 2 秒，
场上 NPC 数量 **`9 → 9` 没变**、两个标记都是 `False`。

> ⚠️ **别用"往场景里摆一份 NPC"替代它**：保存游玩场景会连带把它序列化的**运行时 UI 列表**重新排版，
> 一次保存能带出上千行与本次无关的改动。见 [踩坑总库 A8](../ai/踩坑总库.md)。

> **同样的按需解析还有一处**：`任务引导` 也用 `对话id` 反查"该指谁"（条件=对话 且 `目标npcId` 空时）。
> 两边共用 `DialogueDatabase.取NpcId()`，**别各写一份**。
