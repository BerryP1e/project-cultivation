## 1. 核心思路

> **策划表里一行 = 剧情的一个阶段。** 引擎不认剧情，只认「条件满足 → 执行动作 → 进下一行」。
> 对话、NPC、镜头、场景、黑幕全都是同一张任务表的**动作列**。

所以改剧情 = 改 `任务表.csv`，不用碰代码。

---

## 2. 三层结构

```
Assets/Data/Tables/任务表.csv              ← 唯一真相源，一行一个阶段
  │ 菜单：修仙/从配置表生成资产
  ▼
Assets/Data/Generated/QuestDefinition/<id>.asset     （编辑器产物，不要手改）
  │ 菜单内部自动跟着跑：收集
  ▼
Assets/resources/任务/任务库.asset          ← 运行时才读得到
  ▼
代码：QuestDatabase.取()（静态缓存）
```

「收集」这一步是因为生成资产不在 Resources 里、运行时取不到，所以要摊平成库资产放进 Resources；
`修仙/从配置表生成资产` 结束时自动收集一次。

## 3. 任务模型：阶段链

一行任务表 = 一个 `QuestDefinition`。同一个 `任务id` 的多个阶段按 `阶段` **升序串成链**。
运行时只记 `当前阶段[任务id] = 阶段号`；导出进度是一行字符串 `q_main_004:7;q_main_002:0`（`:0` = 整条已完成）。

```csharp
var 下一 = db.取阶段(任务id, 阶段.阶段 + 1);
if (下一 != null) 进入阶段(任务id, 下一);      // 内部会 执行动作 + 加接取标记
else { 当前阶段.Remove(任务id); 已完成任务.Add(任务id); }   // 整条完成
```

`Update()` 每 `检查间隔`（默认 0.25 秒）轮一次条件。

## 4. 完成条件（`任务条件`）

| 条件 | 判定 |
|---|---|
| `无` | 成为当前阶段的**下一帧**就完成 → **一个阶段只能挂一个动作** |
| `等待秒数` | `Time.time - 阶段开始时间 >= 等待秒` |
| `到达` | 玩家与 `坐标` 水平距离 ≤ `到达半径` |
| `对话` | **玩家按下某一段的「回答 / 继续」时**才完成（填法与自查见 [对话系统](对话系统.md)，那里是唯一权威） |
| `提交物品` | 背包有 `物品id × 数量`（完成时真扣掉） |
| `击杀` | 目标 `目标npcId` 死亡（留空 = 任意 NPC 死一个） |
| `NPC到位` | 目标 NPC 走到（最近一次「飞到」记下的）落点 1.5 m 内 |
| `落点结束` | 玩家落点流程结束（「移动玩家」/「移动玩家且黑幕」把主角放到位） |
| **`有标记`** | 具备 **`物品id`** 那一列写的**对话标记**就算完成（⚠️ 本条件下那一列**不是物品**，是标记名）。等"别处发生的一件事"用它 —— 例：主线阶段37「进塔去」= `物品id = q_主线_出过塔`，而那个标记由 `TowerController.退到塔外()` 打 ⇒ **进过塔、并且出来了**才算（用户 2026-10-02 的要求：不是走到塔门就算） |
| **`在场景`** | 玩家**此刻就在 `场景名` 那一列写的场景里**就算完成（判定忽略大小写）。专治"走进那道光 / 回到洞府"这类**目标本身就是换个场景**的阶段 —— 用 `到达` 要靠坐标（两个场景的坐标是两套空间，容易误判），用 `对话` 又会变成"必须先跟某人说句话"（用户 2026-10-02 明确否掉了这个耦合，见 [design/主线剧情 §6.1](主线剧情.md)） |
| **`灵田已种植`** | `灵田.取().已种数 >= 数量`（`数量` 留空/0 按 **1** 算）。"种着东西的地块数" = 地里**已经不是"待种植"**的块数 —— 即玩家真的摆下一块地**并种了东西**（只摆不种不算） |
| **`境界等级`** | `PlayerCultivation.等级 >= 数量`（`数量` 留空/0 按 **1** 算）。长线门槛用它，例：镇妖塔准入 = 炼气三层 = `数量 3` |
| **`炼过丹`** | `炼丹炉.炼成过的种类数 >= 数量`（`数量` 留空/0 按 **1** 算）。数的是对话标记里的 **`炼成_*`**，而它**只在炼丹成功时**才打 ⇒ **任意一种丹药炼成过就行**。例：主线阶段27「走近丹房」= `数量 1`。⚠️ **不能数 `丹方_*`** —— 那个标记任务表**阶段24 也会打**（一次给 4 张丹方），拿它当判据会让阶段27 一进去就"已经炼过丹"、直接跳到 28（实测踩过） |

> 这三个都是**"验真"型**条件：防"收到道具就算学会种田""走到丹房就算炼过丹"，也给长线进度一个可检查的闸门。
> `数量` 这一列因此有**四种**语义 —— `提交物品` 是**物品个数**、这三个是**门槛数值**（地块数 / 等级 / 丹方种数）。
> ⚠️ 写任务表时按 `条件` 判断 `数量` 指什么，别混。
>
> ⚠️ **"某人在不在场"不许由对话条件决定**（2026-10-02 用户否掉的耦合）：
> 洞府里的大师兄原来靠 `确保对话NPC在场()` 补，而它只在"本阶段点名的对话**此刻能说**"时才补 ——
> 那段对话锁在宗门 ⇒ 玩家一进洞府**人不在**，得先回去说句话才见得到他。
> 现在"要不要他出现"交给 **`动作=确保NPC`**（进洞府这一件事就决定），见 [design/主线剧情 §6.1](主线剧情.md)。
>
> ⚠️ **说明书里承诺的动作，必须真的被判定**（两次都是这么踩的）：阶段21 说明写"种下第一颗种子"、
> 条件却是 `无`；阶段27 说明写"试试炼某一种丹药"、条件却是 `到达` —— 玩家**照说明书做了，主线一点反应都没有**
> （那一步早被"到了就算"吃掉）。写阶段时对一遍：**说明书那句动词，`条件` 里有没有对应的判定**。
>
> ⚠️ **拿标记当"玩法验真"的判据前，先查这个标记有没有别人也在写**：`丹方_` 有两处写
> （炼丹成功 + 任务表阶段24 的 `完成加标记`），于是"学会 4 张丹方"被当成了"炼过 4 种丹"。
> 分出一个只由玩法成功写的 `炼成_` 才对。

## 5. 动作（`任务动作`）

### 5.1 过场演出类（不需要目标 NPC）

| 动作 | 说明 |
|---|---|
| 黑幕字幕 | 台词列按 `\|` 拆行，逐字打出；等待秒 = 打完后再停留多久 |
| 闪白 | 白屏闪一下 |
| 播放对话 | 强制弹框（不用玩家按 F） |
| 镜头看目标 / 镜头回玩家 | 镜头调度 |
| 移动玩家 | 把玩家挪到「坐标」（落点，见 §8.4） |
| 移动玩家且黑幕 | 同上，但**同帧先落黑幕**当遮罩（四幕切到宗门用） |
| 切换场景 | `LoadSceneAsync` 单场景加载 |
| **推进天数** | **把游戏内时间往前推 1 天**（`时间管理器.推进(1f)`）。★ **台词非空时顺便打一段黑幕字幕**：`等待秒` = 打完再停多久，`淡入/淡出档数`、`打字速度` 同其它黑幕阶段。用来演「过了一夜」（例：阶段23「次日清晨」= 推进天数 + 黑幕「翌日，太虚宗」，见 §5.1.1） |
| 生成NPC | 按「动作参数」的预制体路径生成到「坐标」。⚠️ **生成出来的是"那个预制体"，它自带自己的 `NpcInstance.定义`** —— 想生成剧情 NPC 就得给它**自己的预制体（+ Variant）**，不能借用别人的（见 §5.2） |
| 确保NPC | 不在场就按「动作参数」重建 |
| 接取任务 | 动作参数 = 要接取的任务id |

> **`播放对话` 的一条行为**：台词列含 `\|` 时是**逐句演出**（`DialogueUI.演出多行`），
> **每句要点一下才往下走** —— 人玩没问题，但**自动化测试会停在那里等点击**
> （实测就是它把 `演出中` 卡住的，见 §9.5）。

#### 5.1.1 为什么「过夜」要塞进 `推进天数` 这个动作里（2026-10-02）

用户报的：「过了一夜，也没有真的过了一夜；那个'翌日，太虚宗'的黑幕出场时机也有问题」。

| 现象 | 根因 |
|---|---|
| 过夜只有右上角日期在偷偷跳 | 阶段23 的动作只是 `推进天数`，**没有任何画面**（原来那 3 秒是 `条件=等待秒数` 在干等） |
| 「翌日」黑幕出现在**大师兄早上那段话之后** | 那次黑幕挂在阶段25，而"过夜"发生在阶段23 ⇒ **顺序是反的**：玩家先听师兄说「小师弟，醒了？」，才看到「翌日」 |

**任务表「动作」只有一列**，而"过了一夜"本来就是**时间 + 一幕黑**两件事 —— 所以让 `推进天数`
在台词非空时顺手把那一幕演了。用户要的顺序：

```
阶段22 大师兄「灵草成熟，便可拿去炼丹、炼器。改日我再教你。」   ← 种完田、天黑了
阶段23 推进天数 + 黑幕「翌日，太虚宗」                        ← 夜里过去（这里真的是新的一天）
阶段24 大师兄「小师弟，醒了？今日带你去认认丹房…」+ 给丹方/材料  ← 次日清晨，在洞府
阶段25 黑幕「大师兄引你往丹房去」（幕留着不收）
阶段26 切换场景 Sect —— 过渡自己在这块黑幕上打出「太虚宗」再切
```

⚠️ **阶段25 的台词里不要再写「翌日，太虚宗」**：切场景的过渡会自己打「太虚宗」，
写重复了就是连着两块"太虚宗"黑幕。
⚠️ 这一阶段的 `条件=等待秒数` **会被 `演出中` 挡到幕收掉之后**才判定（条件检查在
`if (演出中) return;` 之后）⇒ 不会在天还黑着的时候推进到下一阶段。

**实测**（Play）：`[纪年] 新的一天 —— 太虚历 1 年 1 月 2 日`、
`[任务] 调度：推进天数 + 黑幕「翌日，太虚宗」打完停留 1.00s，淡入 24 档 / 淡出 24 档`；
幕在时 `演出中=True`、阶段停在 23；幕收掉后 23 → 24 并开始播大师兄那 5 句 ✔

### 5.2 NPC 调度类（先按 `目标npcId` 找 `NpcInstance.定义.id`）
播动画 / 攻击玩家 / 销毁 / 走向 / **飞到**（升空 → 前进 → 悬停）/ 处决。

**`飞到` 的完整流程**（`任务管理器.飞过去()`，协程）：

```
Yufeng_TakeOff → 等 0.45 秒 → 前进状态（`动作参数`，留空 = "Yufeng_Forward"）
              → 自己 MoveTowards 位移（速度 = `动作速度`）+ 朝目标水平转向
              → 到点（≤ 0.2 米）切 Yufeng_Idle
```

| 列 | 作用 |
|---|---|
| `动作目标npcId` | 飞谁；同时把这个落点记进 `NPC落点`（下一阶段用 `条件=NPC到位` 判定的基准） |
| `动作参数` | **前进状态名**（默认 `Yufeng_Forward`） |
| `动作速度` | 米/秒 |
| `坐标X/Y/Z` | 落点；**留空 `(0,0,0)` = 飞向"玩家当时的实时位置"前方 2 米**（写死坐标会因为玩家走动而飞错地方） |

而且它**不阻塞阶段推进**（`执行动作` 是同步流程、协程没法 yield）——
"到位之后才播对话"要靠**下一阶段的 `条件=NPC到位`** 保证。

> ⚠️ **要让 NPC 演「常态御风」，就用 `飞到`，不要用裸的 `播动画`。**
> 站着不动的 NPC 只播一个御风姿态时，会被 NPC **自己的待机行为按回 `idle`**
> （实测：派发了 `播动画 Yufeng_Idle`，`Animator` 却一直停在 `idle`、高度也没变）；
> 而 `飞到` 这条路的位移由任务管理器接管，**同时把升空 / 前进 / 悬停一气演完**，
> 所以站得住。详见 §9.7。

> ⚠️ **「找到目标 NPC」失败会静默跳过**（只打一条 Warning），但**阶段照样推进** →
> 表现常常是"对话弹了但人不在"，去 Console 搜 `动作的目标 NPC 不在场景里`。
>
> `生成NPC` 会登记「这个 NPC 是用哪个预制体造的」，`找NPC` 找不到时就**就地重建**（重建点 = 玩家附近）
> —— 登记的 id **优先取 `动作目标npcId`，没填拿实例的 `NpcInstance.定义.id` 兜底**；
> 只有 `动作参数`（预制体路径）时也记得住。详见 §9.4。

> ⚠️ **`生成NPC` 生成的是"那个预制体本身"，而预制体自带它自己的 `NpcInstance.定义`。**
> 所以**借用别人的预制体会带上那个人的身份**（id / 名字 / 好感 / 境界全是别人的）。
> 实测：想让师父出场，若直接生成 `YangJian_03`，拿到的是一个**境界 83 的战斗 NPC**。
> **剧情 NPC 一律给它自己的预制体** —— 可以是别人 prefab 的 **Prefab Variant**，
> 也可以是**用自己 FBX 重建的独立 prefab**；**要看基地骨架合不合用**（要演御风就得有御风状态）。
> 详见 §9.6。

### 5.3 奖励：`奖励物品` 与 `奖励贡献` **并列发、互不影响**

`任务管理器.发奖励(阶段)` 一次看两列：

| 列 | 发什么 |
|---|---|
| `奖励物品` | 写法 `物品id:数量|…`，逐个塞进背包 |
| **`奖励贡献`** | **int**，`阶段.奖励贡献 > 0` 时 `宗门贡献.加(奖励贡献, "任务「任务名」第 N 阶段")` |

两列**各发各的** —— 填了贡献不会吃掉物品，反之亦然。货币全貌见
[guides/宗门贡献与兑换](../guides/宗门贡献与兑换.md)。

### 5.5 观感参数全部表驱动（改表即可，不用动代码）

**硬规矩**：演出的可调数字**不许硬编码在 C# 里**，必须能从任务表改。用到的列：

| 想调什么 | 列 | 说明 |
|---|---|---|
| 黑幕台词 | `台词` | 多行用 `\|` 分隔 |
| 黑幕打完停留 / 等 N 秒才推进 | `等待秒` | 等不及可点左键跳过；`条件=等待秒数` 也用它 |
| 黑幕淡入 / 淡出快慢 | `淡入档数` / `淡出档数` | 档数 ÷ `黑幕字幕.淡步频`(12) = 秒。默认 24 ≈ 2 秒 |
| 黑幕打字快慢 | `打字速度` | 字/秒。0/空 = 组件默认 18 |
| NPC 走/飞速度 | `动作速度` | 米/秒 |
| 镜头时长/高度 | `镜头时长` / `镜头高度` | |
| 奖励 | `奖励物品` | `物品id:数量\|...` |

读取方在 `任务管理器`（例如 `取淡入档数(阶段)`）。**加一个新可调项 = 加一列 + 在 `QuestDefinition`
加字段 + 消费它的代码去读**（三步见 [reference/配置表字段](../reference/配置表字段.md) 的 4.2）。

> ⚠️ 约定：**0 或空 = 用代码里的默认值**（`任务管理器.默认淡入档数` 等）。这几个数值 0 在语义上没意义，
> 所以拿它当"没填"的哨兵；想"不淡"就填 `1`。要写进新列的 Tooltip，否则分不清"空 = 默认"还是"空 = 0"。

## 6. 标记（flags）：任务与对话解耦的桥

任务**不直接改对话**，对话**不直接看任务**，两边都只认一个全局集合：

```csharp
对话标记.添加一批(阶段.接取加标记);   // 进入阶段时
对话标记.添加一批(阶段.完成加标记);   // 完成阶段时
```

于是"任务到某一步时 NPC 多一个专属回答" = 任务写标记 + 对话行填「需要标记」并给个**更高的优先**。
反方向靠对话表的 `触发任务` / `完成任务` 两列（在**按下回答时**执行，见 `DialogueUI.按下回答` →
`任务管理器.处理对话绑定`）。

### 6.1 三个加标记的列（别混用）

| 列 | 什么时候加 | 用途 |
|---|---|---|
| `接取加标记` | 阶段被设为当前时 | "这个阶段开始了" |
| `完成加标记` | 阶段完成时 | "这个阶段过去了" |
| **`打标记`** | **不主动加** —— 只在**读档时按进度重放** | **补回旧档缺的标记** |

**为什么需要 `打标记`**：前两列只在阶段**实际走到**时才打，而读旧档时阶段早就过去了，标记永远补不上 ——
表现是大师兄回话时 `q_主线_在宗门` 是 false，三条主线对白全不满足，对话系统退到通用段 `dlg_common_01`。
做法：`任务管理器.补齐进度标记()` 在读档 / 跨场景后调，对每个任务把「已完成的阶段」和「当前阶段之前」的
所有 `打标记` 重放一遍（`HashSet` 幂等，重复加无害）。

**填表口径**：某个标记从"这一阶段起就该有" → 在这一阶段的 `打标记` 里写上。
例：`q_main_004` 阶段3「从此踏上修仙路」的 `打标记 = q_主线_在宗门`。

### 6.2 标记与存档

`对话标记` 随存档走（`SaveData.对话标记`），而且是**静态内存、会跨 Play 会话残留** ——
编辑器里测新流程**先重启 Unity**。读档时 `恢复存档进度()` 先按存档恢复，再调 `补齐进度标记()` 兜底，
所以**旧档 + 新加的 `打标记` 也能自愈**，不用重开档（见 [design/存档系统](存档系统.md)）。

## 7. 触发区与演出锁

### 7.1 任务触发区（`任务触发区.cs`）

挂在场景里的圆柱上，管三件事：

```
进圈 → 接取「触发任务id」/ 推进一格「完成阶段任务id」/ 写「加标记」
前置：需要完成任务id（推荐，会存档）| 需要标记（不存档）| 高度容差
```

| 设计点 | 做法 |
|---|---|
| 半径 | **跟随范围圈**：`实际半径 = 范围圈.lossyScale.x / 2` —— 缩放场景里那个圆柱就是改触发范围 |
| 高度 | **用玩家碰撞体中心判**，不用脚底根坐标（地面不平时脚底偏低会误挡） |
| 排查 | **进圈不触发会说明原因**（哪条前置没满足、高度差多少） |
| 体检 | 菜单 `修仙/主线/触发区一览（当前场景 / 全部场景）` |

范围圈模型与 Gizmos 是两层显示：`游戏里隐藏范围圈` 默认开启，`Awake` 就关闭范围模型的 Renderer；`显示范围` 只负责 Scene 视图调试。Play 中 `OnDrawGizmos` 检查当前绘制是否来自 Scene 视图，Game 视图即使开启 Gizmos 也不画黄圈。隐藏只影响显示，继续按原范围圈缩放计算半径，不删除模型、不改任务触发条件。若游戏中看到黄线，先区分 Renderer 与 Gizmos，不要为此把检测半径改为零。

### 7.2 演出锁：挡住玩家 + 挡住推进

```csharp
// ① 挡玩家操作（Player 上的 演出锁 组件）
演出锁.cs：该锁 = 黑幕字幕.演出中 || (对话也锁 && DialogueUI.正在显示)
// ② 挡阶段推进（任务管理器.Update）
if (演出中) return;
```

## 8. 跨场景与落点

根因：`LoadSceneMode.Single` 会**销毁旧场景的一切**。

### 8.1 两条接力通道

```
旧场景销毁前：钉住任务进度(导出进度())  → 静态快照（背包/功法/神通/任务进度）
新场景 Awake：                         → 灌回() → 导入进度()
```

- 存储是**静态字段**（`跨场景数据.cs`），不随对象销毁；玩家靠 `DontDestroyOnLoad` 宿主跨过去。
- 进度用 `跨场景数据.钉住任务进度(导出进度())` 在**切场景之前**钉住（接力竞态见 [踩坑总库 B 段](../ai/踩坑总库.md)）。
- **动作接力**：切场景那阶段的动作不能当场发（新场景还没激活完），所以推进一格 + 任务id塞进静态队列
  `跨场景待发动作` + 钉住进度 → 新场景第一帧 `Update` 再取出来执行。

### 8.2 黑幕要先盖上再切场景（四幕开头的定式）

```
阶段3  落黑幕(无字)  淡入 24 档 ≈ 2s，等待秒 2      ← 黑幕在古古镇就盖上
阶段4  切换场景 Sect 坐标=宗门落点                   ← 全程黑屏；同时登记落点
阶段5  黑幕字幕      「从此，一个平凡的少年踏上了修仙路」淡入 0（**不淡**）、
                     打字 9 字/秒、打完停 2s 或点左键跳过
阶段6  落点结束 → 生成NPC（大师兄）
```

- **为什么先盖幕**："切完场景再淡入"会在切换那一帧露出画面，主角被拉到策划点位的**拉扯过程也会被看到**。
- **`落黑幕` 动作**：只落黑幕、不打字（台词列留空），可同时登记玩家落点；
  等待秒 = 等它淡完的时间（≈ `淡入档数 ÷ 淡步频(12)`）。
- 落点登记放在**切场景那个阶段**（黑幕阶段还在旧场景，在那登记落点没意义）；`切到场景` 会读「坐标」列，
  填了就 `请求落点()`，由新场景的管理器执行。
- 那一段 `条件=无`：起幕 → 等 2 秒 → 进下一阶段（切场景）。

### 8.3 跨场景必须活着的状态

| 状态 | 存在哪 |
|---|---|
| 黑幕字幕 | `DontDestroyOnLoad`（黑屏 + 切场景时画面不能露出来） |
| 落点目标 / 是否仍在接管 | 静态字段 |
| 未走完的等待秒 | 静态字段（否则「等候 60 秒」一切场景就清零重来） |
| 已执行动作 | 静态 `HashSet`（三条派发路径不能重复执行同一阶段） |
| `演出中` | **`static`**（任务管理器随场景重建，实例字段会让新管理器读到 `false`） |
| 黑幕的收幕计时 / 淡入淡出进度 | 黑幕自己的**实例字段**（它 `DontDestroyOnLoad`，计时不会被切场景打断） |

> 协程随对象销毁消失、`演出中` 必须 `static`、等待秒数跨场景清零、重复派发三条路径 —— 权威条目见 [踩坑总库 B 段](../ai/踩坑总库.md)。

### 8.4 落点机制（`移动玩家` / `移动玩家且黑幕`）

```
请求落点(坐标, 接管秒) → 记静态目标 + 截止时刻；Update 每帧 处理落点():
  · 登记当帧不动（让新场景先摆完）· 只在偏离超过 容差(1m) 时才纠正 · 到截止时刻无条件放权（默认 0.6 秒）
```

- **不是协程**（原因见 [踩坑总库 B 段](../ai/踩坑总库.md)），是静态状态 + `Update`。
- 只负责"放到位"，**不负责按住玩家**：早期版本每帧硬写 `position` + 反复开关 `CharacterController`，
  把玩家锁死在落点上（往外跑又被拉回来）。
- `移动玩家且黑幕`：同帧落黑幕 + 登记落点，黑幕盖住那段拉扯。
  四幕流程：`1 等2秒 → 2 切场景 → 3 移动玩家且黑幕 → 4 等「落点结束」`。
- 找玩家优先 `GameObject.Find("Player")`，再退到按 `PlayerVitals` 组件找。
- ⚠️ **0 秒接管必须真的立刻放置一次**：原来 `请求落点` 里 `Mathf.Max(0.1f, 接管秒)` 把 0 抬成 0.1，
  `处理落点` 又先判 `Time.time >= 落点截止时刻` → 0 秒立刻成立 → 直接放弃，**位置从来没被应用过**。

### 8.5 跨场景接力：三条必须守住的规矩 ⚠️

「从宗门传送到个人洞府后，背包全丢、神通全没、也没落在对应落点上」一口气踩了三条（详见 [踩坑总库 专题：场景一致性](../ai/踩坑总库.md)）。

**① 存档只在「本局第一次进游戏场景」时应用一次。** `任务管理器.Start()` 里调的 `应用存档()` 原来**每个场景都跑**，而 `SaveSystem.应用到角色()` 的"是新档"分支会清空玩法数据并无条件重建 `面板.物品`：

```csharp
bool 是新档 = 存档里 背包/法宝/灵阵/坐骑/真灵 全空;
if (是新档) 面板数据.清空玩法数据();     // 连已学功法、已获得神通一起清
恢复面板(数据, 面板数据);                 // 面板.物品 = new List<>() 无条件清空重建
```

存档是空的时候（新开档还没存过），每次切场景都会把 `跨场景数据` 刚接过来的背包清成空 → **玩家数据全丢**。→ 用静态 `本局已应用存档` 挡住。

**② 接力期间不要用存档位置覆盖落点。** `SaveSystem` 会按 `数据.位置` 摆玩家，而切场景的目标是**目的地的落点** —— 冲突时**落点必须赢**：`跨场景数据.正在接力` 为真时跳过"按存档位置摆放玩家"（由 `黑幕字幕.开始场景过渡()` 置真、过渡第 5 段位置假）。

**③ 落点的 `0 秒接管` 必须按 §8.4 的做法真的应用一次**，否则传送落点等于没登记。

### 8.6 传送落点（`Teleporter` 用**名字**给落点）与传送交互

任务表给的是**坐标**落点；传送门给的是**名字**落点 —— `黑幕字幕.开始场景过渡(场景名, 显示名, 落点, 落点名)` 里二选一：

```
case 1（新场景加载完）:
  · 有 落点名 → 找场景物体(落点名) → 请求落点(点.position, 0f)   // 0 秒 = 立刻放置一次
  · 只有 落点坐标 → 请求落点(坐标)                              // 默认接管 1.2 秒
```

**铁律：落点名必须是目标场景里真实存在的物体名。** 找不到时**不报错**，只是不摆位 → 玩家留在**场景默认点**上，表现成"传送了但站的地方不对"。**约定：落点就用目标场景自己那道传送门的点位。**

| 出发点 | 目标 | 落点 |
|---|---|---|
| Sect / `main teleport` | village | `village to sect` |
| Sect / `main teleport` | Sect_Wilderness | `wild to sect` |
| Sect / `sect2 to tower` | Demon-Suppressing Tower | `tower to sect2` |
| Sect / `sect1 to 3c` | 3C_Testbed | `3ctestbed to sect1` |
| village / `village to sect` | Sect | `main teleport` |
| Sect_Wilderness / `wild to sect` | Sect | `main teleport` |
| 3C_Testbed / `3ctestbed to sect1` | Sect | `sect1 to 3c` |
| Demon-Suppressing Tower / `tower to sect2` | Sect | `sect2 to tower` |

> 宗门有 **3 道门**：`main teleport`（古古镇 / 宗门野外）、`sect2 to tower`（镇妖塔）、`sect1 to 3c`（3C）。**其他地图回宗门都是回到 `main teleport`**。用「修仙/体检/场景一致性」逐条核对；这三条传送门自身的点位脚下都是实心地面（实测门 y 与地面差 0~0.24m、门点重叠 0 个）。

**传送交互**（不再"走上去自动弹面板"，改成和 NPC / 建筑同一套设施交互）：

```
走近（< 交互距离 3.5m） → 出现「F 前往古古镇」提示 → 按 F → 弹「是否传送？」面板
                        → 点选项传送 ／ ESC 关掉 ／ 走出范围自动关
```

- 传送圈在 `Awake()` 里给自己**运行时补**一个 `StationInteractable`（类型=传送、按键=F）；
  面板仍由 `Teleporter` 自己画（要按选项数量动态生成按钮）。
- 接线细节、ESC 协调、界面开关的规矩收进 **[design/交互系统](交互系统.md)** —— 那里是**唯一权威**。
- 顺带消掉了老隐患：以前落点若压在传送圈里会"立刻再次触发、来回弹"，现在要按 F 才开。

## 9. 坑与注意

### 9.1 重复派发（做法与判据统计见 [踩坑总库 B 段](../ai/踩坑总库.md)）

三条路径会在切场景那一帧碰同一阶段：`进入阶段()` 自己、`导入进度` 的 `待发动作` 队列、跨场景静态队列 `跨场景待发动作`。「生成NPC」因此跑两遍、后一个大师兄顶掉前一个 → 对话不出现。
**做法**：静态 `已执行动作`（`任务id#阶段`），由 `执行动作` **入口**登记，两条队列在派发前先查它；⚠️ 别用 `阶段开始时间` 当去重判据（`导入进度` 会给接手阶段写那个时间戳，两者语义必须分开）。

### 9.2 无条件阶段的拆分代价

`条件=无` 的阶段必须"一个阶段一个动作"，导致四幕被拆成十几段。

### 9.3 引导（`任务引导`）看的是任务表末尾四列

演出之外，玩家还得知道**现在该去哪**。这件事由 `任务引导.cs` 一个人做（左侧追踪面板 +
目标头顶感叹号 + 出画面时的屏幕边缘箭头），**只读任务数据、不改任何任务状态**。

| 项 | 口径 |
|---|---|
| 引导哪一条 | **只看 `类型 = 主线`**；多条并跑取 **`任务id` 最大**的那条（id 按剧情顺序编，越大越靠后） |
| 目标怎么来 | 先查 `引导npcId` / `引导坐标`，**推不出来才按 `条件` 自动推**（`对话/击杀/NPC到位` → 找 NPC；`到达` → 用 `坐标X/Y/Z`） |
| 四列 | `引导npcId` / `引导坐标`（`x;y;z`，**分号**）/ `引导地点名` / `引导场景`，见 [reference/配置表字段 §4.3](../reference/配置表字段.md) |
| 跨场景 | 填了 `引导场景` 而玩家不在那个场景 → **不画标记**（两套坐标空间），面板改写「目标：X（在「Sect」）」 |
| 挂载 | 由 `场景自举` 补到**主相机**上，不写进场景 |

> **两个反复咬人的点**：① 不能只订阅 `阶段开始/阶段完成` —— 读档与跨场景接手走
> `导入进度()`，它**故意不发事件**，只订阅事件的 UI 会显示过期状态（现在每 0.4 秒自检一次）；
> ② ⚠️ **任务动作 `生成NPC` 造出来的是场景内对象，跨场景必丢**，而 `已执行动作` 会跳过它、
> **不会在新场景重跑** ⇒ 剧情 NPC 要跨场景活着，**别靠"往场景里摆一份"**（见 §9.5），
> 靠任务系统的按需重建。
> 完整规则、算法与实测数字见 [guides/任务引导](../guides/任务引导.md)。

### 9.4 跨场景的剧情 NPC：**登记 + 缺人就补**

`生成NPC` / `飞到` 造出来的都是**场景内对象**，玩家一切场景就随旧场景销毁；而任务动作
**不会**在新场景重跑（`已执行动作` 按 `任务id#阶段` 跳过）。所以"某段对话要跟某人说话，
而那人不在场"必须能被兜住 —— 这件事由 `任务管理器` 管，共两块：

**① `生成NPC` 必须登记"这个 NPC 是用哪个预制体造的"。**

```
生成过的NPC[ npcId ] = 预制体路径      // 供 找NPC 在它不在场时就地重建
```

⚠️ 登记 id **优先取任务表的 `动作目标npcId`，没填就拿刚生成出来那个实例的
`NpcInstance.定义.id` 兜底**（都拿不到才打一条警告「这个 NPC 以后不在场时没法自动重建」）。

**为什么非要兜底**：早期只按 `动作目标npcId` 登记，而任务表里 `生成NPC` 那一行
**常常只填了 `动作参数`（预制体路径）** —— 于是"人不在了就重建"这段代码**写得没错、
却从来没被走到**：`q_main_004` 阶段5 生成的大师兄一次都没被记下来，玩家自己走进洞府
（走传送门，**不是**任务驱动的 `切换场景`）之后他就永远消失，洞府那一幕的对话条件
**永远达不成**、整条灵田教学线卡死。

**② `确保对话NPC在场(阶段)`：要跟谁说话，那人不在就补在玩家旁边。**

对每个 `条件=对话` 的**当前阶段**各调一次：

| 项 | 口径 |
|---|---|
| 要跟谁说话 | 任务表 `目标npcId`；**没填**就用 `对话id` 走 `DialogueDatabase.取NpcId()` 反查 |
| 补在哪 | 玩家旁边（重建点 = 玩家附近，`找NPC` 的兜底位置） |
| **谁会补** | ⚠️ **只补任务自己生成过的 NPC**（内部查 `生成过的NPC`）—— **不会凭空造出场景里本来没有的路人** |
| 什么时候 | 主循环里，**演出锁之前、条件判定之前** —— 它不参与"条件是否达成"，纯粹是"把场景补齐"，所以不该被演出锁挡住（否则过场期间进场景，人得等过场结束才出现） |
| 频率 | 每个「阶段 + NPC」**只试一次**（失败也不刷屏） |
| **什么时候不补** | ⚠️ **这段对话此刻根本出不来**（`DialogueDatabase.阶段对话能出(阶段)` 为 false，例如它被 `场景_3C_Testbed` 锁在洞府里而玩家还在宗门）就**不补** —— 否则玩家会在"这段话根本说不了"的地方看到一个能按 F 的师兄，而这一阶段的本意是"走进传送光"。见 §9.3 与 [guides/任务引导 §3.3](../guides/任务引导.md) |
| 补完能引导吗 | 能。`任务引导` 走的是同一套 `目标npcId` / `对话id` 解析，**而且用的是同一个 `阶段对话能出` 判断** |

**实测**（洞府那一幕）：`[任务] 生成 大师兄_任务生成 于 (24.07,-0.69,-5.29)`
→ 进洞府 + 拨到阶段18：`[Warning] 找NPC：npc_dashixiong 不在场 → 就地重建于 (0.00,0.02,1.20)`、
`「灵田初见」要跟 npc_dashixiong 说话，但它不在场 → 已就地补出来 @(0.00,0.02,1.20)`
→ 面板立刻有目标（`[目标：大师兄　2.7 米]`、头顶感叹号激活）→ 说完话 18→19、阶段19 的「飞到」正常执行。

**反面对照**（"不会凭空造路人"这一条也实测过）：在一个**没跑过主线**的场景（`village`）等 2 秒，
场上 NPC 数量 **`9 → 9` 没变**、两个标记都是 `False`。

> ⚠️ **别用"往场景里摆一份 NPC"替代它**：保存游玩场景会连带把它序列化的**运行时 UI 列表**重新排版，
> 一次保存能带出上千行与本次无关的改动。见 [踩坑总库 A8](../ai/踩坑总库.md)。

> **同样的按需解析还有一处**：`任务引导` 也用 `对话id` 反查"该指谁"（条件=对话 且 `目标npcId` 空时）。
> 两边共用 `DialogueDatabase.取NpcId()`，**别各写一份**。

### 9.5 ⚠️ `演出中` 卡住 = **整条主线静默冻住**

**现象**：等级早就到了炼气三层，阶段28「修炼到炼气三层」**死活不推进** —— 条件本身没问题
（现场手判 `等级 >= 3` 是 `true`），可阶段就是不动。

**根因**：`任务管理器.演出中` 是 **`static`**，由 `播黑幕 / 播对话 / 切到场景` 置**真**、
由黑幕收幕 / 对话演完置**假**。一旦那段演出**被打断**（切场景把协程连带销毁、强制对话
还在等玩家点、对象被销毁…），它就**永远卡在 `true`**。而 `Update()` 里有一句

```csharp
if (演出中) return;      // 有阻塞式演出在跑就先别推进阶段
```

⇒ **所有阶段的 `条件` 都不再判定** ⇒ 表现成"主线不动了"，而且**不报任何错**。

**修法**：主循环里加一次**自愈自检** —— 连续 **1.5 秒**「自称在演出、但**既没有对话也没有黑幕**」
就自动清掉并打一条 Warning（`[任务] 「演出中」卡住了（没有对话也没有黑幕）→ 已自动清掉，恢复阶段判定`）。

为什么是 **1.5 秒**而不是立刻清：`播对话` 会**先**置真、对话框**下一帧**才显示 ——
立刻清会误判成"演完了"，让 `条件=无` 的阶段在过场里偷偷往后推进（那就变成另一种错）。

**还有一个必须知道的行为**：`播放对话` 的台词含 `|` 时是**逐句演出、每句要点一下才往下走**
（`DialogueUI.演出多行`）⇒ **自动化测试会停在那儿等点击**（本次就是这样把 `演出中` 卡住的）。
人玩没问题，**写测试 / 排查时要记得点它**。

> **通用教训**：**一个"锁"只要有"置真"和"置假"两条路，就要防"置假那条没走到"。**
> 静态标志尤其危险 —— 它跨场景存活（`B3` 要求它必须是 `static`），所以**卡住的状态也会跨场景存活**。
> 同类判据：**任何"先拦住一切、事后再放开"的写法，都要有一个"看门狗"兜底，
> 而且看门狗的判据要用"确实还在忙"而不是"自称在忙"。** 原文见 [踩坑总库 B84](../ai/踩坑总库.md)。

### 9.6 剧情 NPC 怎么加（**手搓的 `NpcDefinition` 不在 CSV 里**）

**`NPC表.csv` 不是 NPC 的唯一来源。** 生成资产比 CSV 行数多 ——
`npc_dashixiong`（大师兄）、6 个 `mount_*`（坐骑）、`npc_shifu`（太虚宗掌门/师父）
**都不在 `NPC表.csv` 里**，是**手搓的 `NpcDefinition` 资产**（实测：`Generated/NpcDefinition/`
**252 个** vs CSV **244 行**）。

| 项 | 口径 |
|---|---|
| 加这类 NPC 要不要动 CSV | **不用**。直接在 `Generated/NpcDefinition/` 下建 / 复制一个 `NpcDefinition` 资产 |
| 但它凭什么被运行时认识 | **`NPC库`（`Assets/resources/NPC数据/NPC库.asset`）是"收集"出来的** —— 新资产要跑一次收集才在库里；`任务引导` / `确保对话NPC在场` 取名字都走 `NpcDatabase库.取()` |
| 怎么做最快 | `CopySerialized` 自一个模板 NPC，改 `id` / 名字 / 模型；**别照抄文戏 NPC 的气血** |
| ⚠️ 气血必须改 | 模板文戏 NPC 只有 **1** 点血 ⇒ 会被顺手一发 AOE 打死。师父实测调到 **5000** |

> 原文见 [踩坑总库 A10](../ai/踩坑总库.md)。

**⚠️ 还要给它自己的预制体。**（原文见 [踩坑总库 A9](../ai/踩坑总库.md)）

`生成NPC` 生成的是"**那个预制体**"，而预制体自带它自己的 `NpcInstance.定义`。
借用别人的 prefab ⇒ **带上那个人的身份**（id / 名字 / 好感 / 境界全不对）：

> 实测：想让师父出场，若直接生成 `NPC/Human/YangJian/YangJian_03`，
> 拿到的是一个**境界 83 的战斗 NPC** —— 身份、好感、名字都不对。

两种做法**都行，但要看"基地骨架"**：

| 路线 | 做法 | 什么时候用 | 代价 |
|---|---|---|---|
| **Prefab Variant** | 以某个现成 prefab 为基底，只覆盖 `NpcInstance.定义`（+ 蒙皮网格 / 材质） | 基底骨架**正好合用**时最省事 | **受基底限制**：基底没有的动作你也不会有 |
| **独立 prefab** | 用**自己的 FBX** 重建，逐字段复刻需要的组件/引用 | 基底不合用（骨骼不同、没有你要的动作） | 要自己把该配的都配齐（**最容易漏字段**，见 [踩坑总库 B88](../ai/踩坑总库.md)） |

**基底怎么挑**（实测过两条人形 rig）：

| prefab | rig | 骨骼 | 自带御风状态 |
|---|---|---|---|
| `大师兄.prefab` | 78 骨、首骨 `BoneRoot` | **78** | ✅ `Yufeng_TakeOff / Forward / Idle` 都有 |
| `YangJian_03.prefab` | `Bip01` rig | **43** | ❌ **没有** |

所以"要演御风"就**不能**拿 `YangJian_03` 当基底（动作根本不存在）—— 这也是为什么
**师傅现在走的是独立 prefab**：它要用**自己的 FBX**（`太虚宗掌门（师傅）.fbx`，
81 节点 / 78 骨 / 首骨 `BoneRoot` / Generic / NoAvatar），同时**带上大师兄那套控制器**
（`controller = 大师兄`、`avatar = null`、13 个片段含 4 个御风）。

> **现状**：`Assets/resources/NPC/Human/太虚宗掌门/太虚宗掌门.prefab` **已经是独立 prefab**
> （`PrefabUtility.GetCorrespondingObjectFromSource` → `null` = **不再有基底**）。
> **路径没变**，所以任务表的 `生成NPC`（`动作参数`）与 `npc_shifu`（`动作目标npcId`）**一个字都不用改**
> —— 这也是"换个做法不影响接线"的正确形态。

**实测**（阶段30 师父现身）：

```
[任务] 生成 太虚宗掌门_任务生成 于 (0.00, 0.02, 2.50)
npc_shifu 数量=1  定义=npc_shifu  DisplayName=太虚宗掌门   ✓
```

> ⚠️ 独立 prefab 单独生成后 `CrossFade("Yufeng_Idle")`，`IsName` **仍是 False** ——
> 那**不是回归**，是 §9.7 那条（要被 `飞到` 接管位移才站得住）。

### 9.7 ⚠️ 站着不动的 NPC 播一个姿态，会被**待机行为按回 `idle`**

**现象**：想让师父"常态御风"地站在主角旁边，于是给他派了 `播动画 Yufeng_Idle`。
日志里派发成功、阶段也推进了 —— 但运行时 `Animator` **一直停在 `idle`**、
`IsName("Yufeng_Idle") = False`、**高度一动没动**（看起来像"御风没做"）。

**根因**：**NPC 自己的待机行为每帧在驱动 Animator**（`NpcAiBase` 那套"没在打、没在走 → 播 Idle"），
你在某一帧 CrossFade 过去，下一帧就被它按回来。**裸的 `播动画` 争不过它。**

**修法**：要 NPC 演「常态御风」，**用 `任务动作.飞到`**（见 §5.2）——
那条路由任务管理器**接管位移**（`Yufeng_TakeOff → 前进 → MoveTowards → Yufeng_Idle`），
一个协程把"升空 / 前进 / 悬停"演完，站着不动的待机逻辑抢不过它。
（另一条正路是让 NPC 进入**真正的飞行状态**，那是 AI 层的事，目前没做。）

**实测**（`q_main_004` 阶段31，洞府，玩家 `(0.00,0.02,0.00)`）：

```
[任务] 太虚宗掌门_任务生成 飞向玩家实时位置 (0.00, 0.02, 2.00)
[任务] 调度：太虚宗掌门_任务生成 飞到 (0.00, 0.02, 2.00)
t+0.4s  Animator = idle           （TakeOff 淡入中）
t+1.1s  Animator = ✅Yufeng_Idle   正在播的片段 = 大师兄_御风_Idle   连测 4 次到 t+2.1s + 再等 2 秒都保持
落点    师父 (0.00, 0.02, 2.19) → 玩家身前 2.19 米
```

> ⚠️ **别把"高度没变"当成没飞**：`0.02 → 0.02` 是**对的** —— 御风的"浮空"在**动画姿态**里，
> 不在 `transform` 上（大师兄也一样）。判据要读 **Animator 当前状态名**，不是读 y。

**通用教训**：**"我调了播放接口" ≠ "状态真的切过去了"。**
任何"我让它播 X"的地方，都要**读回当前状态断言**（`Animator.IsName` / 实际片段名），
或者**走那条已经验证过的完整路径**（这里是 `飞到`，而不是自己拼几个 `播动画`）。
同类前科：`B37`（改 `animator.speed` 被 `PlayerAnimationController` 每帧重写）。
