## 5. 第五轮：跨场景接力三条硬伤（用户实测报的）

用户原话：「从宗门通过传送阵传送到个人洞府，背包里的东西全丢了，学会的神通全没了，
也没生成在对应的应该在的落点上」。

**三条根因，都在公共代码里，和"用哪个传送门"无关**（见
[场景一致性与踩坑规律 §7](场景一致性与踩坑规律.md)）：

| # | 根因 | 修法 |
|---|---|---|
| ① | `任务管理器.应用存档()` **每个场景的 Start 都跑**；它内部 `是新档 = 存档全空` → `清空玩法数据()` + `恢复面板()` 无条件重建列表。空存档时每次切场景都把刚接力来的数据清掉 | 加静态 `本局已应用存档`，**只在本局第一次进游戏场景时跑一次** |
| ② | `SaveSystem` 按**存档里的位置**摆玩家，把"目的地落点"覆盖成"上次存档站的地方" | 新增 `跨场景数据.正在接力`，接力期间跳过按存档位置摆放 |
| ③ | `请求落点(位, 0f)` 实际等于"根本不放置"：`Mathf.Max(0.1f, 接管秒)` 把 0 抬成 0.1，而 `处理落点` 又先判"到点放权" | 尊重传入的接管秒；特判"0 秒 = 立刻放置一次" |

**实测**（宗门 → 个人洞府 → 回宗门）：
```
bag=25 passive=1 able=1  player=(-7.96, 0.00, -11.28)   ← 落点精确命中
bag=25 passive=1 able=1  player=(-18.23, -0.02, 27.54)  ← 回程也对
```
（用**真实操作**复的：走进光圈 → 弹面板 → 点按钮。直接调 `执行()` 会绕过触发逻辑。）

### 顺带修掉的

- **传送门没有黑幕+场景名**：`Teleporter` 自己造宿主裸调 `LoadSceneAsync`，
  既没过场、也没钉进度（这是"进宗门剧情重放"的另一半原因）。
  → 全部切场景入口统一走 `黑幕字幕.开始场景过渡()`，过渡新增"按名字解析落点"。
- **3C_Testbed / Sect_Wilderness / 镇妖塔 没有 `任务管理器`** → 传过去进度"没地方放"。
- **落点重名**：`sect1 to 3c` / `sect2 to tower` 既是传送门又是落点名，
  按名字遍历先命中传送门 → 玩家被放到门身上立刻又踩进光圈。
  → `找场景物体` 优先返回**没有 `Teleporter` 组件**的那个。
  （**重名是我造的**：我给落点起了"指向我的那个名字"。用户早就把落点摆好了。）
- **三个传送门只有特效、没挂组件**：`village to sect` / `wild to sect` / `main teleport`。
  → 按用户描述补齐连线（`main teleport` 加组件、选项配 古古镇/宗门野外），
  落点用**场景里本来就有的 `SpawnPoint`**，没新建物体。

## 7. 第七轮：消除两个隐患（用户要求"不影响现在的功能"）

### ① 学习类道具引用：导入时自动回填

隐患：学习类效果身上有一个**直接引用**，物品表只写了 id → 导入后引用为空 →
代码退到 `能力查找.按id&lt;T&gt;()`，而那个函数**整段在 `#if UNITY_EDITOR` 里**、
用 `AssetDatabase`：

- **打包后返回 null ⇒ 点学习道具毫无反应**；
- `AssetDatabase.LoadAssetAtPath` 加载的资产**不会被记进构建**。

实测：23 件物品里 **12 个学习类引用全为 null**。

做法：**不新建机制**，让已有的回填工具在导入后自动跑：

```csharp
// DataTableImporter.ImportAll()，紧挨着 RewirePanelData()
回填效果引用.回填(true);      // 静默模式
```

实测：`[回填效果引用] 查过 15 件、回填 13 件、找不到 0 件` / `引用已填=14 仍为空=0`
（"回填 13 件"是因为**导入会重写资产、把引用清空**，回填紧接着补回来 —— 正说明必须自动化。）

### ② 面板目录：清掉场景里冗余的副本

那些目录已经是**死数据**（运行时必被 `面板库` 覆盖），留着白占体积还容易误导。
新增菜单 `修仙/面板/清掉场景里冗余的目录副本`（**前置检查**：面板库不存在就拒绝执行）。

实测：`清理后 5 个场景目录全 = 0` / `运行时灌回 神通=11 法宝=3 灵阵=5 坐骑=9 真灵=233`

### 顺带

- 补上上一轮漏提交的 `.cs.meta`。
- 把 `Data/Generated/ItemDefinition` **纳入版本管理**（原来整个目录都没跟踪）。

## 8. 主线：大师兄到位 + 境界页功法展示

### 大师兄飞到身边没后续（阶段13 卡死）

三个坑叠在一起：

1. 表里 NPC 只填在「**动作目标npcId**」，而条件的「目标npcId」是空的 →
   `查找在场NPC("")` 拿不到人。→ 条件侧读不到就退回动作侧 id（表里也补了）。
2. 用的是**只读**的 `查找在场NPC`，而任务生成的 NPC **切场景会被销毁** →
   永远等不到人。→ 改用会**重建**的 `找NPC`。
3. **重建点在玩家前方 2 米，而判定阈值是 1.5 米** → 重建了也判不到位。
   → 重建距离取 `min(1.2, 到位判定距离 × 0.8)`，**必须小于阈值并留余量**。

实测：`阶段=14` + `完成「拜入太虚宗」第 13 阶段：大师兄到位` ✓

> 附带教训：我加的兜底提示**写在每帧判定里 → 刷屏几百条**。已改成只报一次。

### 境界页「功法展示」空白

根因：那块是 `UIEntryInfo`，而 `UIEntryInfo.Show()` **只由 `UIEntryList.选中某行()` 调用** ——
它不在任何列表里，`infoTarget` 也没人指向它 → `Show()` 从没被调用过，
**永远显示占位「（未设定当前功法）」**，学没学秘籍都一样。

修：`UIEntryInfo` 加 `显示当前功法` 开关（置真时只认 `data.当前功法` + 订阅 `data.Changed`），
`CharacterPanelBuilder` 接线，**5 个场景面板重建**。

### 新档 `功法id` 清空

`建新档()` 原来写死 `功法id = "gongfa_taixu_lianqi"`，和"已学功法为空"矛盾；
`应用到角色` 里有 `if (功法 != null) 当前功法 = 功法;`，一旦取得到就会让主角**凭空多一门功法**。
→ 改成 `""`。

## 10. 第八轮：体检抓出的第三个真 bug（`跨场景数据` 被 builder 删掉）

**怎么发现的**：整理文档时跑了一次「修仙/体检/场景一致性（只报告）」，结果：

```
项 / 场景	Village	Sect	3C_Testbed	Sect_Wilderness	Tower
任务管理器	1	1	1	1	1
UIPanelData	1	1	1	1	1
跨场景数据	0	0	0	0	0     ← 5 个场景全缺
演出锁	1	1	1	1	1
CameraYawRotator 1	1	1	1	1
共 5 处缺失
```

**根因**：`跨场景数据` 是**跨场景接力的宿主**（靠 `OnDestroy` 在旧场景销毁前把
背包/已学功法/神通拍成静态快照）。它原来靠**手工**挂在 `CharacterUI` 上，
而 `CharacterPanelBuilder` 是「`DestroyImmediate(旧 CharacterUI)` → 重建」的 ——
**我一跑 builder 就把它连旧物件一起删了，而且再也不会有**。

**为什么当时没立刻炸**：`场景自举` 不补它（注释里写明"需要 UI 装配的不补"），
但接力那几天还跑得动，所以没暴露。**一旦有人只重建面板而不记得手工挂，背包就会全丢。**

**修**：
1. `CharacterPanelBuilder` 里 `AddComponent<跨场景数据>()`（和 `UIPanelData` 同物件）——
   它属于面板装配的一部分，必须由 builder 生成，不能靠人记得挂。
2. `场景自举.查装配()`：发现面板上缺这个组件就**明确报错**（说明为什么运行时补不了：
   它需要在旧场景 `OnDestroy` 时就在，新场景 `Awake` 才补已经错过时机），并给出修法。
3. 重跑 builder 修好 5 个场景 → 体检 **0 处缺失**。

**验证**（真实传送 宗门 → 个人洞府）：
```
出发前: bag=23 学会=True
到达后: scene=3C_Testbed bag=22 已学=1 当前功法=青云剑诀 player=(-7.96, 0.00, -11.28)
```
（`bag` 少 1 是因为秘籍被消耗了，正确。）

> **教训**：凡是"销毁重建"式的 builder，都要检查**有没有手工挂的组件会被一起删掉**。
> 跑一次 `修仙/体检/场景一致性` 就能查出来 —— 这个工具本身是第六轮建的，
> 结果第八轮就抓到了自己的 bug。

## 12. 换电脑同步后的一轮：三个 bug（2026-09-28）

用户在另一台电脑上做完大量更新并 push，这台电脑 `git pull` 后（`0154a9a9 → 6b095c93`，10 个提交）
实测报了三个问题。**三个根因彼此无关**，分别记：

### ① 主动技能栏明明是空的，装备神通却提示"栏已满"

**根因**：UI 的"格数"和数据的"列表长度"是两套东西。
- 三个页面各画了 **6 个** `UIActiveSkillSlot`（`ActiveSkillBar.slots.Count == 6`）；
- 而 `UIPanelData.主动技能` 在场景里序列化出来是**空列表（Count = 0）**。

于是 `HasEmptySlot()` 遍历 0 格 → 一个空位都没找到 → 返回 `false`
→ `UIEntryList.OnRowAction` 弹出「主动技能装备栏已经满了」。
画面空、数据也空，但结论是"满了"。

**修**：`UIPanelData.EnsureSkillSlots()`，把 `主动技能` 恒定为 `技能槽位数 = 6` 格（缺的补 null）。
⚠️ 注意**不能**写成 `if (主动技能 == null) 主动技能 = new List<...>()` ——
那正是原来的写法，而场景里存的是**已存在的空 List**，`null` 判断根本不成立。
`EnsureFormationSlots()`（战阵 9 格）早就是这么做的，技能槽漏了而已。

**实测**：`主动技能 Count = 6`、`HasEmptySlot() = True`、`FirstEmptySlot() = 0` ✓

### ② 从宗门传送到古古镇，没落在落点上

**根因**：**传送落点从来没建过**，传送门一直在复用"场景默认点"。
- `Sect/main teleport` 的「前往古古镇」落点字段填的是 `SpawnPoint`；
- 而 village 的 `SpawnPoint` 坐标 `(-18, 0.4, -30)` **恰好就是** `Player` 的场景内初始位置
  （预制体摆的那个默认点）。

于是落点机制**确实执行了**、玩家**确实被摆到了 `SpawnPoint`**，
但那个点和默认点重合 → 看起来像"根本没落点"。

**这里的教训是概念混淆**（三个点必须分清，详见
[踩坑与注意事项 §B7](踩坑与注意事项.md)）：
| 点 | 物体 | 用途 |
|---|---|---|
| 场景默认点 | `Player` 的初始 transform | 直接跑这个场景时的站位 |
| 新存档出生点 | `主角出生点`（小屋前） | **创建新存档**时主角在哪 |
| **传送落点** | 目标场景**自己那道传送门** | **每次从别的地图传送进来**时站哪 |

`SpawnPoint` 是被 `SceneRigSyncer` 当**通用出生点**同步到 5 个场景的（死亡流程也拿它兜底复活），
它压在默认点上是"正常"的 —— **错的是传送落点复用了它**。

**修**：按用户口径，**落点直接用目标场景自己那道传送门的点位**：

| 出发点 | 目标场景 | 落点（改成） |
|---|---|---|
| Sect / `main teleport` | Village | ~~`SpawnPoint`~~ → `village to sect` |
| Sect / `main teleport` | Sect_Wilderness | ~~`SpawnPoint`~~ → `wild to sect` |
| Sect / `sect2 to tower` | Demon-Suppressing Tower | `tower to sect2`（本来就对） |
| Sect / `sect1 to 3c` | 3C_Testbed | `3ctestbed to sect1`（本来就对） |
| village / `village to sect` | Sect | `main teleport`（本来就对） |
| Sect_Wilderness / `wild to sect` | Sect | `main teleport`（本来就对） |
| 3C_Testbed / `3ctestbed to sect1` | Sect | `sect1 to 3c`（本来就对） |
| Demon-Suppressing Tower / `tower to sect2` | Sect | `sect2 to tower`（本来就对） |

**为什么"落在传送门身上"是安全的**（实测）：
7 道门的**脚下都是实心地面**（门 y 与地面差 0~0.24m）、门点胶囊**重叠 0 个**，
所以落上去站得稳。而第 5 轮那条"落在门上会来回弹"的隐患，
在 ③ 改成"按 F 才开面板"之后**已经不存在**了。

**实测**（真实走完整个过场）：玩家落点 `(-20.952, 0.000, -42.800)`，
`village to sect` 门位 `(-20.952, 0.000, -42.800)`，**距离 0.000m** ✓

**顺带加了防线**：`修仙/体检/场景一致性` 新增「传送路线体检」——
逐条检查每个选项的落点物体在目标场景里存不存在。
之前那类 bug 之所以难查，是因为它**不报错**，只是把人放到默认点上。
现在体检输出「共 8 条传送路线，落点全部可解析 ✓」。
（同时也修了体检清单里 `Village.scene` 的大小写 —— 真实文件名是 `village.scene`。）

### ③ 需求变更：传送点改成"靠近提示按 F"，不再走上去自动弹面板

用户要求：「不是走上去就弹出传送面板，而是和 npc 以及建筑一样，靠近后会提示按 F 传送，
按下 F 后才会打开传送的互动面板」。

**做法**：把传送圈接进项目**已有的**那套设施交互（不另起一套）——
- `StationInteractable.StationKind` 新增 `传送`；
- `Teleporter.Awake()` 给自己**运行时补一个** `StationInteractable`
  （类型=传送、按键=F、交互距离 3.5m、提示文字 = 只有一个选项时用选项名）；
  运行时补而不是让美术在 5 个场景各挂一遍 —— 手挂必然漏（这就是"场景一致性"那类 bug 的成因）。
- `StationInteractor.打开界面` 加「传送」分支：**只负责"按 F 这一下"**，
  面板仍由 `Teleporter` 自己画（它要按选项数量动态生成按钮，占位幕布满足不了）；
- `StationInteractor.关闭界面` 对应加分支：传送面板**不能 `Destroy`**
  （不是它造的），只能让 `Teleporter` 自己收起来，否则下次再按 F 时引用已销毁。
- 删掉 `OnTriggerEnter/OnTriggerExit` 自动开关面板（连同只为此存在的 `冷却` 字段）。

**实测**：站在传送门上等 90 帧**不会自动弹面板** ✓；按 F 开 → 同一个面板实例复用（instanceID 不变）→ 关 → 再开正常 ✓

也没有做离开传送阵自动退出传送面板」。

**ESC 的病根不在 ESC 上，而在"界面开着的标记"被清掉了**：

`StationInteractor.Update` 里有一行自愈
`if (有界面打开 && 当前界面 == null) 有界面打开 = false;`（"界面物件没了就把标记收回"）。
传送面板是 `Teleporter` 自己造的，我上一轮**没把面板根交给 `StationInteractor`**
→ 下一帧自愈把 `有界面打开` 清成 false
→ 而"要不要处理关闭"的开关是 `界面已打开 => 当前界面 != null`（也是 false）
→ `if (界面已打开) { if (Input.GetKeyDown(关闭键)) 关闭界面(); }` **这一行永远走不到**。

**诊断探针抓到的证据**（逐帧打两个状态）：
```
① 打开后 立即     → 面板已开=True  界面已打开=True   有界面打开=True   当前界面=传送面板
   等30帧后      → 面板已开=True  界面已打开=False  有界面打开=False  当前界面=null   ✗
② 走到 25m 外    → 面板已开=True                                              ✗ 不关
```

**修两处**：
1. `Teleporter` 暴露 `面板根`，开面板时写进 `StationInteractor.当前界面`
   → 标记不再被清 → ESC 恢复（`Input.GetKeyDown(关闭键)` 那条路走得到）。
2. `StationInteractor.Update` 的"界面已打开"分支新增
   `if (当前设施 != null && !在范围内(当前设施)) 关闭界面();`
   → 走出交互范围自动关。距离判定抽成 `在范围内(设施)`，
   **`找最近设施` 和它共用同一处判定**，不会出现"提示没了但界面还开着"。

**实测**（同一个探针，修完后）：
```
① 等30帧后 → 界面已打开=True   当前界面=传送面板     ✅ ESC 那条路通
② 走到 25m 外 → 面板已开=False  界面已打开=False      ✅ 走远自动关
③ 回门口再开  → 面板已开=True                        ✅ 引用没被销毁
```

### ① 树冠挡住相机就自动隐形

**关键发现：工程里本来就有 `OcclusionTransparency`**（挂在 5 个场景的主相机上，

**修**：给树冠单开一条**包围盒相交**通路（不依赖碰撞体）：
- 按物件名认树（树根+子件都以 `environment_Tree` 开头，实测 **9 个品种**）；
- 只在**相机视锥里**的树参与测试（`CalculateFrustumPlanes` + `TestPlanesAABB`）；
- 「线段 vs AABB」用 slab 法（`线段近包围盒()`），比 `Physics.Linecast` 便宜且不需要碰撞体；
- 树表 **5 秒重建**一次，不是每帧遍历全场景。

**材质**抽成 `遮挡素材.cs` 共用（建筑和树冠走同一套）：
**绝不改 `sharedMaterial` 指向的材质本身** —— 树冠材质是**多棵树共用**的，

### 17.1 顺手查清的两个技术点（都写进 `guides/特效系统.md`）

**① 本工程的 Resources 根是小写的 `Assets/resources`** ——
`Assets/Resources` 与它其实是**同一个目录**（Windows 大小写不敏感，`git ls-files`
只跟踪小写那个）。所以特效包**自带的 `resources/` 子目录是正常的普通目录**，
不是第二个 Resources 根，按路径照常取得到。
（我一开始被"两个都 test-path 为真"误导，差点当成符号链接，用 .NET 精确列目录才查清。）

**② 示例场景/脚本别跟着资源进 `resources/`** ——
`resources/` 下的东西**会进平台构建**。而 `Combat Magic VFX Vol.1` 的 `demo.cs` 里有：
```csharp
effectObjects = Resources.LoadAll<GameObject>("");   // 空路径 = 整个工程 Resources 全扫
```

实测这个调用现在会扫到 **2670 个 GameObject**（含 261 个 NPC + 环境）并逐个 `Instantiate`。
所以把 `Demo/` 场景 + `scripts/` 搬到了 **`Assets/Scripts/Demo/CombatMagic/`**
（那里不进平台构建，但留在工程里随时能看效果）。
`UnionAssetes` 的 `ParticleScale.cs` + `ParticleScaleEditor.cs` 是包的一部分（缩放工具），不搬。

> 另：`ParticleScale.cs` 里第 15/19 行写的是 `particle` 而字段叫 `_particle`，
> 我一度以为要编译不过——实际 `particle` 是个**属性 getter**（懒取 `GetComponent<ParticleSystem>()`），
> 没问题。**先看全文再下结论**，别被局部 grep 骗了。

**`ground-flashes` 根本拉不成链条**，要求"把它的资产抽出来，自己想办法做个能实现的特效"。

### 19.2 为什么拉不成（查出来的真因）
| 现象 | 真因 |
|---|---|
| 横向爆到 10.4m、且**随镜头角度变** | `renderMode = Stretch` 是沿**粒子速度**拉的，而这些发射体 `startSpeed ≈ 0`，方向退化；`alignment = View` 在 Stretch 下不起作用 |
| `ground-flashes` 拉不长 | 它的 `lengthScale = 5 / velocityScale = 6`，另外它还开着 **Lights 模块**，是唯一会横向爆的部件 |
| `Resources.Load` 取不到 `ground-flashes` | 它**不是独立资源**，是 `ground-dust` 下的一个子节点 |

于是把那棵子树的 4 个粒子部件（`ground-flashes` / `lightning-ray` / `lightning-glow` /
`ground-arcs`）抽出来挂到一个新根上，做成 `lightning-fx/雷链.prefab`。

### 19.3 定下来的做法
- 发射体：`Box scale = (0.06, 0.06, 1)`（**Z 最长** → `探测长度轴` 自动选到 Z）
- `scalingMode = **Hierarchy**`
- `renderMode = **Billboard**` + `alignment = View`
- 每颗粒子**随机 `startRotation`**（这张贴图是有方向的"闪电条"，同向会排成梳齿）
- 粒子原地不动（`velocityOverLifetime` 关）
- **基准长度 = 1、长度补偿 = 0**

### 19.4 ⚠️ 中途走了大弯路：用户反馈"完全没看到"之后才查出的真因
第一版我按"Shape 只缩放发射体 + Stretch 沿速度拉伸"的思路做完，还用
`renderer.bounds` 量出一张自洽的表（间距 3/8/15m → 链长 3.00/8.00/15.00m）就宣布通过。
**用户反馈"这个闪电链我完全没看到"** —— 回头用 `GetParticles()` 复查，粒子在链轴上
**只铺开 0.26m**，链根本就是一坨。`bounds` 是**虚胖**的，我被它骗了整整一轮。

三条真因（已写进 [踩坑 B26–B32](../ai/踩坑与注意事项.md)）：
1. **`renderMode = Stretch` 会让链几乎完全看不见**（速度≈0 时拉伸方向退化）。
   同一时刻同一机位对比：`Stretch` 全黑 / `Billboard` 一条明亮锯齿雷电。
2. **`scalingMode = Shape` 会把 `localScale` 作用两次**：`localScale.z = 3.42` 时
   铺开 **11.7m**（≈3.42²）而不是 3.42m → 链被拉稀。`Hierarchy` 才是线性的（3.39m ✓）。
   **这和我原先记的正好相反**，旧记录是基于 `bounds` 的错误读数。
3. **量尺寸必须用 `GetParticles()`**，而且要记得 `simulationSpace = Local` 时
   `position` 是本地坐标、要先 `TransformPoint` 转世界（我在这儿又错了一次）。

另外还踩了：**Play Mode 被用户暂停时，带 `yield` 的探针会一直挂到超时**
（暂停时 `Destroy(go, 秒)` 也不推进，所以临时特效会一直挂在 Hierarchy 里，
用户会选中它 —— `selection.activeObject` 就是 `雷云闪电_Player`，这条线索帮了大忙）。

|---|---|---|
| 2.15m（玄霄雷决两木桩） | 2.14m | −0.01m |
| 3m | 2.99m | −0.01m |

### 19.6 视觉复核（两条重要经验）
1. Edit 截图 / Game View MP4 **都拍不到粒子**。可靠办法是

3. 想看细节要**另起一台特写相机**（`CopyFrom(主相机)` + `clearFlags = SolidColor`），

### 23.3 ⚠️ 我在这里连错两次，还把特效改坏了（用户当场发现）
**用户反馈**：「lightning-sphere 是一个闪电雷球，但是你这里完全是静止的，
并且受击特效 lightning-explode 也是」。**完全正确。**

**错误链**：
1. 我把测试实例生成在 `(400,20,400)`（**相机视锥外**），量 `GetParticles` 恒为 **0 颗**，
   于是判断"这个常驻光球特效来不及长起来"。
   **真相**：特效 `cullingMode = PauseAndCatchup` —— 被剔除的粒子系统**停止模拟**。
   同一 prefab 放相机里正常生长（2→9→13→18 颗）；用户在场景手放的原版实例有 12/12/35/2 颗。
   **特效从来就是好的。**
2. 基于假结论加了"预热" `ParticleSystem.Simulate(0.4f)` ——
   它会把系统**暂停**（`isPlaying=False, isPaused=True`），
   于是闪电球和命中爆炸都变成**一帧静止画面**。

**改法**：把预热**整段删掉**，回到最朴素的实现 ——
`Instantiate(lightning-sphere)` 放在**主角 R_Hand 骨骼**上 → 飞向锁定目标 →
命中时 `Instantiate(lightning-explode)` 放在**锁定目标身上**。不预热、不缩放。

实测：球离手 **0.011m**、`isPaused=False`、爆炸落在目标身上、
出弹时动作进度 **0.400**、伤害 171.99、充能 3→2。

教训写进 [踩坑 B35/B36](../ai/踩坑与注意事项.md)：
**探针物件必须在相机视野内**；**`Simulate()` 会暂停系统，不能拿来预热**。

### 23.3b 用户给的正确做法：到节点**停 1.5 秒**让球长出来（已实现）
> 「当动画播到球生成的时候时，会停止 1.5 秒，直到让球的粒子基本长出来，
> 然后再继续播，球再飞出去」

两段式实现：
```
动作播到 40% → ① 球生成在主角 R_Hand 骨骼上（先不飞）+ 动画定住（animator.speed = 0）1.5s
             → ② 动画放开继续播 + 球放飞（追踪）
             → 命中：目标身上生成 lightning-explode + 结算
```
为了让"定住"生效，给 `PlayerAnimationController` 加了正式接口
**`定住动作(bool)` / `动作已定住`** —— 它的 Update 每帧重写 `animator.speed`
（且 `Mathf.Max(0.01f, …)` 不允许 0），外面直接改没用（踩坑 **B37**）；
`停止动作()` 和 runner 的 `收尾()/OnDestroy()` 都会放开，避免人僵住。

**实测**：
```
t=0.69s 进度=0.407 speed=0.00 定住中=True  球粒子 0
t=1.19s 进度=0.407 speed=0.00 定住中=True  球粒子 25
```

### 28.5 修「冰刺忽然消失」：存活改成按 prefab 自然时长自动算（2026-09-29 用户报）

用户报：「冰刺特效消失得很突兀，原版好像是慢慢消失的」。
**根因**：我把 `冰刺特效存活` 写死成 **1.2 秒**，而 `frost-shock` 的自然总时长是 **9.1 秒**：

| 粒子系统 | duration | startLifetime | 单个总时长 |
|---|---|---|---|
| `spikes-main` / `spikes-second` | 0.10 | **0.00~9.00** | **9.10** |
| `flash` | 0.10 | 2.00~3.00 | 3.10 |
| `rays-*` | 0.10 | 1.50~2.00 | 2.10 |
| 其余（whirls / shockwave / sparks） | — | — | 0.6~1.7 |

→ `spikes-*` 的粒子寿命是 **0~9 秒随机**，原版就是**慢慢融化**；写死 1.2 秒 = 硬切掉后面 7.9 秒。

**修法**：`特效摆放.量特效总时长()`（所有系统 `startDelay + duration + startLifetime(最大)` 取最大，各自 ÷ `simulationSpeed`）；
`BasicFrostSpike01` 新增 `存活按特效自动`（默认 true）/ `存活倍率`（1.05）/ `存活上限`（0 = 不封顶），
`冰刺特效存活` 降级成**兜底值**。

**实测淡出曲线**（单发，每秒采一次存活粒子）：
`520(t=1s) → 191 → 95 → 91(t=4~8s，视觉上已看不见) → 73 → 0(t=10s)`；日志打「特效存活 **9.56s**」= 9.1×1.05 ✓。
（拍图确认 t≈5s 时地上已经看不到冰了 —— 可见的淡出在 ~3 秒内自然完成。）

> 教训：**特效存活别写死秒数**。资源包的粒子寿命常带"长尾"（这里 0~9 秒随机），
> 写短了就是硬切，表现就是"忽然消失"。用 `量特效总时长()` 自动算，需要时再用 `存活上限` 收。

## 38. 修「近战 AI 被挡住就呆在原地 / 一波怪排队不打」（2026-09-29 用户报）

### 38.1 先复现，再动手
8 只寒狼间隔 1.2 米排成一列冲过来（22 秒，玩家冻结）：


### 38.2 根因不是一个，是**四个叠在一起**
| # | 根因 | 现象 | 修法 |
|---|---|---|---|
| 1 | 移动是"直线走 + 前方探障"，**被挡就 `停止移动动画(); return;`** | 后面的怪原地不动 | **侧偏绕行**：±25/50/75/100° 依次试，第一个能走的方向就用；偏好边按 `InstanceID` 奇偶分（免得全往一边挤），选定后 0.6 秒不改边 |
| 2 | **探障把"玩家本人"当障碍** | 寒狼射程 1.3，却停在 **1.69 米** 永远够不到 | 探障**排除当前锁定目标**（怪被"要打的那个人"挡住是荒谬的） |
| 3 | `SphereCast` **起始球压着同伴**时，所有方向都返回 `distance=0` 的命中 | "八个方向全被挡" → 一步不动（寒狼胶囊 **2.58 米宽** > 1.2 米间距，排一列本来就重叠） | 跳过 `distance ≈ 0` 的命中：那是"已经挤着了"，不是"前面有障碍" |
| 4 | 所有怪都瞄敌人脚下**同一个点** | 谁先到谁占住，后面排到天边（=用户说的"排队"） | **接近点改成"自己这一侧的环"**：目标点 = 敌人 + (反方向) × 攻击距离 × 0.8 |

### 38.3 修完还有"叠在一起"——再加两条
- **同伴分离** `算分离()`：`OverlapSphere` 找 2.5 米内的同类（只推怪，不推玩家/建筑），越近推得越狠。
