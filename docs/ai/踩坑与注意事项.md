# 踩坑与注意事项

> **改代码前先扫一遍这份。** 全部是实际踩过的，每条都写了症状 → 真因 → 做法。
> 相关：[ai/工程与工具链](工程与工具链.md) · [reference/配置表字段](../reference/配置表字段.md)

---

## A. 配置表 / 导入器

### A1. 改了表但游戏里没变化
**真因**：游戏读的永远是 `Assets/Data/Generated` 下的**资产**，不是 CSV。
**做法**：改完表跑 `修仙/从配置表生成资产`。
复查用 `修仙/检查配置表是否已同步`（只读，会告诉你哪张表的 CSV 比资产新）。

### A2. 导入器**现在空值也会写**了（2026-09-27 改）
**背景**：原来 `ApplyRow` 只在非空时写字段（`if (!string.IsNullOrEmpty(val)) SetFieldValue(...)`），
于是**清空一个单元格不会撤回资产里的旧值**。

**实测症状**：`q_main_003` 第 1 阶段的 `等待秒` 早就从表里删掉了，资产里却还留着 `3` ——
表现成「进触发区后要干等 3 秒才生成野猪」，查了半天以为是逻辑问题。
（同样地，很多阶段残留着 `动作速度 3.5`、`到达半径 5`、`说话人 主角` 这些表里根本没有的值。）

**现在**：空值也写入（string→`""`、数值→`0`、bool→`false`、枚举→`0`、Vector3→`zero`），
**配置表成为真正的唯一真相源**。

> ⚠️ 策划改表时**不要留空想表达"沿用上次"** —— 没有那个语义了，留空就是清零。
> ⚠️ 只有「属性列」保持"空 = 不设该属性"（`AttributeSet` 会先 `Clear`，语义正确）。
> ⚠️ 让字段清零**不再需要**"删资产重导"，第 A3 条那个坑随之作废（但已存在的残留仍要靠重导清掉一次）。
>
> **边界（目前没有受影响的字段，但加新列时要记住）**：空值写入走的默认值对少数类型是"非零但不可用"——
> 例如 `Color` 会变成 `(0,0,0,0)`（**全透明**，表现成"看不见"）。
> 现在 `Data/` 下的 `ScriptableObject` 没有 `Color` 字段，所以没实际踩到；
> 以后要给表加 `Color` 列的话，得在 `SetFieldValue` 里单独给个合理默认值。

### A3. 曾经的坑：导入器不清空空单元格 → 删资产重导（**已被 A2 修复**）
历史做法：改了某行、让字段变空时，要先删掉生成资产再重导。
**现在不需要了**，因为空值会直接写入。保留此条只为了解释"为什么老资产里有残留值"。

### A3. 删完资产要**导两次** ⚠️
**真因**：删完立刻导，`AssetDatabase` 还没注册完删除，导入器会写出一批**空壳资产** ——
`任务id` / `阶段名` / `条件` 全空，只有 `阶段` 有值，**文件明显变小**（1518 → 1332 字节）。
**做法**：删完 → `refresh` → 跑一次导入 → **再跑一次导入**。
或者干脆用菜单重导两次，然后用 `stages:<任务id>` / 直接看资产文件复查。

### A4. CSV 表头必须在第一行
**真因**：导入器按第一行做列名映射。
**做法**：往文件开头插数据行时，**务必插在表头之后**。
（踩过：插了两行对话到开头，表头被挤到第 3 行，整张对话表读不出来。）

### A5. 小数会被截断 → 阶段/分段撞号 ⚠️
**真因**：`阶段`、`分段` 是 `int` 字段，CSV 里写 `11.5` 会变成 `11`。
**后果**：和原有 `11` 行**撞号**，`取阶段(任务id, 阶段)` 只返回其中一条，另一条永远读不到。
**做法**：想在某个阶段前插一行，**必须整数重编号**（把后面的全部 +1），不能用小数插队。

### A6. Unity 把中文写成 `\uXXXX` 转义
**真因**：`.scene` / `.asset` 里的中文字段名和字符串都是转义形式。
**做法**：**不要拿中文字面量去 grep** `.scene` / `.asset`（会假阴性）。
认物件要用**预制体来源**：`PrefabUtility.GetCorrespondingObjectFromSource(go) == 预制体资产`。
要读字段名就按 `\uXXXX` 形式搜（例如 `"\u7269\u54C1id"` 是「物品id」）。

## B. 跨场景与协程（**本项目 bug 的重灾区**）

### B1. 协程会随对象销毁而消失 —— 一切跨场景问题的根
**症状**：协程入口日志打了，**协程体内一条日志都没有**。
**真因**：`StartCoroutine` 挂在 MonoBehaviour 上；切场景销毁旧场景 → 协程直接没了。
**做法**：**任何可能跨 `LoadSceneAsync` 的长过程都不要用协程**，
改成**静态状态 + 活着的对象在 `Update` 里驱动**。

实际踩过的四个：

| 症状 | 被打断的协程 | 现在的做法 |
|---|---|---|
| 主角落点不生效（停在场景初始摆放处） | `移动玩家到` | 静态 `请求落点()` + `Update` 处理 |
| 黑幕起了不解除（一直黑） | `播黑幕` | 黑幕**自己**按「字打完 + 停留」收幕 |
| 黑幕整段被漏掉 | `播黑幕`（死在 `WaitForSeconds`） | 先落黑幕 + 开始打字，再等待 |
| 大师兄不见了 / 不飞过来 | 任务生成的 NPC 被场景销毁 | `找NPC` 找不到就**就地重建** |

### B2. 进度接力曾经是竞态
**真因**：`跨场景数据.OnDestroy` 里 `FindObjectOfType<任务管理器>()` 导出进度，
而 `LoadSceneAsync` 完成那一瞬**新旧场景短暂共存** → 可能抓到即将销毁的旧管理器，
导出残缺甚至空串。
**做法**：**切场景之前**就 `跨场景数据.钉住任务进度(导出进度())`，不依赖 OnDestroy。

### B3. `演出中` 必须是 `static`
**真因**：黑幕是 `DontDestroyOnLoad` 的（跨场景），而任务管理器随场景重建。
如果 `演出中` 是实例字段，切场景后新管理器读到 `false`，**黑幕还盖着阶段就自己推进了**。

### B4. 重复派发：三条路径碰同一阶段
**真因**：切场景那一帧，`进入阶段()`、`导入进度` 的待发动作队列、跨场景静态队列
**都会碰同一个阶段**。「生成NPC」因此跑两遍，后一个顶掉前一个 → 对话不出现。
**做法**：静态 `已执行动作`（`任务id#阶段`），在 `执行动作` **入口**登记，队列派发前先查。

> ⚠️ **别拿 `阶段开始时间` 当去重判据** —— `导入进度` 会给所有接手阶段写那个时间戳
> （「等待秒数」计时要用），于是本该补发的动作全被跳过、**主线直接卡死**。
> 两份语义必须分开。

### B5. 等待秒数会因切场景清零
**症状**：「等候大师兄禀报」等 60 秒，玩家在等待期间穿传送门 → 计时从头开始 →
看起来像"剧情卡住"。
**真因**：`导入进度` 把 `阶段开始时间` 重置成当前时间。
**做法**：切场景前记下未走完的**剩余秒**，新场景导入时把开始时间往前挪。

### B7. 「场景默认点 / 新存档出生点 / 传送落点」是三个不同的东西 ⚠️
**症状**（2026-09-28 用户报）：从宗门传送到古古镇，**没落在落点上**，落在"默认位置"。

**真因**：传送落点字段复用了 `SpawnPoint`，而 village 的 `SpawnPoint` 坐标**恰好等于**
`Player` 的场景内初始位置 —— 机制跑了、也确实摆到了 `SpawnPoint`，但它就是默认点。

三个点必须分清：

| 点 | 物体 | 什么时候生效 |
|---|---|---|
| **场景默认点** | `Player` 的初始 transform（预制体摆的） | 直接运行这个场景时的站位 |
| **新存档出生点** | `主角出生点`（小屋前，`主线开场` 用） | **创建新存档**开局时 |
| **传送落点** | 目标场景**自己那道传送门** | **每次从别的地图传送进来**时 |

`SpawnPoint` 是被 `SceneRigSyncer` 当**通用出生点**同步到 5 个场景的
（`PlayerDeathSequence` 也拿它兜底复活），它压在默认点上是"正常"的。
**错的是拿它当传送落点。**

**做法**：传送落点直接用**目标场景自己那道传送门**的点位（门脚下都是实心地面，实测站得稳）。
判断一条路线对不对：**落点名必须是目标场景里真实存在的物体名**。

> ⚠️ 这一类 bug **不报错**：`找场景物体` 返回 null 之后只是"不摆位"，
> 表现成"传送过去了但站的地方不对"，极难发现。
> 所以 `修仙/体检/场景一致性` 里加了「传送路线体检」，逐条核对落点能否解析。

### B8. "落在传送门上会来回弹" —— 已随交互方式变更而消失
第 5 轮为防"落点压在传送圈里 → 立刻再次触发 → 来回弹"，
给落点起了跟传送门**不同**的名字，并让 `找场景物体` 优先跳过带 `Teleporter` 的物体。

2026-09-28 传送改成「靠近提示按 F、按 F 才开面板」之后，
**落在门上不会自己弹面板**了，所以"落点就用传送门自己"是安全的。
`找场景物体` 那个筛选**保留**（无害的兜底），但**不再是必须的**。

### B9. 界面"开着的标记"被自愈逻辑清掉 → ESC 关不掉 ⚠️
**症状**（2026-09-28 用户报）：按 F 能唤出传送面板，但**按 ESC 关不掉**；
同时"走出传送阵也不会自动关"。

**真因**：`StationInteractor.Update` 里有一行自愈
`if (有界面打开 && 当前界面 == null) 有界面打开 = false;`（意思是"界面物件没了就把标记收回"）。
传送面板是 `Teleporter` 自己造的，开面板时**没把面板根交给 `StationInteractor`**
→ 下一帧自愈逻辑把 `有界面打开` 清成 false，
而"要不要处理关闭"的开关是 `界面已打开 => 当前界面 != null`（也是 false）
→ `if (界面已打开) { if (Input.GetKeyDown(关闭键)) 关闭界面(); }` **根本走不到**。

**实测证据**（诊断探针）：
```
① 打开后 立即    → 面板已开=True  界面已打开=True   有界面打开=True   当前界面=传送面板
   等30帧后      → 面板已开=True  界面已打开=False  有界面打开=False  当前界面=null   ✗
```

**修**：`Teleporter` 暴露 `面板根`，开面板时写进 `StationInteractor.当前界面`。

**规矩**：**任何**界面在打开时都必须把根物件写进 `当前界面`，哪怕是别人造的。
"走出范围自动关"也是同一个开关（`当前设施` + 在不在范围内）。

> 教训：**"标记"和"真值"两套状态并存时，必然有一个自愈逻辑会咬人。**
> 调试这类问题的办法就是**逐帧把两个状态打出来看第几帧开始不一致** ——
> 光看代码很难发现（这次就是靠探针在第 20 帧抓到 `有界面打开` 已经变 false）。

### B10. 改代码里的"默认值"对**已有场景里的组件**无效 ⚠️
**症状**（2026-09-28）：把 `StationInteractor.交互键` 的默认值从 `Mouse1` 改成 `F`，
代码也编译过了，但游戏里建筑**还是右键才能交互**。

**真因**：`交互键` 是 `public` 字段，**值已经序列化进场景文件**了
（`Player` 上那份 `StationInteractor` 存的是 `Mouse1`）。
改代码里的初始化值只影响**新加的组件**，已存在的实例读的是场景里存的值。

**规矩**：只要是 `public` 字段的默认值变更，**必须同时把已存在的场景/预制体实例也改一遍**。
本次做法：写个编辑器脚本遍历 5 个场景，把 `Player` 上组件的 `交互键` 逐个改成 `F` 并 `SaveScene`。
（同理适用于 `提示最高点`、`交互距离` 这类新增字段——但**新增**字段用默认值没问题，
因为旧场景里没有那个键，反序列化时直接取类型的默认值 ✓）

### B11. 树冠没有碰撞体 → 射线类遮挡判定**永远打不到树冠**
**症状**（2026-09-28 用户报）：树冠挡在摄像机和角色中间时不会变透明。

**真因**：工程里本来就有 `OcclusionTransparency`（相机→主角连线上变透明），
但它是**打射线看命中**的，而**树冠一个碰撞体都没有**
（实测 village：树干 153 个 `CapsuleCollider`，树冠 365 个子渲染体 **0 个**）。

**修**：给树冠单开一条**包围盒相交**的通路（不依赖碰撞体），
先按相机视锥剔除，再做「线段 vs AABB」的 slab 测试。详见 [design/遮挡透视](../design/遮挡透视.md)。

> 教训：**"碰撞体"和"看得见"是两码事。**
> 凡是靠 `Physics.Raycast` 找"视觉遮挡物"的功能，都要先问一句
> **"这些东西有碰撞体吗？"** —— 环境美术资产经常只有部分部件带碰撞体。

### B12. 鼠标索敌曾经**完全不受神识范围约束** ⚠️
**症状**（2026-09-28）：策划以为「右键索敌本来就是只能锁定神识范围以内的」。

**真因**：`NpcTargeting.RaycastNpc()` 只判 `最远距离`（默认 **200 米**），
神识范围一次都没参与判定。

**实测证据**（修改前）：神识 12.5 → 神识范围 14 米；把练功木桩搬到 **30 米**外
（射线距离 39.5 米）→ `Physics.Raycast` 命中、`Lock()` 成功。
**这不是"设计如此"，是漏判。**

**修**：限制加在**唯一的鼠标输入入口** `NpcTargeting`（左键选中 + 右键锁定一起管），
而不是加在各武器脚本里 —— 否则每把武器一套口径，加第 5、6 把必然不一致。
`Lock()` / `Select()` 这两个**代码接口不做限制**（自动索敌、剧情脚本要走）。

**附带的两个坑**：
1. **距离要量"体表最近点"**（`Collider.ClosestPoint(玩家位)` 取最小），
   不能用鼠标射线的碰撞点（那点朝向镜头，会低估距离），
   也不能用 `transform.position`（大体积目标中心很远但身体已经贴脸）。
2. **够不着 ≠ 右键点空地**：超范围时**不能顺手清掉已有锁定**，只提示。

### B13. 自动化里验证鼠标射线：`Input.mousePosition` 可能在**窗口外**
**症状**：用 `exec_runtime_script` 写探针验证索敌/拾取，`RaycastNpc()` 一直返回 null，
看着像功能坏了。

**真因**：Editor 里 `Input.mousePosition` 是**光标相对 Game 视图**的坐标，
自动化跑的时候光标可能根本不在 Game 视图上（实测拿到 `(-2084, -1019)`，**负值**）。
`Camera.ScreenPointToRay` **不会**把越界坐标钳到屏幕内 —— 它照样按那个方向射线，
于是射线指向了完全无关的地方（实测与相机视线夹角 **66.55°**）。

**教训**：这类探针不能假设鼠标准星可控。要么用 `ScreenPointToRay(屏幕内坐标)`，
要么直接构造世界射线；**且必须打印"射线实际命中了什么"**，
否则一堵墙（实测 `WallSeg_17`）就会让结论变成假阴性。

### B14. 脚本里搬 Transform 后，物理查询可能读到旧位置
**症状**：探针里 `木桩.transform.position = 新位置;` 之后立刻 `Physics.Raycast`，
打不中；加 `Physics.SyncTransforms()` 就中了。

**修**：脚本里改完 Transform 又要马上做物理查询时，先调 `Physics.SyncTransforms()`。
（`Collider.Raycast` 反而"看起来"正常，容易误判成"层掩码有问题"而走错方向。）

### B15. 特效 prefab 的**部件排列轴**决定了它必须怎么旋转 ⚠️
**症状**（2026-09-28 用户报）：*「整个特效零件散了一样，原版是一个劈下来的雷才对」*。

**真因**：`Electro_Strike_01` 的 12 个部件**全部沿本地 +Z 轴**排开（z 从 0 到 1.42），
这道雷是**朝 +Z 劈出去**的。代码用 `Quaternion.identity` 生成 → 雷横躺着，
看上去就是"零件散开 + 偏到一边"。

**怎么量出来的**（不靠猜）：把 prefab 用几个不同旋转各实例化一份，
等粒子发射出来后读 **`ParticleSystemRenderer.bounds`** 合并包围盒：

| 旋转 | 相对锚点竖直范围 | 水平偏移 |
|---|---|---|
| `identity` | −2.14 ~ +2.14 | **1.30m** ← 就是 bug 的样子 |
| `270,0,0` | −1.62 ~ +4.19 | 0.00 ← 对 |
| `90,0,0` | −4.19 ~ +1.59 | 0.00 ← 朝下劈进地里 |

**规矩**：
1. **资源包的示例场景就是权威答案** —— 去读它里面那个物件的 `rot`。
   （`Electro_Strike_01` 示例里是 `(90,180,0)`、`Electro_Lightning_01/02` 是 `(270,0,0)`，
   实测等价于 `270,0,0`。）
2. 实例化特效时**不要默认 `Quaternion.identity`**，先确认它的朝向约定。
3. `ParticleSystemRenderer.bounds` 是**运行时**才有的真实包围盒 ——
   这是量"特效实际在哪、朝哪"的可靠手段。

### B16. 给"空中单位"做位移时，别无条件贴地
**症状**：雷动千闪在御风 / 骑乘时用，会**掉到地上再飞起来**。

**真因**：落点计算无条件 `目标.y = 地面.y + 0.05`，
而 `PlayerController` 的飞行 / 骑乘高度是**比例控制回拉**
（`verticalVelocity = (目标Y - y) × 8`）—— 把它按下去，它就把人拉回来。

**规矩**：任何"位移 / 传送 / 落点"逻辑，只要可能发生在**御风或骑乘状态**下，
都要先问一句"这人现在是不是在空中"，是的话**保持当前高度**，只做水平位移。

### B17. 探地形要**从高处往下打**，别从脚边往下打
**症状**：想判断"落点下方有没有更高的地形"，从「玩家高度 +1」往下射线 ——
落点处若有一堵比自己高的墙，**永远探不到**。

**真因**：起点落在**墙内部**了，而 Physics 默认**不命中背面**
（`Physics.queriesHitBackfaces = false`），射线穿过去只打到地面。

**实测**（`WallSeg_17`，box 高 4m）：

```
起点 y=10.0 → WallSeg_17  命中点 y=4.00   ✓
起点 y=4.5  → WallSeg_17  命中点 y=4.00   ✓
起点 y=3.0  → Ground      命中点 y=0.00   ✗ 穿过墙了
起点 y=1.2  → Ground      命中点 y=0.00   ✗
```

**修**：统一从 `落点 + 30m` 往下打 80m。另外 `RaycastAll` **不保证有序**，
要"最高的那个面"必须遍历，不能 `break`。

### B18. 自动化验证时：`DestroyImmediate` 会污染后续探测 ⚠️
**症状**：一次探针里 `DestroyImmediate(组件)` 之后，**下一个探针**里
`GetComponent<那个组件>()` 仍然返回一个非 null 的**已销毁**实例，
于是 `在空中()` 这类判定静默失效、结论全错。

**真因**：Unity 的 `==` 对已销毁对象有特殊语义，但 `GetComponent` 在
同一帧内可能仍返回那个"待销毁"的引用；跨探针残留更难查。

**规矩**：
- 探针之间**不要用 `DestroyImmediate` 改场景结构**；要干净状态就
  `EditorSceneManager.OpenScene(..., Single)` **重载场景**。
- 玩家身上可能**已有**同名组件（`PlayerAbilityLoader` 运行时装的）。
  `AddComponent` 会造出**第二个**，而 `GetComponent` 只会拿到**第一个** ——
  测试要改就改 `GetComponent` 拿到的那个，别改自己刚加的。
  实测：玩家上曾同时存在 **2 个 `YufengFlight`**，改错实例导致"修复没生效"的假结论。
- 这类探针**必须打印"我改的是哪个实例 id"**，否则很容易验错对象。

### B19. `scalingMode` 不是 `Hierarchy/Uniform` 时，缩放**只拉开部件间距、不放大粒子** ⚠️
**症状**（2026-09-28 用户报）：*「我缩放了特效的预制体它只是部件间的距离变大了，特效没变大」*。

**真因**：`Electro_Strike_01` 的 12 个部件全是 `main.scalingMode = Shape`。
`Shape` 模式下 transform 的 scale **只作用于粒子的发射形状**，
所以只会把子部件之间的间距拉开，**单粒子尺寸完全不变**。

**实测**（`p2_glow_01` 的世界高度，同一 prefab 不同 localScale）：

```
scalingMode = Shape      localScale 1 → 3.56 ｜ 2 → 3.58 ｜ 4 → 3.62   ✗ 基本不变
scalingMode = Hierarchy  localScale 4 → 14.18                          ✅ 等比放大
```

**规矩**：从资源包拿来的特效，**先查 `main.scalingMode`**。
要在代码里按体型缩放它，必须在生成后改成 `Hierarchy`（或 `Uniform`）。
本例做法：`BasicThunder01.开等比缩放()`。
（`ActiveSkillCaster` 里焚天炎术那段也是为了同一个目的，只是坑表现得更早。）

### B20. 量特效位置要用 `transform.position`，**别用 `ParticleSystemRenderer.bounds`**
**症状**：改朝向时用 `renderer.bounds` 量"雷球在锚点上方还是下方"，
结论反复横跳、改了两轮都改错方向。

**真因**：`ParticleSystemRenderer.bounds` 是**粒子的世界包围盒**，它包含了
每个粒子自身的体积（`startSize` 可达 3）和随机漂移。子部件本身只有 1.4m 的偏移，
但包围盒有 4m 高，于是"球在上还是在下"被体积糊掉了。实测同一旋转下：

```
用 bounds 量：合并 y −1.62 ~ +4.19（看不出球在哪）
用 transform.position 量：雷球 Δy = +2.01、雷柱 Δy = +2.06（一目了然）
```

**规矩**：判断"部件 A 在部件 B 的上方还是下方"，**量 `transform.position`**；
只有判断"视觉整体多大/覆盖到哪"时才用 `bounds`。

### B21. `Billboard + alignment=View` 的特效，换个机位看就"歪"——这是资产特性
**症状**（2026-09-28 用户问）：*「在场景中看它时很正常，但是在游戏通过摄像机看它，
那个雷柱就会变偏移，这是为啥？」*

**真因**：该 prefab 12 个部件全是 `renderMode = Billboard, alignment = View`，
即**每个粒子永远正对相机**。它本质是一叠 2D 贴图片：

- 场景视图相机多半是**接近水平/正面**看 → 贴图正对镜头 → 看着笔直居中
- 游戏相机固定 `pitch 50° / yaw 45°` **俯视** → 同一张贴图被**斜着投影** → 看着歪斜

**部件位置其实完全对齐**（实测 Δx = Δz = 0.00），不是位置错，是投影观感。

**怎么验证我说的对不对**：把**场景视图相机也调到 50° 俯视**，
如果歪斜同样出现，就证明是机位+Billboard 的问题而非模型问题。

**可选缓解**：把"竖直的柱子/球"那几个部件改成 `alignment = World`
（`BasicThunder01.雷特效不随相机` 开关，默认关）—— 柱子在世界上始终竖直，
代价是俯视时贴图被斜看、可能更扁。

### B22. 坐骑 prefab 上挂着 `NpcInstance` + `NpcIndicator`（已修）
**发现**（2026-09-28）：9 个坐骑里有 **6 个**的 prefab **根节点**带着一整套 NPC 组件：

```
灵翅 / 狼骑 / 灵鹿 / 麒麟 / 熊猫 / 灵鹤   →  NpcAnimator + NpcInstance + NpcIndicator
碧水兽 / 巨龙 / 上古神龙                    →  只有 NpcAnimator  ✓（本来是对的）
```

**只要 `NpcAnimator`**（+ `Animator` / `Collider`），别顺手带上 NPC 那一套。

### B23. 排查"莫名多出一个 NPC"时，先看 Console 有没有任务重建警告 ⚠️

这个现象**没能复现**，用户会在下次复现时保留现场。

**但排查中发现两条高度可疑的线索，下次优先查这两处**：

### B33. 「莫名多出一个成男村民」= **外观预览台跑进了真实世界**（已修）⚠️
**症状**：打开面板（这次是学被动神通时开的面板）之后，场景里凭空多出一个
**「村民·成男」** NPC：顶着名牌、会自己走动、还能被右键锁定和对话。关掉面板它也不消失。

**现场取证**（用户暂停了 Play Mode，对象一直挂着，这条线索很关键）：
```
外观预览台              position=(0.00, 1.20, -3.20)  active=True  父=根
外观预览台/预览模型      NpcInstance.enabled=True  DisplayName=村民·成男  定义=npc_cunmin_chengnan
                        NpcIndicator / NpcDialogue / StationInteractable / NpcAiHuman 全是 enabled
```

**三个叠在一起的 bug**：

#### (1) 相机挂在了预览根自己身上 → 整座预览台被拽回世界原点
`外观预览.cs` 的 `建立()` 本来想把预览台丢到很远的地方隔离起来：
```csharp
预览根.transform.position = new Vector3(0f, -1000f, 0f);   // 先丢到 -1000
相机 = 预览根.AddComponent<Camera>();                        // ★ 相机挂在了预览根上
相机.transform.localPosition = new Vector3(0f, 相机高度, -相机距离);  // ★ 等于又改 预览根 自己的位置
```
`相机.transform` **就是** `预览根.transform`，所以最后一句把预览台从 -1000
拽回了 `(0, 1.2, -3.2)` —— 正好是玩家身边。
**修法**：相机建成预览根的**子物件**（`new GameObject("预览相机").AddComponent<Camera>()`
+ `SetParent(预览根.transform, false)`）。
> 对比隔壁 `坐骑预览场地`（y=-4000）：它的 `预览相机` 就是子物件，所以从来没出这个问题。

#### (2) 预览模型是**完整 NPC 预制体**，身上脚本一个没摘
外观资产取出来的模型带 `NpcInstance` / `NpcIndicator`（头顶名牌）/ `NpcDialogue` /
`StationInteractable` / `NpcAiHuman`（自己会走）。原代码只 `Destroy` 了 `Collider`，
注释写着"只留渲染"但代码没做。
**修法**：`去掉会干活的组件()` 把这些脚本连 `NpcInstance` 一起摘掉，只留渲染 + `NpcAnimator`。

#### (3) 预览台是**独立根物体**，面板关掉时不会跟着销毁
面板只是 `SetActive(false)`，组件不销毁 → `OnDestroy` 不触发 → 预览台永远留在场景里。
**修法**：加 `OnDisable() → 拆掉()`（复位状态，下次 `OnEnable`/`显示()` 重建）。

**两个顺带学到的**：
- `Destroy` 删组件会**被 `[RequireComponent]` 拦住**：
  `NpcIndicator` 依赖 `NpcInstance`，先删 `NpcInstance` 会报
  `Can't remove NpcInstance (Script) because NpcIndicator (Script) depends on it`。
  必须**依赖方先删、被依赖的最后删**；而且 `Destroy` 延迟到帧末才生效，
  同一个批次里调用的先后顺序不算数 —— 这里得用 `DestroyImmediate`。
- **凡是"自己 new 了一个独立根物体"的组件，一定要在 `OnDisable` 里收掉**，别只写 `OnDestroy`。

**排查这类「莫名多出一个 NPC」的通用顺序**：
1. `GetComponentsInChildren<NpcInstance>(true)` 把全场景 NPC 按名字分组，看谁重复；
2. 看那个东西的**世界坐标** —— **y 是 -1000 / -4000 这种，就是某个"预览台"漏出来了**；
3. 再顺父链找是谁生成的，看那个组件的 `OnDisable`/`OnDestroy` 有没有真的收掉它。

### B24. 加新神通后「组件永远装不上」→ 漏跑 `修仙/面板/收集面板目录` ⚠️
**症状**（2026-09-28 做千劫雷狱时踩到）：新被动神通资产生成了、学习物品也能学到、
`面板.已获得被动(p)` 和 `IsPassiveEnabled(p)` 都是 `true`，也登记进了
`PlayerAbilityLoader.被动神通表`，**但组件就是永远装不上**。

**真因**：`PlayerAbilityLoader.Refresh()` 遍历的是 **`面板.神通`（可用列表）**，
而这个列表**不是**每次进场景从 `Generated/` 扫出来的 ——
`UIPanelData.EnsureLists()` 是**从 `resources/面板/面板库.asset` 整体拷贝一份**：

```csharp
if (库.神通 != null && 库.神通.Count > 0)
    神通 = new List<DivineAbilityDefinition>(库.神通);
```

而 `DataTableImporter`（从配置表生成资产）**不更新这个库**。所以新神通不在列表里，
`Refresh()` 里那个 `foreach (var a in 面板.神通)` 根本看不到它。

**更坑的是**：手动 `面板.神通.Add(新神通)` 也会被下一次 `EnsureLists()` 覆盖掉，
所以"我看到加进去了、一转眼又没了"。

**修 / 规矩**：加任何新神通 / 法宝 / 灵阵 / 坐骑 / 真灵后，**必须多跑一步**
**「修仙/面板/收集面板目录」**。完整流程：

```
1. 改 CSV
2. 修仙/从配置表生成资产     ← 生成 <类型>/<id>.asset + 物品 + 效果
3. 修仙/面板/收集面板目录     ← ★ 漏了这步就白干
4. 在 5 个场景的 PlayerAbilityLoader 里登记组件类名
5. 重载场景验证
```

> 教训：**"资产存在" ≠ "运行时能看到它"。** 项目里有好几处"聚合缓存资产"
> （面板库就是典型），它们由各自的收集器刷新，**不在导入器的职责里**。
> 排查"东西明明有却读不到"时，先找有没有这类缓存。

### B26. 别用 `ParticleSystemRenderer.bounds` 量特效尺寸 —— 它会**虚胖**，害我得出全错的结论 ⚠️⚠️
> 📌 **B26–B32 这一组是 2026-09-28 做"闪电链"时踩出来的。**
> 那个自制件 `雷链` 最终**被用户判定不合格、已删除**，闪电链/落雷特效槽**空置待补**
> （见 [闪电链特效](../guides/闪电链特效.md)）。
> **但这些坑与具体资源无关，是粒子系统 + 探针的通用问题，补特效时照样会踩，所以全部保留。**

**这是本轮最大的教训。**（2026-09-28 做闪电链时）

我用 `renderer.bounds` 量"链有多长"，得到一张漂亮且自洽的表：
间距 3/8/15m → 链长 **3.00/8.00/15.00m**，横向恒定 1.51m。于是判断"长度完全正确"。

**实际上粒子压根没铺开** —— 用 `GetParticles()` 量出来，粒子在链轴上只铺开 **0.26m**，
链就是中间一坨。用户反馈"完全没看到"才发现。

**正确做法**：量真实粒子，投影到链轴上：
```csharp
var arr = new ParticleSystem.Particle[ps.main.maxParticles];
int n = ps.GetParticles(arr);
for (int i = 0; i < n; i++) {
    // ⚠️ simulationSpace = Local 时 position 是**本地**坐标，必须先转世界，
    //    否则会被 lossyScale 再除一次（我就这么又错了一次）
    var wp = ps.main.simulationSpace == ParticleSystemSimulationSpace.Local
           ? ps.transform.TransformPoint(arr[i].position) : arr[i].position;
    float a = Vector3.Dot(wp - 链.transform.position, 链轴);
    minA = Mathf.Min(minA, a); maxA = Mathf.Max(maxA, a);
}
```
> 顺带更正旧记录：`ParticleSystem.particleCount` 在这个引擎里**是可用的**（实测 135/290/145/174），
> `GetParticles` 也能用。**只有 `bounds` 不能用来判断尺寸。**
> 详见 **B20**（同类问题）。

### B27. `renderMode = Stretch` 会让链**几乎完全看不见** ⚠️
**现象**：`ground-flashes` 那棵子树的粒子速度 ≈ 0，而 `Stretch` 是沿**速度**拉伸的，
速度为零时方向退化。同一个特效、同一时刻、同一机位对比：

| renderMode | 画面 |
|---|---|
| `Stretch`（速度 0.6） | **几乎全黑**，只有中间一坨淡淡的雾 |
| `Stretch` + `velocityScale=4` | 一条又粗又直的平滑光柱，完全不像雷电，还冲出两端很远 |
| `Billboard` | 一条明亮的锯齿雷电 ✓ |

**修法**：`renderMode = Billboard` + `alignment = View`。

### B28. `scalingMode = Shape` 会把 `localScale` 作用**两次** ⚠️
实测：`shape.scale.z = 1`、`localScale.z = 3.42` 时，
`Shape` 下粒子在链轴上铺开 **11.7m**（≈ 3.42²），`Hierarchy` 下是 **3.39m** ✓。

| 模式 | 效果 |
|---|---|
| `Shape` | 缩放松了**两次** → 链被拉稀、糊成一团 |
| `Hierarchy` | 线性一次 ← **可变长链要用这个** |

> ⚠️ 这和我之前记的**正好相反**（旧记录说"Shape 只缩放发射体、链长变化时粗细恒定"）。
> 那条是基于 `bounds` 的错误读数得出的。现在有 `GetParticles` 的实测支撑。

### B29. 那张"闪电条"贴图是**有方向的**，同向会排成"梳齿"
`Billboard` 下所有粒子贴图朝向一致，沿链就排出等距的平行短杠（像梯子）。
**修法**：给每颗粒子随机 `startRotation`（`MinMaxCurve(0, 2π)`），打散之后才像乱窜的电弧。

### B30. 拉伸链的长度要用**三维距离**，不能只算水平距离
**现象**：`生成拉伸链` 早期算 `new Vector2(向.x, 向.z).magnitude`。
雷云的雷是从 +3.5m 的云上**斜劈**下来的，只算水平距离 → 链的两端**各差约 1.35m**，
起点够不着云、终点够不着目标（肉眼就是"闪电断了一截"）。

### B32. Play Mode 被**暂停**时，带 `yield` 的探针会卡死到超时 ⚠️
**现象**：探针接连报 `Operation timed out`，没有 `elapsed_ms`。
**真因**：用户在编辑器里点了暂停（`isPaused = true`），协程的 `yield return null` /
`WaitForSeconds` 永远不推进 → 探针挂住。

**做法**：
1. 先 `unity_editor get_state` 看 `isPaused`，或直接 `resume`；
2. 暂停状态下**只能跑完全同步的脚本**（不要 `yield`），这样反而能拍到"用户此刻看到的画面"。
3. 暂停时 `Destroy(go, 秒数)` 不推进，所以临时特效会一直挂在场景里 ——
   用户会在 Hierarchy 里选中它（`selection.activeObject`），这也是个有用的线索。

### B34. 探针里**别用 `transform.position += …` 推玩家** —— `PlayerController` 会把它覆盖掉 ⚠️
**现象**（2026-09-28 调雷云跟随插值时踩到）：我给玩家每帧 `position += v * Time.deltaTime`
想让它以 6 m/s 匀速跑，用来量云拖后多少。结果量出来的滞后远小于理论值。
**真因**：`PlayerController.Update()` 每帧会按输入重新算位置，**把我设的位置覆盖了**。
实测：我推了 **2.14m**，角色实际只走了 **0.67m**（≈1.87 m/s 而不是 6 m/s），
于是"实际速度"只有我假设的三分之一，滞后量自然全测错。

**做法**：
- 要精确控制速度，就用一个**没人管的假角色**（`new GameObject` + `AddComponent<那个组件>()`）；
- 或者**读角色的真实位移**再换算速度（`(末位置 − 初位置) / 累计 deltaTime`），
  不要拿"我以为的速度"去做理论对比。

> 顺带：这类"动态手感"的数值在编辑器里量会**很吵**（桥的帧间隔不稳），
> 量到一个干净的比例就够定调参方向了（这次量到 `滞后 ÷ (速度×平滑时间) = 1.07 ≈ 1` ✓），
> 不要去追那张抖动很大的扫描表。

### B35. 探针物件**必须放在相机视野内** —— 视锥剔除会停掉粒子模拟，读数全是假的 ⚠️⚠️
**这是本轮最贵的一次错误**（2026-09-28 做瞬雷天闪，连错两次、还改坏了特效）。

#### 第一次错：把测试物件丢到相机外，量出"特效不出粒子"
我把 `lightning-sphere` 实例生成在 `(400, 20, 400)`（远离场景，**图省事、免得挡镜头**），
然后量 `GetParticles` —— **1.5 秒内恒为 0 颗**，于是判断"这个常驻光球特效来不及长起来"。

**真相**：这些特效的 `cullingMode = PauseAndCatchup` ——
**被视锥剔除的粒子系统会停止模拟**。同一个 prefab 同时放两个，实测：
```
相机内（玩家旁边）  ： 2 → 9 → 13 → 18 颗   ← 正常生长
相机外（x=400）     ： 0 → 0 →  0 →  0 颗   ← 被剔除，压根没在跑
```
用户在场景里手放的那个原版实例是 12/12/35/2 颗 —— **特效本来就是好的**。

#### 第二次错：用 `ParticleSystem.Simulate()` 去"预热"，结果把特效**冻住**
基于上面的假结论，我加了一版"预热"：
```csharp
ps.Simulate(0.4f, false, true, false);   // ✗ 想让球一生成就是"长好的样子"
```
`Simulate()` 之后 **`isPlaying = False`、`isPaused = True`** —— 系统被**暂停**了，
而且不会自己恢复，于是**闪电球和命中爆炸都变成一帧静止画面**（用户当场发现：
"完全是静止的"）。实测同一时刻：不预热 `isPaused=False` 但被剔除；
预热过的 `isPaused=True`，粒子位置三帧**一动不动**。

**正确做法**：
- 想量粒子，**把实例放在相机能看到的地方**（或者干脆放在玩家旁边）；
- **不要用 `Simulate()` 当预热**。真要让特效"一出现就是长好的"，用
  `main.prewarm = true`（要先设好、再让它开始播，例如 `SetActive(false)` → 设 → `SetActive(true)`），
  它不会暂停系统；
- 更稳的做法：**别改特效**。用户要的就是"原原本本生成、飞过去、命中生成"。

> **教训**：一个"特效没反应"的结论，先问一句**我的测量条件是不是有效**。
> 这次如果一开始把实例放在镜头里，根本不会有后面这一串。
> （同一个坑的另一面见 **B36**。）

### B36. `ParticleSystem.Simulate()` 会**暂停**粒子系统 ⚠️
`Simulate()` 的定位是"配合 `Pause()` 做逐帧快进/拖拽预览"，
**它跑完会把系统留在暂停态**（`isPlaying=False, isPaused=True`），
之后再没有外力是不会自己动的。

所以：
- **不要**拿它当"预热 / 快进到稳定态"用 —— 那等于给特效拍一张静态照片；
- 真要用，必须在后面补 `ps.Play(true)` 把它重新播起来，并且**验证 `isPaused == false`**。

> 判断信号：只要看到 `isPlaying=False` 而 `isPaused=True`，
> 就是被 `Simulate()`（或 `Pause()`）停住了，不是特效本身的问题。

### B37. 想"停住动画"不能直接改 `animator.speed` —— `PlayerAnimationController` 每帧都会重写它 ⚠️
**场景**（2026-09-28 做瞬雷天闪）：用户要求"动画播到 40% 节点时**停 1.5 秒**让雷球长出来，
再继续播、球再飞出去"。

**第一反应**是外面直接 `动画.animator.speed = 0`，但不行：
`PlayerAnimationController.Update()` 里有一句**每帧都执行**的
```csharp
animator.speed = Mathf.Max(0.01f, playbackScale * (动作播放中 ? 动作速度倍率 : 1f));
```
两个问题：① 下一帧就被覆盖回去；② `Mathf.Max(0.01f, …)` **连 0 都不允许**。
而且 `动作速度倍率` 是 `{ get; private set; }`，外面本来也写不了。

**做法**：在那个类里加一个正式接口（**要停就停在这个类内部**）：
```csharp
bool 动作定住;                                    // 私有状态
public void 定住动作(bool 定住) => 动作定住 = 定住;
public bool 动作已定住 => 动作定住;

// 每帧那句改成：
animator.speed = 动作定住 ? 0f
    : Mathf.Max(0.01f, playbackScale * (动作播放中 ? 动作速度倍率 : 1f));
```
并且在 `停止动作()` 里把 `动作定住 = false` —— **否则"定住"会留给下一个动作、甚至把人永远僵住**。
调用方（runner）还要在 `收尾()` 和 `OnDestroy()` 里各补一道 `定住动作(false)`。

**实测**（停在 40% 节点 1.5 秒）：
```
动作进度=0.407  animator.speed=0.00  定住中=True   球粒子 0 → 25 → 50   ← 定住了、球在长
动作进度=0.435  animator.speed=1.00  定住中=False  球已飞出            ← 放开、继续播
```

> **通用教训**：一个字段如果**由某个组件的 Update 每帧写**，
> 外部"临时改一下"必然无效。要么走它提供的接口，要么把状态交给它管 ——
> 别在别人每帧覆盖的地方做临时手脚。

### B38. 特效存活**别写死秒数** —— 同一个坑一天踩了四次 ⚠️⚠️

**症状**：特效"提前消失 / 忽然没了"，而原版（直接在编辑器里拖出来播）是慢慢消失的。

**根因**：资源包的粒子寿命经常带**长尾**（比如一撮粒子的 `startLifetime` 是 0~9 秒随机），
而代码里写死了一个偏短的存活秒数 → 到点 `Destroy` = **硬切**。

**四次中招（2026-09-29）**：

| # | 谁 | 写死的值 | prefab 自然总时长 | 备注 |
|---|---|---|---|---|
| 1 | 沧澜寒渊录普攻·冰刺 | 1.2s | `frost-shock` **9.1s** | 见 [沧澜寒渊录 §2.4](../guides/沧澜寒渊录.md) |
| 2 | 寒墟 / 冰暴术 | 3s / 2s | `frost-ring` 10.1s、`frost-frozen-tomb` **20.7s** | 同批修的 |
| 3 | 玄霄雷诀普攻·雷劈 | 1.2s | `lightning-ray` **4.5s** | **粒子峰值正好在 1.2~3s**，等于砍在最强的时候 |
| 4 | 焚天炎术（范围伤害） | 拿"伤害窗口 3s"当了特效寿命 | `Effect_13_DangerClose` **5.0s** | 火焰柱还没落完就 Destroy |

**正确做法**：用 [`特效摆放.量特效总时长()`](../../cultivation/Assets/Scripts/Combat/特效摆放.cs)
量 prefab 的自然总时长（所有粒子系统取 `startDelay + duration + startLifetime(最大)`，
各自 ÷ `simulationSpeed` 后取最大），存活取 **`max(手动值, 自然时长 × 1.05)`**。

- `BasicFrostSpike01` / `BasicThunder01` / `HomingBoltSkillRunner`：都有
  `存活按特效自动`（默认勾上）+ `存活倍率`（1.05）。
- `AreaSkillRunner`（范围伤害）：**伤害窗口和特效存活必须分开**
  —— 伤害按「持续时长」停，特效活到自然播完。
- `IcePillarSkillRunner`（寒墟）：三段特效各自按自然时长算。

**实测曲线**（每秒采存活粒子数）：

| 招 | 峰值 | 修之前 | 修之后 |
|---|---|---|---|
| 冰刺 | 520（t=1s） | 1.2s 硬切 | 9.56s 自然销毁 |
| 雷劈 | **504（t=3s）** | 1.2s 硬切（砍在峰值上） | 4.73s 自然销毁 |
| 焚天炎术 | 5809（t=2s） | 3s 硬切 | 5.25s 自然销毁 |

> ★ **别拿「持续时长」当特效寿命** —— 一个是 **gameplay 窗口**，一个是**美术时长**，
> 两者没有关系。新接任何特效，先量自然时长再决定什么时候 `Destroy`。

### B39. `[NonSerialized]` 的字段**在场景里改不动** —— "我明明关了它" ⚠️

**症状**（用户 2026-09-29 报）：宗门场景里那几座能互动的楼，**按 F 有反应、但头顶不弹提示**。

**真因**：`StationInteractable.现在可交互` 上写着 `[System.NonSerialized]`：

```csharp
[System.NonSerialized] public bool 现在可交互 = true;   // ← 场景/预制体存不住，加载永远回到 true
public bool 显示靠近提示 = true;                        // ← 这个才是序列化的
```

工作日志里当时写的是「4 座待开发楼：`显示靠近提示=false`、**`现在可交互=false`**」——
**后半句从来没生效过**。于是这 4 座楼 = 提示被藏（序列化生效）+ F 照样能按（字段回到 true）
→ 正好是用户看到的样子。（审计脚本也会被骗：编辑模式下把它读出来是 `True`，
但那不是场景里存的值，是构造函数给的默认值。）

**修**：把这 4 座的 `显示靠近提示` 改回 `1`（手改 `.scene` 的 YAML，diff 只有 4 行）。

**通用教训**：
- 想在**场景/预制体**里存住的状态，字段**不能**带 `[NonSerialized]`；只想运行时管的状态才带它。
- 字段带 `[NonSerialized]` 时，"在 Inspector 里关掉它"是**假动作** —— 下次加载就回来了。
- **要"整座设施停用"，用序列化得到的手段**：`交互距离 = 0` / 组件 `m_Enabled = 0` /
  直接把物件停用；**别只关 `显示靠近提示`**（那只藏提示，F 还能按）。
- 审场景时别只信 Inspector/反射读出来的值，**要看 `.scene` 里到底有没有这个键**
  （`git grep` 搜那段转义键名，一眼就知道存没存）。

### B40. ⚠️ `Renderer.bounds` 对**蒙皮武器**不可靠 —— 拿它做近战判定会让怪整场打空

**症状**（2026-09-29 做 21 只妖魔的近战判定时）：穷奇站在自己量出来的站位（1.9 米）上，

- 出现"站在该站的位置上却打空"，**先量判定体运行时包围盒 vs 真值前伸**，别先怀疑状态机。

### B41. ⚠️ 探针里复位玩家**必须调 `复活()` / `回满()`** —— 直接写 `当前气血` 会留下 `已死亡`

**症状**：连续做几轮怪物伤害测试，**从某一轮开始所有怪都"0 出手"**，
每只都停在 `待机`，状态机像死了。花了两轮测试才发现是**测试脚本自己的问题**。

**真因**：探针里为了不让玩家被打死，写的是
`玩家.当前气血 = 玩家.气血上限;` —— 这只改了数字，**没清 `已死亡` 标记**。
而所有敌对 NPC 的决策第一行是「玩家已死 → 待机」，于是全场怪都不动。

**修**：探针里一律用 `玩家.复活()`（或 `回满()`）—— 它们**就是**为清这个标记准备的
（`PlayerVitals` 的注释里早写了"以前这里不清 `已死亡`…结果打到一半全场 NPC 集体不动"）。

**通用教训**：
- 直接改"当前值"字段，等于绕过那段代码的**副作用**；有专门入口就用入口。
- 一次 Play 会话里连做多组测试，**上一组的副作用会污染下一组**（尤其死亡、静态标记）。
  怀疑"AI 挂了"之前，先怀疑**上一次测试留下的状态**。

### B42. **自动挂载发生在 `Start()`，不是 `Awake()`**

`NpcInstance` / `NpcAi*` 那套"按类名自动挂组件"是跑在 `Start()` 里的。
探针里 `Instantiate` 之后**立刻**去 `GetComponent` 会**查不到**（只有 `yield` 过一帧的那一只挂上了）。

**做法**：批量造完**统一 `yield return null`（最好两帧）**再去查；别边造边查。

> **我自己又犯了一次**（2026-09-29 做怪物 AI 时）：`Instantiate` 之后立刻
> `ai.出手 += ...` 挂事件，`ai` 是 null → 事件**静默没挂上** → 读数全是"出手 0"，
> 白查了两轮。**挂事件、读状态之前，先等一帧。**

### B43. ⚠️ `SphereCast` 的**起始球压着别人**时，所有方向都返回 `distance = 0` 的命中

**症状**（用户 2026-09-29 报"拉一波怪，它们排着队、原地不动"）：
8 只寒狼间隔 1.2 米排成一列冲过来，**后排 6 只一步都不走**（`走过 = 0.0 米`）。
给它们加了"被挡就侧偏绕行"之后**依然不动** —— 因为 `找绕行方向` 报"**八个方向全被挡**"。

**真因**：`Physics.SphereCast*` 只要**起始球和某个碰撞体重叠**，就会给**任何方向**都返回一个
`distance = 0` 的命中。而这些怪的碰撞体**特别大**（寒狼的胶囊实测 **2.58 米宽** > 1.2 米间距），
排一列时彼此本来就重叠 → "四面八方全被挡" → 一步不动。

**修**：判定里**跳过 `h.distance <= 0.001f` 的命中** —— 那是"已经挤在一起"，
不是"前面有障碍"。挨着了该做的是滑开，不是永远罚站。

**通用教训**：
- 用 `SphereCast` 做"前面有没有东西"时，**必须处理"起点就在碰撞体里"这种情况**
  （自己身上也一样 —— 见 §15.6）。`distance == 0` 的命中基本都可以忽略。
- **怪的碰撞体可能远大于它的模型**（寒狼 2.58 米）。按"间距 1.2 米排一列"这种假设写逻辑一定会翻车。

### B44. ⚠️ 近战怪"停手余量"必须和"够得着"用**同一个数**，否则会差几厘米永远不出手

**症状**（同一天，我自己引入的）：给"围上来"加了环形接近点（半径 = 攻击距离 × 0.8）之后，
6 只怪**全部整齐地停在 1.34 米**、**一次都不出手**（射程 1.30）。

**真因**：我把停手条件写成"离**目标点** ≤ 0.3 米就停"：
环半径 1.04 + 余量 0.30 = **停在 1.34 米**，而射程是 **1.30** —— **永远差 4 厘米**。
这和 `NpcAiCombatant.决策()` 里那条老注释是**同一个坑**（停靠距离必须比攻击距离近一点）。

**修**：停手直接用 `到敌人距离 <= 攻击距离 × 0.85f`（和 `决策()` 同一个阈值）。

**通用教训**：
- 判定型逻辑里"两个相关的阈值"必须**同源**（要么同一个常量，要么一处派生另一处），
  各写各的迟早差一点点，而且**现象是"完全不动"**，极难往"差 4 厘米"上想。
- 这个坑在**同一个项目里已经出现过两次**了（老的那次是"停在攻击距离边界上，
  浮点误差判够不着"）。写"停下来"的条件时，先去找"能不能动手"用的是哪个数。

### B45. 直接改 `transform.position` 的移动**没有物理推挤** —— 一群怪会叠在一个点上

**症状**：把"排队"修好之后，7 只寒狼**方位角全是 0°** —— 它们沿同一条直线走到了**同一个点**上，
互相穿模叠在一起。

**真因**：这套 NPC 移动是 `transform.position += 方向 * 速度 * dt`（没有 NavMeshAgent、没有刚体），
所以**没有任何"挤开"的力**。

**修**：加了 `NpcAiBase.算分离()` —— `OverlapSphere` 找 2.5 米内的**同类单位**
（只推怪，不推玩家/建筑），越近推得越狠，作为横向分量加进前进方向。
实测方位角从"全是 0°"变成 **-118° ~ +87°**。

**通用教训**：**没有物理引擎帮忙的时候，"分开"得自己写。** 反过来，也别指望
`Collider` 能把它们分开 —— 碰撞体只被用来"探路"，不会真的推开谁。

### B46. ⚠️ 怪**死了**、飞弹还在飞 → 命中回调访问已销毁的施法者，刷 `MissingReferenceException`

**症状**（2026-09-29 做飞弹怪时抓到的）：怪被打死、它射出的箭还在飞；箭命中玩家那一刻抛异常：

```
MissingReferenceException: The object of type 'NpcAiJianMo' has been destroyed but you are still trying to access it.
  NpcAiBase.生成装饰特效 → 生成命中特效 → 在目标结算 → NpcProjectile.到达 回调
```

**真因**：飞弹的命中回调是挂在 `NpcProjectile.到达时` 上的**闭包**（`飞.到达时 += () => 在目标结算(...)`），
它捕获的是**施法者那个组件实例**。怪被销毁之后，闭包照样会被调用 ——
而 `生成装饰特效` 里有一行 `fx.name = "NpcFx_" + name;`，访问已销毁对象的 `name` 就抛。

**修**：名字兜底 `this != null ? name : "已销毁的施法者"`。
**注意不要顺手把伤害也掐掉** —— 弹都飞出来了，该打还得打；只让"特效名字"这一处降级。
（实测：出箭后立刻销毁施法者 → 异常数 0 ✓）

**通用教训**：
- **回调/事件比持有者活得久**是常态（飞弹、DoT、延时结算都这样）。闭包里访问宿主之前先判 `this != null`。
- 探针里"造完就 Destroy"很容易**批量制造**这类异常 —— 看到它先想清楚
  **是代码本来就有的、还是探针制造的场景**（这条是本来就有的，白鹿精时代就在了）。

### B47. ⚠️ 拿**蒙皮网格当弹体**（把子部件烘成 prefab）时，必须先**算主轴 + 居中**

**症状**（用户 2026-09-29 报）："箭现在是**斜着飞**的，不是正对飞行方向。"

**真因**：把 `Object135`（蒙皮网格）`BakeMesh` 出来直接当弹体，有两个问题：

| 问题 | 数字 | 后果 |
|---|---|---|
| 网格里的箭头是**斜放**的（不在任何坐标轴上） | 烘出来包围盒 `1.23 × 0.50 × 1.61`（斜放 → AABB 被撑成一个扁盒子） | 弹体 `forward` 就算对，**视觉上箭也是斜的** |
| 网格**中心不在原点** | 包围盒中心 `(-0.96, 0.85, 1.47)` | 弹体**飘在手外面约 1.9 米** |

**修**：
1. **找主轴**：遍历所有顶点找**相距最远的一对**，方向就是轴（实测 `(-0.601, 0.196, 0.775)`），
   再 `Quaternion.FromToRotation(轴, Vector3.forward)` 把顶点转正 → 包围盒变成 `0.15 × 0.12 × 1.92`（一眼是根箭）
2. **居中**：顶点全部减包围盒中心
3. **定"哪头是尖"**：取轴两端各 ~18% 的顶点算**平均横向铺开**，**细的那端是箭尖**
   （实测 -Z 端 0.023 / +Z 端 0.060 → 反了 → 再多转 180°）；
   另外**渲一张侧视图**、在 +Z 放个方块 -Z 放个球，一眼就能核对（比看数字直观得多）

**通用教训**：
- **"长轴看起来是 Z" ≠ "长轴就是 Z"** —— 斜放的模型 AABB 依然是个正规的盒子。
  真正的轴要自己算（最远两点 / PCA）。
- 把子部件做成独立 prefab 时，**顺便把中心归零**：不然它会飘在挂点外面，
  而这种偏移**光看包围盒 size 是看不出来的**（要看 center）。
- 朝向这种事**数值 + 渲图两条都对上再收工**：我第一版只翻了 180°、没对轴，
  又被用户抓了一次。

### B48. ⚠️ **别跟动作抢方向盘**：施法/射箭动作自带站位和转体，AI 每帧纠向目标反而是错的

**这条是"我改错了一次又改回来"的完整记录**，比结论本身更值得看。

**症状**（用户 2026-09-29 报）："**箭魔的拉弓瞄准方向不是他朝向的方向**，你看一下。"

**我的第一版判断（错的）**：量到攻击期间 `transform` 偏航从 180° 甩到 257°（离玩家最多 **77°**），
而 `攻击期间锁定朝向` = true（攻击期间不纠向），于是**把它设成 false** —— 每帧把身体纠向玩家。
改完 `transform` 确实 **0°** 了，还渲了图"证明"身体朝玩家、弓口对玩家。**我以为修好了。**

**用户下一句就把我打回来了**：
> 「**还是不太对**」「射击开始时的**朝向就是射箭的正确方向**，射击过程中的**转体**会让朝向和射箭方向偏离」
> 「**对于箭魔这种，在射击时不要朝向玩家就好了**」

**正解**：那套动作**自带站位与转体**（弓手本来就侧身站、身体随拉弓转，只有持弓的手指向目标）。
AI 每帧把身体纠向玩家 = **跟动作抢方向盘**，等于**把动作的转体整个抵消掉** —— 手感当然不对。
**`攻击期间锁定朝向` 应该保持 true（射击时不纠）**，让动作自己演。

**真正让"瞄的方向 ≠ 朝向"的是另一件事**：当时**弹体是我另生成的一支箭**，
出生点靠"量出来的骨骼 + 偏移"近似，和动画里那支箭不是一回事。
用户点出正解：
> 「他射箭的动画中其实**已经有了箭这个组件**……**能否让动画结束了箭也不消失，让它真正的飞出去**？」

→ 改成 **发射那一刻手动蒙皮量出动画里那支箭的真实世界位置**当出生点，
并把它藏起来（= 飞出去了），飞的是烘好的静态网格副本，动作结束再放回来。
实测出生点误差 **0.000~0.019 米**（原来是 1.075 米 —— 那 1 米是基类"推出自己碰撞体"的前移量，
纯网格弹体不需要，覆盖成 0）。

**通用教训**：
- **动画自带的表现（站位/转体/位移）不要用 AI 去"纠正"**。先问一句：这是动作设计的一部分，还是 bug？
  弓手侧身站、挥拳带转体，都是**设计**。用 AI 每帧把它掰回"正对目标"只会更难看。
- **"数字对了"可能只是把别的东西压掉了**。我把偏角从 77° 压到 0°，代价是抹掉整个转体 ——
  数字漂亮，手感更糟。**量数字之前先想清楚"这个数字应该趋近于什么"**。
- **用户说"还是不太对"时，不要再沿原方向加码**，把判断依据（我量的、我改的、我看到的现象）摊开问一句，
  或者换个完全不同的解法 —— 这次用户直接给了更好的解法（用动画里那支箭）。
- 出生点这类"和动画里某个物件对齐"的需求，**优先直接从动画里取那个物件的位置**，
  别用"骨骼 + 手工偏移"去近似（偏移还会随动作变化，每招都得重量）。

> **后续**：箭魔本身用户 2026-09-29 **决定删掉了**（理由：箭出手比动作早、方向还歪），
> 但上面这套结论**仍然成立**、也已经留在框架里（`飞弹妖魔Ai.动画弹体节点名`），
> 以后有"动作里自带弹体"的怪直接用。删除记录见 [guides/怪物飞弹 §12](../guides/怪物飞弹.md)。

## C. 对话系统

### C1. 「条件=对话」的对话id 必须是**入口段**
**真因**：按 F 打开对话走的是 `最小分段(npcId)` = **第 1 段**，之后靠「跳转」往后走。
**后果**：填了一个靠后的段 → **该阶段永远达不成** → 对话无限循环。
（踩过：`q_main_003` 第 12 阶段填 `dlg_act3_dashi_7`（第 7 段），
入口是 `dlg_act3_dashi_1`（第 1 段）→ 招募对话一直重复。改成第 1 段后正常。）
**做法**：对每个 `条件=对话` 的阶段，比对「该段分段号」与「该 NPC 最小分段号」；
不等就要确认有**跳转链**能走到。链路终点是合法的（玩家点完整条链，最后一段按下时推进）。

### C2. 「对话」完成的时机是**按下回答**，不是刚显示 ⚠️ **两个地方都要改**
有**两套**任务接线，都必须在「按下回答/继续」时才生效 —— 只改一个就会留下一半的坑：

| 接线 | 数据来源 | 作用 |
|---|---|---|
| `通知对话(id)` | 任务表 `对话id` | 完成「条件=对话」的那一阶段（按 id 比对） |
| `处理对话绑定(触发任务, 完成任务)` | 对话表 `触发任务` / `完成任务` 列 | 显式接取/完成某个任务 |

**踩过两次**：
1. 第一次只把 `通知对话` 从 `显示分段` 移到 `按下回答`，**漏了 `处理对话绑定`**；
2. 于是 `完成任务` 在**这一段刚显示**时就生效了 —— 实测「按下『仙人，我准备好了』（跳到 21 段）
   → 21 段一显示就把 q_main_003 第 13 阶段做完了 → 后面按的『好』『结束』全是空跑，
   最后那下『结束』什么都没发生」。
3. 现在两件事都在 `按下回答()` 里，顺序是**先 `处理对话绑定`、再 `通知对话`**
   （前者会把阶段往前推，后者再去比对新的当前阶段，就不会误伤）。

> 「结束」按钮是 `DialogueUI` 给**没有回答的段落**自动加的（`加按钮("结束", …)`），
> 所以「仙人，我准备好了」→「好」→「结束」这三下**都是真实按键**，都能触发接线。

### C3. `逐行打` 不要自动开「打完自动收幕」⚠️
**症状**：开场那三句黑幕**不连贯**，每句之间黑幕消失一次（用户原话：
"每过一个黑幕要取消一下黑幕"）。

**真因**：`逐行打` 里设了 `落幕后自动收 = true`，而 `说()` 也走 `逐行打` ——
于是**每一句**打完（默认 `打完后的停留 = 0.5` 秒）后 `Update` 就自动收幕。
开场是**三句分开 `yield` 的 `说()`**，所以一黑一亮三次。

**做法**：`落幕后自动收` 只由 `下落并定时收起()`（"整段过场"）开启。
`说()` 只负责打字 + 落一次幕，收盘交给调用方（`主线开场` 最后自己调 `收幕()`）。
⚠️ 而且它必须在 `StartCoroutine` **之前**设：协程第一帧会调 `落下()`，而 `落下()` 会把它清成 false。

### C4. `收起()` 改成协程后会把刚落下的幕抹掉 ⚠️
**症状**：**新档开场的第一个黑幕不见了**（其他黑幕正常）。

**真因**：`Awake()` 里调 `收起()` 把幕藏起来。原来是同步的（当场 `SetActive(false)`），
改成"排一个协程几帧后淡出"之后，那次收起的后果被**推迟到之后执行**：
```
Awake()      收起()           → 排了个淡出协程
Start()      说() → 落下()     → 幕 alpha = 1（幕刚显示）
下一帧        那个协程开始跑    → 淡到 0 → SetActive(false)  ← 抹掉了
```
其他黑幕不走 `Awake`，所以只有新档开头这一条中招。

**做法**：
- 已经是隐藏状态时 `收起()` **不再排协程**，当场生效；
- **同一帧内「开始演出 → 收幕」忽略收幕**（`演出开始时刻` 判定），并打 Warning；
- `落下()` 起幕时清掉一切残留的收幕/自动收状态。

### C5. 收幕的防重入标志必须**同步**设上，否则会把淡出协程反复掐死 ⚠️
**症状**：黑幕卡住不动 —— 字已经打完显示着，**点左键、等待都没反应**，
阶段也不推进（`演出中` 永远为真）。而 Console 里阶段其实**推进过一次**。

**真因**：`立即收掉(24)` 里的防重入标志 `正在收幕 = true` 原来写在协程 `淡出幕` 的
**第一行**，而协程要到**下一帧**才跑：
```
Update 帧N: 立即收掉 → StopCoroutine(收起协程) → StartCoroutine(淡出幕)   ← 协程还没跑，标志仍 false
Update 帧N: 同一帧里再次满足收幕条件 → 立即收掉 → 又 Stop + Start        ← 把刚起步的协程掐死
下一帧:      淡出协程刚跑第一行就被上面的 StopCoroutine 杀掉 → 幕永远关不掉
```

**做法**：`正在收幕 = true` 放在 `立即收掉()` 里**同步**设，`淡出幕` 收尾时清掉；
`落下()` 起幕时也要能打断正在进行的淡出，否则两边抢 alpha。

> 教训：**改用协程实现的状态机，"进入状态"的标志要在同步调用处设，不能放在协程体内。**

### C6. 对话表里的 `完成任务` 填的是**任务id**，不是阶段id
走 `处理对话绑定` → `完成当前阶段(任务id)`，推进的是**该任务当前的阶段**。

### C7. 同段位多条候选时，**优先值必须拉开**
`候选()` 排序：优先大者胜 → 平手时 NPC 专属压过通用 → 再平手时带标记的压过无标记的
→ 最后按 id。
**后果**：任务专属回答和默认回答同优先 → 可能被默认回答顶掉（踩过）。

### C8. 出场比"该说话的时候"早的 NPC 会弹出默认对话 ⚠️
**症状**：大师兄在第 7 阶段就生成了，而它该说的招募话要到第 12 阶段才打上
`q_主线_招募中` 标记。玩家提前按 F → **弹的是无标记的默认段**，
看起来像"说错了话"。等剧情演完再按 F 就正常 —— 所以表现为"时好时坏"。

**真因**：对话选段按**标记**过滤（`候选()` 里 `对话条件.满足`）。
标记没打上时，招募段/可启程段都不满足，只剩下招募链的**中间段落**（`分段 2~7`，
本该靠跳转到达、永远不是入口）—— 于是"第一个可用段"成了默认对话。

**现在的做法**：`NpcDialogue` 每帧判定「这个 NPC 当前有没有任何满足条件的对话段」，
没有就把 `StationInteractable.现在可交互` 置 false →
**不显示「F 对话」提示、按 F 也没反应**（`StationInteractor.找最近设施()` 会跳过它）。

⚠️ **这道门槛是通用的**：任何"当前没有任何可用对话段"的 NPC 都会不可对话。
所以给 NPC 配对话时要注意留一个**无标记的兜底入口段**，否则他在标记没满足时会变哑巴。

### C9. `对话标记` 是静态内存、会跨 Play 会话残留
**做法**：编辑器里测新流程**先重启 Unity**。存档 v5 起标记会进存档（见 [design/存档系统](../design/存档系统.md)）。

## D. Unity / 编辑器

### D1. `exec_editor_script` 用的是上次编译的程序集
**做法**：改完 `.cs` 先 `refresh`（`Uni "refresh"`），否则新类型/新字段找不到。

### D2. `unity_editor refresh` 会退出 Play Mode
会丢弃运行时状态，测到一半刷新要重来。

### D3. `exec_runtime_script` 会自动进 Play Mode
跑之前**确认当前打开的场景是对的**（曾白跑两次：Play 跑在 `StartScene` 里，那里根本没有任务管理器）。

### D4. UI 构建器会重建 CharacterUI 层级
菜单 `修仙/构建角色面板 UI` 跑完会把挂在 `CharacterUI` 上的**其它组件（如 `跨场景数据`）删掉**。
**症状**：到宗门后对话不触发 + 进度不接力。
**做法**：跑完 UI 构建，**务必检查并补回 `跨场景数据`**。

### D5. 不要在协程/脚本里忙等
`while (Time.time - t0 < wait) { }` 会**冻死主线程**（`Time.time` 不前进）——
曾把 Unity 搞到闪退。**只能 `yield return new WaitForSeconds(...)`**。

### D6. 首帧新建的 UI 用内置字体 → 中文不显示
**真因**：`Resources.GetBuiltinResource<Font>("LegacyRuntime.ttf")` **不含中文**。
运行时新建的 UI 对象（`new GameObject` + `AddComponent`）Inspector 上没挂字体，
就会回落到它 → **一个字都不显示**。
**做法**：照 `DeathScreenUI` / `黑幕字幕.取字体()` 的写法，编辑器里用 `AssetDatabase`
找 `Assets/Fonts/SimHei.ttf`。
（踩过：黑幕起了、字一个都没有，排查半天以为是时序。）

### D7. 静态数据跨 Play 会话残留
`对话标记`、任务完成状态、`已执行动作`、落点状态都是 **static** → 不重启 Unity 就串局。

### F6. `.dsh` 的 PowerShell 脚本要存成**带 BOM 的 UTF-8** ⚠️
**症状**（2026-09-28，换到只有 PowerShell 5.1 的电脑上）：
跑 `.dsh\health.ps1` 报一堆**语法错误**：`意外的标记")"`、`不允许使用空管道元素`、
`表达式中缺少右")"`，而且报错行里的中文全是乱码（`绐楀彛` 这种）。

**真因**：脚本是**无 BOM 的 UTF-8 + 含中文**，而 **Windows PowerShell 5.1 对无 BOM 文件
按 ANSI(GBK) 解码** → 中文变乱码 → 把引号/括号吃坏 → 整个脚本解析失败。
`pwsh` 7 默认按 UTF-8 读，所以在有 pwsh 7 的电脑上从来不出问题（家里那台就是）。

**三种解法**（按推荐顺序）：
1. **给文件加 UTF-8 BOM** —— `health.ps1` / `serve-unity-mcp.ps1` 已加。
   3 个字节，pwsh 7 也认，两边都能跑。
2. 脚本**只写 ASCII**（`uni.ps1` 就是这个策略，文件头注释写明了原因）。
3. 用 `pwsh` 7 跑（但这台机器上没有，不能依赖）。

**判断某个脚本在这台机器上能不能跑**：看它「有没有 BOM」+「有没有中文」，
无 BOM 且含中文 → 在 PS 5.1 上必挂。

> 另外两个相关点：
> - `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` 才能直接 `& script.ps1`
>   （这台机器的执行策略禁止跑脚本）；不想改策略就 `[scriptblock]::Create((Get-Content $p -Raw -Encoding UTF8))`。
> - **别用 shell 拼含中文的命令**：经 harness 传过去会被损坏（本项目已知坑，
>   见 `docs/guides/对话系统使用说明.md` §5）。要写中文文件就用文件编辑工具。

### F7. ⚠️ 编辑配置表 CSV 会**丢掉 UTF-8 BOM** → Excel 打开全是乱码
**症状**（2026-09-29 用户报"我的那些表打开现在是乱码"）：
`主动神通表.csv` / `功法表.csv` / `被动神通表.csv` 在 Excel 里整片乱码。

**真因**：这几个文件原来是 **UTF-8 with BOM**，我用文本编辑工具改它们时，
写回去变成了 **UTF-8 without BOM**。中文 CSV 没有 BOM 时，
**Excel（中文 Windows）会按 ANSI/GBK 解** → 乱码。

**怎么一眼确认是它**：`git diff` 里表头那一行会"删了又加"，而**文字一个字没变** ——
变的只有开头那个看不见的 `U+FEFF`：
```
-﻿神通id,神通名称,...      ← HEAD 版有 BOM
+神通id,神通名称,...       ← 我的版本 BOM 没了
```

**修法**：把 BOM 加回去（字节级写入 `EF BB BF` + 原内容）。
本次把 `Assets/Data/Tables/` 下**全部 13 个 CSV 统一都加上 BOM**
（本来就有的 5 个 + 补的 8 个），这样整套一致，Excel 都能正常打开。

**BOM 会不会把导入器搞坏？不会** —— 实测带 BOM 重跑「修仙/从配置表生成资产」，
13 张表全是「新建 0 更新 N」（没有因为列名错位而新建资产），
抽查资产值也都对（`ability_shunlei_tianshan` 结算=追踪弹/倍率=3/耗灵=55…）。
`File.ReadAllText` / `ReadAllLines` 默认会**自动吃掉 BOM**，所以列名不受影响。

> **规矩**：以后改 `Assets/Data/Tables/*.csv`，**改完要检查第一行前 3 字节是不是 `EF BB BF`**；
> 用文本编辑工具批量改过之后，跑一次"补 BOM"的检查再交。
> 同理适用于任何"中文 + 要给 Excel/PS 5.1 看"的文件（参考 **F6**）。

### F8. ⚠️ 编辑器工具**别用 `EditorUtility.DisplayDialog` 弹报告** —— 模态框会挡住主线程，把自动化卡死
**症状**（2026-09-29 用户报）："你跑导入器、或者用一些工具，跑完会跳出一个需要点一下确认的
Windows 面板，但**在你那里好像是默认没有跑完，然后就一直思考、卡住**，浪费 token 和时间。"

**真因**：`EditorUtility.DisplayDialog` 是**模态**的 —— 它**阻塞编辑器主线程**直到有人点按钮。
AI 通过桥跑菜单时**没人去点**，于是：
命令永远不返回 → 调用方（我）以为还没跑完 → 一直等 → 白烧时间。

**修法（本次）**：**报告类弹框一律改成写 Console**（信息本来就已经 `Debug.Log` 过了，弹框纯属重复）：

| 文件 | 原来 | 现在 |
|---|---|---|
| `面板库收集器.cs` | 收集完弹"神通 N / 法宝 N …" | 只 `Debug.Log`（内容一样） |
| `场景一致性体检.cs` | 弹整份体检报告 | 只 `Debug.Log` |
| `面板目录清理.cs` | 开头报错弹框 + 结尾报告弹框 | 都改成 `Debug.Log` / `Debug.LogError` |
| `回填效果引用.cs` | `if (!静默) DisplayDialog(...)` | 去掉弹框（`静默` 参数留着不改调用点） |

**保留**的弹框只剩"**动手改东西之前**的真确认"（这些是有意挡住误操作的）：
`NpcAssetFixer`（3 处）、`NpcAvatarFixer`（1 处）、`VillageSceneBuilder`（覆盖已存在场景前 1 处）。

#### 万一以后还是撞上了一个模态框，**别干等**，这样收场：
1. **`unity_job`（action `list` 或 `status`）** —— 它跑在**后台线程**上，
   **主线程被模态框挡住时它照样能用**；被挡住的命令会以 "detached" 形式连同
   **弹框标题 / 正文 / 按钮文字**一起报回来。
2. **`unity_dialog`（action `click`，`button` 填按钮文字的正则，如 `"好|确定|OK"`）** 点掉它。
3. 再 **`unity_job`（action `status`，带 job_id）** 把那个被挡住的命令的**结果收回来**。

> **规矩**：编辑器工具里**只有"即将破坏性修改"才允许弹模态框**；
> **任何报告/统计/完成提示都写 Console**。要用户看的东西，Console 一样看得见。

## 【硬性规矩】新增字段必须想清楚"空/null 是什么语义"

> 这一条是被反复批评后立的（2026-09-27）。**不是风格问题，是正确性问题。**

### 加任何字段前，先回答三个问题

1. **它可能是 null / 空吗？**（`Resources.Load` 读不到、表里没填、旧资产没有这个字段 → 都会是 null/空）
2. **null/空 代表什么业务含义？**（"还没配置" / "不限制" / "用默认值" / "真的有 0 个"）
3. **看到 null/空 时，代码该做什么？**（用默认值 / 跳过 / **明确报错**）

**三个问题答不出来，就不要加这个字段。**

### 两条硬性要求

**① 声明时就给初值**（让"默认语义"看得见）

```csharp
public string 打标记 = "";                                   // ✓ 空 = 没有标记
public List<X> 列表 = new List<X>();                         // ✓ 空 = 一个都没有（不是 null！）
public float 打完停留 = 0f;                                  // ✓
public string 目标场景;                                      // ✗ 不给初值 → 调用方忘了就是 null
```

**集合一律 `= new List<T>()`**，绝不留 null。否则每个用它的地方都得判空，迟早漏一处。

**② 允许 null 的地方，必须"响亮地失败"**

```csharp
var 库 = PanelDatabase.取();
if (库 == null) return;              // ✗ 静默失效：面板空白，一句日志都没有，极难查
```

```csharp
if (库 == null)
{
    if (!报过) { 报过 = true; Debug.LogError("[面板库] 读不到 .../面板库.asset —— 面板会是空的。修法：菜单「修仙/面板/收集面板目录」"); }
    return;                          // ✓ 明确报错 + 说清怎么修 + 只报一次
}
```

### 已经踩过的（都是"没想清空值语义"）

| 现象 | 空值没处理的地方 |
|---|---|
| 面板页空白、毫无线索 | `PanelDatabase.取()` 返回 null 时静默 `return` |
| 12 个学习道具打包后失效 | `使用效果.神通/功法/外观` 为 null 时退到 `#if UNITY_EDITOR` 的查找，打包返回 null，**没人报错** |
| 门派便服"弄没了" | 奖励挂在**对话之后**的阶段，错位后玩家以为丢了 |
| 弟子名字变成"五个字母" | 起名界面缓冲没做长度/内容校验 |
| 回古古镇重演开场 | `演过` 是实例字段 → 每次重建都是初始值 `false` |

### 反向检查（写完一段代码后问自己）

- [ ] 我为这个新字段写了初值吗？
- [ ] 集合字段是 `new` 出来的吗（不是 null）？
- [ ] 可能为 null 的地方，是**报错**还是**静默跳过**？
- [ ] 如果静默跳过了，**排查的人能不能从日志看出发生了什么**？

### 补充：判定型条件必须保证"有基准"，且基准要**够得着**

`任务条件.NPC到位` 曾同时踩三个坑（2026-09-27，用户报"大师兄飞到我身边就没后续了"）：

1. **目标 id 只填在「动作目标npcId」上**，条件读的「目标npcId」是空的 →
   `查找在场NPC("")` 拿不到人。**修**：条件侧读不到就退回动作侧那个 id。
2. **用了只读的 `查找在场NPC`**，而任务生成的 NPC **切场景会被销毁** →
   永远等不到人。**修**：改用会重建的 `找NPC`。
3. **重建点离玩家 2 米，而判定阈值是 1.5 米** → 重建了也判不到位。
   **修**：重建距离取 `min(1.2, 到位判定距离 * 0.8)`，**必须小于阈值并留余量**。

**通用教训**：
- 判定型条件要保证「有基准」：动态落点 → 表里坐标 → 玩家位置，逐级兜底，**不能默默用 (0,0,0)**。
- 兜底路径也要**能满足判定**（重建点到判定基准的距离必须 < 阈值）。
- 兜底提示**只报一次**（写在每帧判定里会刷屏几百条 —— 我犯过）。
